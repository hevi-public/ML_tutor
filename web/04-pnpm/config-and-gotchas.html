pnpm

Config & gotchas

v11 moved where settings live. If you upgraded from 10 and your configuration stopped applying, this is why.

The v11 config break
  • .npmrc is now registry and auth only.
  • Everything else moves to pnpm-workspace.yaml (per project) or ~/.config/pnpm/config.yaml (global).
  • The pnpm field in package.json is no longer read.
  • Environment variables use pnpm_config_*, not npm_config_*.
  • These are silent — old settings are ignored, not warned about.

What changed

Worth checking deliberately after an upgrade rather than waiting to notice. Anything you set in .npmrc that is not a registry or auth setting — auto-install-peers, node-linker, shamefully-hoist, strict-peer-dependencies — has stopped applying.

Where each setting goes now

FileHolds
.npmrcRegistry URLs, auth tokens, scoped registries. Nothing else
pnpm-workspace.yamlEvery pnpm setting for this project, plus workspace packages and catalogs
~/.config/pnpm/config.yamlYour machine-wide defaults
package.jsonpackageManager, and your dependencies. The pnpm field is dead
 
# pnpm-workspace.yaml
packages:
  - 'apps/*'

# packages allowed to run install scripts
allowBuilds:
  - esbuild
  - '@angular/build'

# strictness
strictPeerDependencies: false
autoInstallPeers: true

# supply chain (these are the v11 defaults, shown for clarity)
minimumReleaseAge: 1440
blockExoticSubdeps: true
# .npmrc — auth and registry only
@acme:registry=https://npm.acme.internal/
//npm.acme.internal/:_authToken=${NPM_TOKEN}

The settings worth knowing

SettingDoesUse when
allowBuildsPackages permitted to run install scriptsesbuild, sharp, native modules
strictPeerDependenciesUnmet peers are an errorDefault is strict; loosen only deliberately
autoInstallPeersInstall missing peers automaticallyConvenient; hides genuine conflicts
shamefullyHoistFlat node_modules like npmLast resort for a tool that scans the tree
nodeLinkerisolated (default), hoisted, pnphoisted for React Native and similar
overridesForce a version anywhere in the treePatching a transitive vulnerability
packageExtensionsAdd missing metadata to someone else's packageA dependency with wrong or absent peers
minimumReleaseAgeExcludePackages exempt from the quarantineYour own scoped packages in CI
verifyDepsBeforeRunCheck node_modules matches the lockfile before running scriptsDefaults to install in v11

Overrides

# pnpm-workspace.yaml
overrides:
  # everywhere in the tree
  minimist: '^1.2.8'
  # only under a specific parent
  'some-pkg>lodash': '^4.17.21'

The blunt instrument for a transitive vulnerability you cannot wait on. Leave a comment saying why and when it can go, because an override that has outlived its reason is a version pin nobody understands.

Patching a dependency

pnpm patch some-broken-pkg@2.1.0
# edit the files in the temp directory pnpm prints
pnpm patch-commit /path/that/pnpm/printed

Writes a patch file and records it, so the fix is reapplied on every install. Vastly better than forking, and unlike editing node_modules directly it survives a reinstall and does not corrupt the shared store. Note that v11 removed ignorePatchFailures: a patch that no longer applies is now an error rather than a warning, which is right — a silently skipped patch is a bug that reappears.

Common failures

"Cannot find module X" after switching from npm A phantom dependency — the code imports something it never declared. Add it to package.json. Do not reach for shamefullyHoist.
A package's install script did not run Blocked by default since v10. Add it to allowBuilds. In v11 strictDepBuilds defaults to true, so this is an error rather than a silent skip — which is an improvement, since the v10 version failed later and further away.
CI cannot install a package published this morning minimumReleaseAge quarantines new versions for 24 hours by default in v11. Intentional. If it is your own package, add it to minimumReleaseAgeExclude.
A bundler or test runner cannot resolve a linked package Some tools resolve paths themselves rather than through Node, and the symlinked layout confuses them. For Vite and Vitest the answer is usually optimizeDeps.include or server.deps.inline — see pnpm with Angular.
Two lockfiles in one repository A stray package-lock.json next to pnpm-lock.yaml means someone ran npm install. They will drift, and CI will install something different from your machine. Delete the npm one and add it to .gitignore.

CI

- uses: pnpm/action-setup@v4          # reads packageManager from package.json
- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: pnpm
- run: pnpm ci                        # or pnpm install --frozen-lockfile

Order matters: pnpm/action-setup must come before setup-node, because cache: pnpm needs pnpm on the PATH to locate the store.
