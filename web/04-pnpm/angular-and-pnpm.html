pnpm with Angular

The practical intersection: making the CLI use pnpm, keeping @angular/* in lockstep, and the two places the symlinked layout causes real friction.

At a glance
  • ng new --package-manager pnpm, or set it in angular.json afterwards.
  • ng update works normally — it shells out to whichever package manager the workspace is configured for.
  • Angular's build needs esbuild in allowBuilds.
  • Use a catalog for @angular/*: they must all be the same version.

Setting up

pnpm dlx @angular/cli@22 new my-app --package-manager pnpm
// angular.json — for an existing workspace
{
  "cli": { "packageManager": "pnpm" }
}

That setting is what makes ng add, ng update and the CLI's own install prompts use pnpm rather than shelling out to npm and producing a second lockfile.

# pnpm-workspace.yaml — Angular's builder needs esbuild to build itself
allowBuilds:
  - esbuild
Symptom: the build fails on a fresh clone but works after a rebuild Usually esbuild missing from allowBuilds — its postinstall fetches the platform binary, and without it the build fails at the point it tries to use it. In v11 strictDepBuilds defaults to true, so you get a clear error at install time instead.

Keeping Angular versions in lockstep

Every @angular/* package must be on the same minor. In a monorepo, a catalog makes that structural rather than a convention people have to remember:

# pnpm-workspace.yaml
catalogs:
  ng:
    '@angular/animations': ^22.0.8
    '@angular/common': ^22.0.8
    '@angular/compiler': ^22.0.8
    '@angular/core': ^22.0.8
    '@angular/forms': ^22.0.8
    '@angular/platform-browser': ^22.0.8
    '@angular/router': ^22.0.8
    '@angular/cdk': ^22.0.6
    '@angular/aria': ^22.0.6
// every app and lib
{
  "dependencies": {
    "@angular/core": "catalog:ng",
    "@angular/router": "catalog:ng"
  }
}
ng update does not know about catalogs It rewrites versions in package.json, where it will find "catalog:ng" rather than a range. Upgrade by editing the catalog block yourself, then run ng update --migrate-only --from=21 --to=22 to get the code migrations without the version rewriting. Worth knowing before your first catalog upgrade.

Peer dependencies

pnpm is stricter about unmet peers than npm, which surfaces real conflicts that npm hid. Angular libraries peer-depend on @angular/core, so a library that has not published support for your major will say so at install time rather than failing mysteriously at runtime.

SituationDo
A library genuinely does not support your Angular versionWait, or find an alternative. The error is correct
It works fine but the range is stalepackageExtensions to widen its declared peer range
You are mid-upgrade and need to proceedstrictPeerDependencies: false, temporarily
A peer is genuinely optionalautoInstallPeers: false and install it yourself
 
packageExtensions:
  some-angular-lib@1.2.3:
    peerDependencies:
      '@angular/core': '>=20 <23'

Vitest and the symlinked layout

Vite resolves some paths itself rather than through Node, and a symlinked workspace package can end up outside its dependency optimisation — which surfaces as a module resolution failure or a duplicated Angular instance in tests. The fix is to tell Vite about it rather than to flatten the tree:

// vitest.config.ts — only if you actually hit this;
// remember to point the builder at it with runnerConfig
export default defineConfig({
  test: {
    server: {
      deps: {
        inline: [/^@acme\//],       // process linked workspace packages
      },
    },
  },
});
Two copies of @angular/core If a linked library resolves its own copy rather than sharing the application's, DI breaks in confusing ways — an InjectionToken from one copy will not match a provider from the other. Check with pnpm why @angular/core; the answer is normally a peer dependency declared as a regular dependency in the library.

CI

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm ci
      - run: pnpm exec ng build
      - run: pnpm exec ng test --no-watch

In a monorepo, add a filter so pull requests only build what could have broken: pnpm --filter "...[origin/main]" test.

Docker

FROM node:22-slim AS build
RUN corepack enable
WORKDIR /app
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY apps/web/package.json apps/web/
RUN pnpm ci
COPY . .
RUN pnpm --filter web build

FROM nginx:alpine
COPY --from=build /app/apps/web/dist/browser /usr/share/nginx/html

Copying the lockfile and manifests before the source keeps the install layer cached across source changes. For a Node server rather than a static build, pnpm --filter web deploy --prod ./out produces a directory with only that package and its production dependencies.
