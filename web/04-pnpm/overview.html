How pnpm works

Two design decisions — a shared content-addressable store and a non-flat node_modules — explain almost every way pnpm differs from npm, including the ones that look like bugs.

At a glance
  • One copy of each package version on disk globally, hard-linked into each project. Ten projects on the same version cost the space of one.
  • node_modules contains only your declared dependencies. Everything else lives in node_modules/.pnpm and is symlinked.
  • That is why an import you never declared stops resolving — a phantom dependency. It is the feature working.
  • In v11 the store index is a single SQLite database rather than a file per package.

The store

npm downloads and extracts a copy of every package into every project. pnpm extracts each package version once, into a global content-addressable store keyed by hash, and builds each project's node_modules from hard links into it. The files are shared, so a second project using the same version costs essentially nothing.

The practical consequences: installs are fast when the store is warm (nothing to download or extract), disk usage across many projects is a fraction of npm's, and offline installs work for anything you have installed before.

Hard links mean edits are shared Editing a file inside node_modules to debug something edits the copy in the store, and therefore every project using that version. Use pnpm patch instead — it takes a copy, lets you edit it, and produces a patch file that is reapplied on install.

The layout

This is the part that changes behaviour rather than just performance. With npm's flat node_modules, every transitive dependency is hoisted to the top level, so require('lodash') works whether or not you declared lodash — as long as something in your tree depends on it.

npm — flat and hoisted            pnpm — only what you declared
node_modules/                     node_modules/
├── express/                      ├── express -> .pnpm/express@5.1.0/…
├── body-parser/   ← transitive   └── .pnpm/
├── cookie/        ← transitive       ├── express@5.1.0/
├── lodash/        ← transitive       │   └── node_modules/
└── …  (hundreds more)                │       ├── express/
                                      │       ├── body-parser -> …
   any of these is importable         │       └── cookie -> …
   whether you declared it or not     └── body-parser@2.2.0/…

In pnpm the top level contains only your direct dependencies. Each package gets its own node_modules under .pnpm containing symlinks to exactly what it declared. Node resolves through the symlinks and finds only what should be visible.

"It works with npm but not pnpm" Nearly always a phantom dependency: the code imports a package it never declared, and npm's hoisting happened to make it available. The fix is to add it to package.json. It is worth doing rather than working around, because the npm version was already broken — it would break the day the transitive dependency changed or was removed.
shamefullyHoist is the escape hatch, not the fix Setting shamefullyHoist: true makes pnpm build a flat node_modules like npm's. The name is a joke with a point. It is occasionally necessary for a tool that scans node_modules directly, but reaching for it to fix a missing import is choosing to keep the bug.

Symlinks and tooling

The symlinked layout occasionally confuses tools that resolve paths themselves rather than asking Node. In an Angular project the one you may meet is Vite's dependency optimiser, which can miss a linked workspace package — the answer is usually adding it to optimizeDeps.include or server.deps.inline rather than flattening the whole tree. See config & gotchas.

What changed in v11

Also in v11, from the release notes: pnpm itself is pure ESM and requires Node 22.13 or later; the store index moved from a JSON file per package to a single SQLite database (store version 11); global installs are isolated with their own lockfile; and there are new first-class commands including pnpm ci, pnpm sbom, pnpm clean and pnpm peers check.
