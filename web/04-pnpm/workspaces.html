pnpm

Workspaces, filters & catalogs

Catalogs are the reason to use pnpm for an Angular monorepo: one place to say which version of @angular/* everything uses.

At a glance
  • pnpm-workspace.yaml lists the packages — and, since v11, holds all pnpm settings too.
  • workspace:* means "the copy in this repo", and fails loudly if there isn't one.
  • catalog: names a version once for the whole repo.
  • --filter selects packages, including by dependency relationship and by what git says changed.

The workspace file

# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'libs/*'
  - '!**/dist/**'

# One version per dependency, for the whole repo.
catalog:
  typescript: ~7.0.2
  rxjs: ^7.8.2

# Named catalogs, when one version genuinely is not enough.
catalogs:
  angular22:
    '@angular/core': ^22.0.8
    '@angular/common': ^22.0.8
    '@angular/router': ^22.0.8

# v11: pnpm settings live here too, not in .npmrc
allowBuilds:
  - esbuild
  - '@angular/build'
// apps/web/package.json
{
  "dependencies": {
    "@angular/core": "catalog:angular22",
    "@angular/common": "catalog:angular22",
    "rxjs": "catalog:",
    "@acme/ui": "workspace:*"
  }
}

Why catalogs matter for Angular

Angular packages must move in lockstep — @angular/core at 22 with @angular/router at 21 fails at runtime in ways that are tedious to diagnose. In a monorepo with eight packages that each list eight Angular dependencies, that is 64 version strings to keep identical, and upgrading means editing all of them.

With a catalog it is one block. Drift becomes impossible rather than merely discouraged, and the upgrade is a single edit.

catalog: is rewritten on publish A published package cannot carry "catalog:" — consumers have no catalog. pnpm replaces it with the resolved version when packing, the same way it handles workspace:. This is only a concern for packages you actually publish.

The workspace protocol

SpecifierMeansPublished as
workspace:*The local package, any versionThe exact version
workspace:^The local package^ plus the version
workspace:~The local package~ plus the version
workspace:../uiA specific pathThe version

The value over a plain version range is that it fails if no local package matches, instead of quietly downloading a same-named package from the registry — which is both a confusing bug and a dependency-confusion attack vector.

Filters

SelectorSelects
--filter webThe package named web
--filter "./apps/*"By directory glob
--filter "@acme/*"By name pattern
--filter web...web and everything it depends on
--filter ...webweb and everything that depends on it
--filter ...web...Both directions
--filter "web^..."Its dependencies, excluding web itself
--filter "...[origin/main]"Packages changed since a git ref, plus their dependents
--filter "!web"Everything except web
 
# build a lib and everything that consumes it
pnpm --filter ...@acme/ui build

# test only what this branch could have broken
pnpm --filter "...[origin/main]" test

# run every app's dev server at once
pnpm --filter "./apps/*" --parallel dev
The ...[origin/main] filter is the CI win On a large monorepo, testing only packages whose code changed plus everything downstream of them is the difference between a two-minute and a forty-minute pipeline — without the risk of missing a dependent, which is what makes naive "only test what changed" schemes unsafe.

Ordering

pnpm -r build runs in topological order: a package builds after everything it depends on. That is usually what you want and is why --parallel (which ignores order) should be reserved for things like dev servers that have no build-order relationship.

Deploying one package

pnpm --filter web deploy --prod ./out

Produces a self-contained directory with the package and its production dependencies, workspace links resolved to real copies. For a Docker image this replaces copying the whole monorepo and hoping the layer cache saves you.
