jOOQ: the model

jOOQ's bet is the opposite of an ORM's: instead of hiding SQL behind objects, it generates typed Kotlin from your actual schema so SQL becomes compile-checked code. You write the queries; it guarantees they reference real tables, real columns, right types.

At a glance
  • Codegen is the foundation: migrated schema in, Tables.ORDERS etc. out. A renamed column breaks the build, not the dashboard at runtime.
  • No entity lifecycle: no dirty checking, no lazy proxies, no flush ordering. Rows in, DTOs out, SQL visible.
  • Licensing is a fact to know: the OSS edition (Apache-2.0) is licensed for open-source databases — fine on Postgres. Commercial databases require a paid edition. OSS needs JDK 21 since 3.20.
  • Boot's starter wires DSLContext into Spring transactions — @Transactional just works (see data & transactions).

Do it this way now

// A repository is a class with queries — not an interface a framework implements.
@Repository
class OrderRepository(private val dsl: DSLContext) {

    fun findRecent(customer: CustomerId, limit: Int): List =
        dsl.select(ORDERS.ID, ORDERS.PLACED_AT, ORDERS.TOTAL_CENTS)
            .from(ORDERS)
            .where(ORDERS.CUSTOMER_ID.eq(customer.value))
            .orderBy(ORDERS.PLACED_AT.desc())
            .limit(limit)
            .fetch(mapping(::OrderSummary))     // constructor-ref mapping
}

DDLDatabase jOOQ parses your .sql migration files into an in-memory model No Docker; but the parser, not Postgres, defines what's valid — dialect corners get missed
Shared dev database Codegen against a long-lived dev server Simple until the schema drifts from migrations; avoid for teams

What changed

jOOQ or JPA/Hibernate? One honest table

jOOQJPA/Hibernate
You writeSQL, typedEntity graphs; SQL is derived
Great atReads, reporting, window functions, CTEs, database features (MULTISET, MERGE)CRUD-heavy domains with deep object graphs and cascades
Failure modeVerbose inserts/updates for wide tables; you hand-roll patterns an ORM gives freeN+1s, LazyInitializationException, surprise flushes — implicit behaviour at a distance
Performance modelWhat you wrote is what runsDepends on fetch strategy tuning and cache layers
Schema changesCompile errors after codegenRuntime mapping errors, or drift if DDL is entity-generated
Honest summaryQuery-shaped services (this stack) fit jOOQ; aggregate-root domains with heavy write graphs are where JPA still argues its case
Gotcha: don't fight the generated types The moment codegen output gets hand-edited or committed selectively, the guarantee inverts — the types lie. Regenerate on every schema change (the Gradle task dependency does it), commit the whole output, and treat a dirty git diff under the generated package as the build telling you a migration happened.
