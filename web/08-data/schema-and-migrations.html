Schema & migrations

The schema is code: versioned SQL files, applied by Flyway on startup, and — because this stack runs jOOQ — the same migrated schema is what code generation compiles against. The pipeline's order is the whole trick.

At a glance
  • Flyway is the default here (Boot manages 12.4.0): plain SQL files, V-prefixed versions, a schema history table. Liquibase (5.0.3) is the alternative when you need changelog abstraction or rollback tooling.
  • The pipeline order: migrate a throwaway database → run jOOQ codegen against it → compile. Schema drift becomes a compile error, not a production incident.
  • Migrations are append-only. Editing an applied migration is how checksums break at 2am; fix forward with the next V-file.
  • Boot 4 note: the starter is explicit now — the card below.

Do it this way now

-- src/main/resources/db/migration/V014__order_totals.sql
-- One concern per migration; expand-migrate-contract for anything hot.
ALTER TABLE orders
  ADD COLUMN total_cents bigint;             -- 1 expand: nullable first

UPDATE orders SET total_cents = subtotal_cents + tax_cents
  WHERE total_cents IS NULL;                 -- 2 backfill

ALTER TABLE orders
  ALTER COLUMN total_cents SET NOT NULL;     -- 3 contract (next release if hot)
ConventionRule
Versioned filesV014__order_totals.sql — zero-padded, double underscore, description that reads in history
Repeatable filesR__views.sql for views/functions — re-applied when their checksum changes, always after V-files
Local resetDrop the schema and re-migrate; never edit applied files
Concurrent indexesCREATE INDEX CONCURRENTLY can't run in a transaction — mark the migration non-transactional
Out-of-orderLeave flyway.out-of-order=false unless parallel branches force it — ordering is the audit trail

What changed

Flyway or Liquibase?

FlywayLiquibase
Migration unitPlain SQL files (the DB's own dialect)Changesets in SQL, XML or YAML — abstracted
Mental modelNumbered scripts, forward-onlyChangelog graph with preconditions and contexts
Rollback storyWrite the inverse migration yourselfTooling-assisted rollbacks (paid tiers do more)
Fits whenOne database engine, SQL-literate team — this stackMulti-engine products, heavier governance needs
Gotcha: startup migrations and replicas Boot runs migrations on application startup — fine for one instance, a race for many. In multi-replica deployments, run migrations as a dedicated step (init container / CI job invoking the same Flyway config) and let app instances verify rather than apply. Flyway's history-table locking prevents corruption either way, but a deploy blocked behind a long backfill helps nobody.
Reading Hibernate-managed schemas

hibernate.hbm2ddl.auto=update — the schema as a side effect of entity annotations — still exists in old services. It has no history, no review artifact and no answer for data migrations, which is why every one of those services eventually adopts a migration tool and baselines with flyway.baseline-on-migrate=true.
