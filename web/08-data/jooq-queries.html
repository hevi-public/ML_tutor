Queries: MULTISET & row mapping

The two features that make jOOQ feel unfair: MULTISET turns nested collections into a typed, single-round-trip query, and path joins make foreign keys walkable. Together they produce the DTO shape your API wanted, straight from SQL.

At a glance
  • Nested lists → MULTISET (3.15+): the database serialises children per parent; jOOQ deserialises into your data classes. No duplicated parent rows, no in-memory regrouping.
  • Foreign keys → path joins: ORDERS.customer().NAME; to-many paths since 3.19.
  • Mapping → constructor references: fetch(mapping(::OrderSummary)) — positional, type-checked at compile time.
  • Know your fetch vocabulary: fetchOne (0..1, throws on 2+), fetchSingle (exactly 1), fetchOptional, plain fetch for lists.

What changed

Under the hood the MULTISET is emitted as SQL/JSON and parsed back — which is why it works over plain JDBC, and why the query stays one round trip regardless of nesting depth.

The canonical shape

// The API DTO — exactly what the endpoint returns
data class CustomerOrders(
    val name: String,
    val orders: List,
)
data class OrderWithLines(val id: UUID, val lines: List)
data class Line(val sku: String, val qty: Int)

fun customerOrders(id: CustomerId): CustomerOrders? =
    dsl.select(
        CUSTOMERS.NAME,
        multiset(
            select(
                ORDERS.ID,
                multiset(
                    select(ORDER_LINES.SKU, ORDER_LINES.QTY)
                    .from(ORDER_LINES)
                    .where(ORDER_LINES.ORDER_ID.eq(ORDERS.ID))
                ).convertFrom { it.map(mapping(::Line)) }
            )
            .from(ORDERS)
            .where(ORDERS.CUSTOMER_ID.eq(CUSTOMERS.ID))
        ).convertFrom { it.map(mapping(::OrderWithLines)) }
    )
    .from(CUSTOMERS)
    .where(CUSTOMERS.ID.eq(id.value))
    .fetchOne(mapping(::CustomerOrders))
// Two levels of nesting, one SQL statement, zero N+1.
Gotcha: MULTISET output is ordered only if you say so Children arrive in whatever order the database produced them. If the API promises ordered lines, put an orderBy inside the MULTISET subquery — sorting the outer query does nothing for the nested collections.
Gotcha: R2DBC + coroutines is its own lane The suspend integration rides on R2DBC — a different driver with a different pool (and no MULTISET emulation gaps on Postgres, but test it). With virtual threads, blocking JDBC from coroutines via a virtual-thread dispatcher is the boring, robust default; choose R2DBC deliberately, not because suspend looked nicer.
Reading pre-MULTISET jOOQ

Flat left-join selects regrouped with fetchGroups or Kotlin's groupBy, into(MyDto::class.java) reflection mapping (works, but positional mapping() type-checks), and hand-batched child queries. All still function; MULTISET replaced the reasons for them.
