The language, by version

What you can write on the line you are on. Each card below is a versioned fact: the badge tells you when the syntax became stable, and the version filter marks whether that includes you.

At a glance
  • Stable since 2.2: guard conditions in when, non-local break/continue, $$-interpolation.
  • Stable since 2.3: nested type aliases; the unused-return-value checker arrives (opt-in).
  • Stable since 2.4: context parameters, explicit backing fields.
  • Still experimental in 2.4: rich errors (union-typed error returns) and collection literals. Read about them, don't ship them.

What changed

The strongest use in this stack is the transaction handle: a repository function that must run inside a transaction declares context(tx: DSLContext), and only a transaction block can provide it — the requirement becomes a compile-time fact. See the jOOQ page for the wiring.

Gotcha: stable ≠ available A feature that is stable in 2.4 still fails on the 2.3 toolchain your build may actually run (Spring Boot's BOM pins Kotlin 2.3.21). Before reaching for context parameters, check which compiler CI uses — set the version filter above to see which cards apply to you.

Coming, but not yet: rich errors and collection literals

Both are experimental in 2.4 and both change daily code, which is exactly why they should wait until they stabilise:

// EXPERIMENTAL in 2.4 — shown so you recognise it, not so you ship it
// Rich errors: a function admits failure in its type, without exceptions
// or a wrapper class:
fun parsePort(s: String): Int | ParseError

// Collection literals:
val ports = [8080, 8081, 9090]

The stable answer for errors in 2.4 remains what it has been: a sealed hierarchy when the caller must branch, exceptions when it cannot recover.

Reading pre-2.x code

Old codebases fake the features above: nested if chains where a guard condition belongs, run/labeled-return contortions where non-local break belongs, and a ${'$'} incantation wherever a template needed a literal dollar. They all still compile — recognising them as workarounds, not style, is the point of the cards above.
