Coroutines — or virtual threads?

They solve different problems. Virtual threads make blocking cheap, so thread-per-request code scales without a rewrite. Coroutines make concurrency structured — cancellation, scoping and streams as language-level facts. On Boot 4 with Java 21+, the usual answer is both: virtual threads underneath, coroutines where the logic is actually concurrent.

The one-line test
  • Request comes in, you call the DB, you return — virtual threads. Plain blocking code, one property, done.
  • One request fans out to several calls that should share a deadline and die together — coroutines. That is structured concurrency, and no thread model gives it to you.
  • A stream of values over time (SSE, polling, batches) — Flow.
  • An existing WebFlux service that works — leave it. Rewrites need a reason, and "virtual threads exist" isn't one.

The canonical shape

// Structured fan-out: three lookups, one deadline, all-or-nothing.
suspend fun dashboard(id: UserId): Dashboard =
    withTimeout(800.milliseconds) {          // 1 deadline for the whole scope
        coroutineScope {
            val user   = async { users.find(id) }        // 2 children start
            val orders = async { orders.recent(id) }
            val flags  = async { features.forUser(id) }
            Dashboard(user.await(), orders.await(), flags.await())
        }   // 3 any failure cancels the siblings and rethrows here
    }

The property to internalise: the scope is a tree. Cancelling a parent cancels every child; a failing child fails the scope. Concurrency gets the same discipline lexical scope gave local variables.

Gotcha: pinning is a Java-version fact On Java 21, a virtual thread that blocks inside a synchronized block pins its carrier thread — old JDBC pools and drivers could stall under load (pgJDBC replaced its internal synchronized with locks back in 42.6 for exactly this reason). JDK 24 removed that limitation (JEP 491), so on Java 25 pinning is no longer a design constraint. Know which side of that line production runs on.

What NOT to migrate

  • Working WebFlux services. Reactive code that already exists and performs is not debt. Migrate when you touch it for other reasons.
  • Blocking repositories called from coroutines — don't wrap every call in async. Sequential code should read sequentially; reach for async only at real fan-out points.
  • Coroutine code to "plain threads + virtual threads". You would be re-implementing cancellation, deadlines and scoping by hand — the parts coroutines do for free.
