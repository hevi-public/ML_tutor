The JVM side: KSP, interop, null-safety

The parts of Kotlin that are really contracts with the JVM: which Java your bytecode targets, how annotation processing runs, and what the compiler believes about Java's nulls.

At a glance
  • Set the toolchain, not the target. jvmToolchain(25) aligns Java and Kotlin compilation in one line; without it, kotlinc's default JVM target is still 1.8.
  • kapt is maintenance-mode; KSP is the processor. And KSP versions stopped tracking Kotlin versions in late 2025 — one less lockstep upgrade.
  • JSpecify violations are compile errors since Kotlin 2.1 — which matters daily now that Spring Framework 7 annotates its whole API.
  • Boot 4 runs Java 17–26; 25 is the LTS to target — and virtual threads need 21+.

Do it this way now

// build.gradle.kts — the three JVM decisions, made explicit
plugins {
    alias(libs.plugins.kotlin.jvm)
    alias(libs.plugins.ksp)                    // not kotlin-kapt
}

kotlin {
    jvmToolchain(25)                           // one line: javac + kotlinc agree
    compilerOptions {
        allWarningsAsErrors = true             // JSpecify violations stay fatal
    }
}

What it replaced

In this stack the processors that matter are jOOQ's (none — codegen is a build step, not annotation processing), kotlinx serialization (a compiler plugin, also not kapt) and mapping/DI libraries like MapStruct or Dagger if you use them — those are the kapt holdouts to check before deleting the plugin.

Gotcha: platform types didn't go away JSpecify enforcement only covers annotated APIs. A Java library without annotations still hands you platform types (String!) that the compiler trusts blindly. The discipline: treat any un-annotated Java boundary as ? until proven otherwise — the compiler won't do it for you there.
Reading kapt-era builds

apply plugin: "kotlin-kapt", kapt("…") dependency configurations, and generated sources under build/generated/source/kapt mark the old world. The mechanical translation is ksp("…") — but only after confirming each processor ships KSP support, which nearly all maintained ones now do.
