Kotlin DSL & version catalogs

The two idioms that make a 2026 build recognisable: scripts in Kotlin, versions in one TOML file. Both are old news individually — the point of this page is the combined shape and its sharp edges.

At a glance
  • build.gradle.kts + libs.versions.toml is the documented default; every snippet in current Gradle docs assumes both.
  • The catalog holds plugins too — alias(libs.plugins.spring.boot) — so even plugin versions live in the TOML.
  • Let Boot's BOM version libraries it manages: catalog entries for Spring/jOOQ/Jackson need no version — the platform decides. Catalog versions are for what the BOM doesn't cover.
  • Dashes become dots: spring-boot in the TOML is libs.spring.boot in scripts.

Do it this way now

// build.gradle.kts — a service module, whole build definition
plugins {
    alias(libs.plugins.kotlin.jvm)
    alias(libs.plugins.kotlin.spring)     // allopen preset for Spring proxies
    alias(libs.plugins.spring.boot)
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-webmvc")
    implementation("org.springframework.boot:spring-boot-starter-jooq")
    implementation(libs.kotlinx.coroutines)   // versioned by the catalog
    testImplementation("org.springframework.boot:spring-boot-starter-webmvc-test")
}

kotlin { jvmToolchain(25) }

What it replaced

Gotcha: where libs doesn't reach The typed libs.* accessors are generated for project build scripts. Inside buildSrc/build-logic plugin source code they don't exist by magic — a convention plugin reads the catalog through versionCatalogs.named("libs") instead. Budget ten minutes for this the first time, not two hours.
Gotcha: two version authorities A version in the catalog and in Boot's BOM is a conflict waiting to confuse someone. House rule that works: the BOM owns everything it manages; the catalog owns the rest (kotlinx libraries, MapStruct, build plugins). Overriding a BOM version deliberately? Do it visibly via extra["jooq.version"], not by a quiet catalog entry.
Reading pre-catalog builds

ext { springBootVersion = '…' } in the root script, "$springBootVersion" string interpolation per dependency, a Versions.kt object in buildSrc, or — the darkest timeline — versions inline in every module and unequal between them. The catalog migration is mostly regex work and immediately makes Renovate/Dependabot useful.
