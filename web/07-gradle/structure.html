Structure & convention plugins

How a multi-module build shares configuration without the root script reaching into every project. One pattern — convention plugins in an included build-logic build — replaced a decade of allprojects folklore.

At a glance
  • Each module declares what it is (plugins { id("conventions.kotlin-service") }); the convention plugin says what that means. No module is configured from outside.
  • build-logic (included build) over buildSrc is the current convention for where those plugins live — same code, better isolation.
  • allprojects/subprojects is documented as discouraged — it couples projects and blocks the configuration-cache/isolated-projects direction Gradle is moving in.
  • Precompiled script plugins are enough. A convention plugin is just a .gradle.kts file in build-logic; writing a Plugin<Project> class is rarely necessary.

Do it this way now

.
├── settings.gradle.kts          # includeBuild("build-logic"); module list
├── gradle/libs.versions.toml
├── build-logic/
│   ├── settings.gradle.kts      # pulls in the same version catalog
│   └── src/main/kotlin/
│       ├── conventions.kotlin-base.gradle.kts      # toolchain, warnings, tests
│       └── conventions.kotlin-service.gradle.kts   # base + Boot + jOOQ codegen
├── service-orders/build.gradle.kts   # plugins { id("conventions.kotlin-service") }
└── lib-domain/build.gradle.kts       # plugins { id("conventions.kotlin-base") }
// build-logic/src/main/kotlin/conventions.kotlin-base.gradle.kts
plugins {
    id("org.jetbrains.kotlin.jvm")
}

kotlin {
    jvmToolchain(25)
    compilerOptions { allWarningsAsErrors = true }
}

tasks.withType<Test>().configureEach {
    useJUnitPlatform()
    maxParallelForks = (Runtime.getRuntime().availableProcessors() / 2).coerceAtLeast(1)
}

What it replaced

Gotcha: plugin versions live in build-logic's classpath A convention plugin that does id("org.jetbrains.kotlin.jvm") doesn't state a version — the version comes from build-logic's own dependencies (implementation(libs.plugins.kotlin.jvm.toDep()) or the marker artifact). Forgetting this puts you back to "which Kotlin is this build actually running" — pin it once in build-logic, sourced from the same catalog.
buildSrc, and the invalidation folklore

buildSrc works fine for the same purpose, and the old lore that any buildSrc change invalidates the whole build stopped being true around Gradle 8. The reasons build-logic won as the convention are softer: it behaves like a normal included build, doesn't sit on every classpath implicitly, and scales to being shared between repos. No urgency to migrate a working buildSrc — just don't start a new one.
