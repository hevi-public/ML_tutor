Gradle: the 8 → 9 arc

Gradle's last few years read as one project: make builds declarative enough to cache aggressively. Kotlin DSL, version catalogs and convention plugins are the idioms; the configuration cache is the payoff. This page is the arc and the upgrade mechanics.

At a glance
  • Current is 9.7.0. Only the current major line gets fixes — there is no LTS. The wrapper pins the version per repository, so upgrading is a one-line, one-repo decision.
  • The modern idioms arrived in 8.x (config cache stable 8.1, Kotlin DSL default 8.2); 9.x makes them the mainline and Gradle 10 is slated to flip the configuration cache on by default.
  • Two JVMs, two decisions: the daemon needs Java 17+ to run Gradle 9; your code compiles on whatever the toolchain says (jvmToolchain(25)). Don't conflate them.
  • Deprecation warnings are the upgrade path: --warning-mode all on the current major tells you exactly what the next major will break.

What it replaced

Upgrading a repository

What you wantCommand
Pin a new Gradle for this repo ./gradlew wrapper --gradle-version 9.7.0
Find what the next major will break ./gradlew build --warning-mode all
Check plugin compatibility first Kotlin plugin, Boot plugin and jOOQ codegen plugin release notes — these three gate this stack's upgrades
See where build time goes ./gradlew build --scan
Gotcha: "unsupported class file version" isn't about your code When a Gradle upgrade fails with class-file-version errors, the daemon JVM is usually the culprit — CI images pinning an old JDK for the build tool while the toolchain happily provisions the right JDK for the code. Set the daemon JVM explicitly (org.gradle.java.home or the CI image) and let toolchains own compilation.
Reading Gradle 6/7-era builds

Groovy scripts with compile/runtime configurations (removed in 7 — today it's implementation/runtimeOnly/api), ext {} version maps, and apply plugin: lines instead of a plugins {} block. Each is mechanical to modernise, and the deprecation warnings enumerate them for you.
