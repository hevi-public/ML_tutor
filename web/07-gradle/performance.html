Performance: the two caches

Gradle has two caches with confusingly similar names and completely different jobs. Knowing which one saves what is most of the performance conversation — the rest is turning them on and fixing what the problems report names.

At a glance
  • Configuration cache skips the configuration phase — the "Configure project" seconds before any task runs. Preferred mode in 9.x, default in Gradle 10 by plan.
  • Build cache skips task execution by reusing outputs (locally or from a remote node) when inputs match.
  • They compose: warm dev loop = configuration cache; CI across machines = remote build cache; both = the fast version of your build.
  • The blockers are plugins, not your code — and the HTML problems report says exactly which ones.

What it replaced

For this stack the plugins to watch are the jOOQ codegen plugin and anything Docker-adjacent — check their release notes for configuration-cache support before blaming Gradle.

Adopting the configuration cache without a bad week

# 1. Trial run — report problems, don't fail on them
./gradlew build --configuration-cache --configuration-cache-problems=warn

# 2. Read the report it prints (build/reports/configuration-cache/…)
#    Each problem names the plugin or script line at fault.

# 3. Fix/upgrade the named offenders, then make it the default:
#    gradle.properties → org.gradle.configuration-cache=true
Gotcha: environment reads poison the cache System.getenv("CI") at configuration time makes the cache entry depend on that value — different environment, cold configuration. Read environment state through providers.environmentVariable("CI") (lazily, at execution time) and the entry stays reusable. The same applies to file().exists() checks in scripts.
Older performance folklore

org.gradle.parallel=true (still valid, long since safe to enable), daemon tuning with giant heaps (rarely needed now), --offline as a speed hack (it isn't; dependency resolution is cached anyway). If a build is slow in 2026, the answer is almost always "the caches aren't on" or "one plugin defeats them" — a build scan will point at which.
