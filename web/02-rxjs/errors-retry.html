Errors & retry

One rule explains most error bugs in RxJS: an error kills the stream. Not the value — the stream.

At a glance
  • An error terminates the Observable. No further values, ever, from that subscription.
  • catchError must return a replacement Observable — whatever you return becomes the rest of the stream.
  • Where you place catchError decides whether the outer stream survives.
  • retry({ count, delay }) replaced retryWhen.

The placement rule

This is the single most useful thing on this page. Consider a search box whose requests sometimes fail:

// WRONG — one failed request kills the search box for good
this.term$.pipe(
  switchMap(t => this.api.search(t)),
  catchError(() => of([])),          // catches, but the outer stream is done
).subscribe(r => this.results.set(r));

// RIGHT — the error is contained inside the inner stream
this.term$.pipe(
  switchMap(t => this.api.search(t).pipe(
    catchError(() => of([])),        // only this request's error is handled
  )),
).subscribe(r => this.results.set(r));

In the first version the error propagates out of switchMap into the outer stream, which terminates it — term$ is dead, and typing produces nothing forever. In the second, the error never escapes the inner Observable, so the outer stream never sees it.

The rule, stated once Put catchError inside the flattening operator when the outer stream should survive. Put it at the end only when the whole pipeline finishing is genuinely acceptable — a one-shot load, for instance.

What changed

retryWhen's notifier was subtle in a way that produced silent failures: completing it stopped retrying and completed the result stream without an error, so a bug looked like success. The config object cannot express that mistake.

Retrying properly

// fixed delay, at most three attempts
source$.pipe(retry({ count: 3, delay: 1000 }))

// exponential backoff, and only for errors worth retrying
source$.pipe(
  retry({
    count: 4,
    delay: (error, retryCount) => {
      // a 4xx will not succeed on retry — rethrow immediately
      if (error.status >= 400 && error.status < 500) throw error;
      return timer(Math.min(1000 * 2 ** retryCount, 15000));
    },
  }),
)
Do not retry non-idempotent writes Retrying a POST that timed out can create the record twice — the request may have succeeded with only the response lost. Retry reads freely; retry writes only when the endpoint is idempotent or you are sending an idempotency key.

Where errors actually go

SituationWhat happens
Error, and the subscriber has an error callbackThat callback runs; the stream terminates
Error, and no error callbackIt is rethrown as an unhandled error — reaching Angular's ErrorHandler, not a try/catch around the subscribe
Throw inside a map or filterBecomes an error notification on the stream
Throw inside a subscribe next callbackNot catchable by catchError — it is downstream of the pipeline
Error inside a tap next handlerBecomes a stream error, same as map
try/catch does not work here Wrapping subscribe() in try/catch catches nothing: by the time values flow, the try block has long since exited. The error callback, or catchError, are the only handlers.

The toolkit

OperatorDoes
catchError(fn)Replaces the stream from the error onward with whatever you return
retry({count, delay})Resubscribes to the source on error
timeout(ms)Errors if no value arrives in time
finalize(fn)Runs on complete, error and unsubscribe — the right place to stop a spinner
throwError(() => e)An Observable that errors immediately. Note the factory
EMPTYCompletes without emitting — a common catchError return when there is nothing to show

catchError return values

// a fallback value
catchError(() => of([]))

// nothing at all — the stream completes quietly
catchError(() => EMPTY)

// handle, then rethrow for someone upstream
catchError(err => {
  this.log.error(err);
  return throwError(() => err);
})

// a different source entirely
catchError(() => this.api.searchFromCache(term))
Returning EMPTY hides failures It is the quickest way to make an error go away, and it makes the UI show "no results" for what was actually a server outage. Prefer surfacing an error state to the user; reserve EMPTY for cases where nothing genuinely is the correct outcome.
