Subscriptions & cleanup

The leak that made destroy$ ubiquitous, and the three modern ways not to have it.

In order of preference
  • Don't subscribe. toSignal() or the async pipe, and Angular manages the lifetime.
  • takeUntilDestroyed() when you genuinely need a subscription — no Subject, no lifecycle hook.
  • An operator that completes — take(1), first(), forkJoin — needs no cleanup at all.
  • Collecting into a Subscription and unsubscribing in ngOnDestroy still works; it is just more code.

What changed

Two details that matter in practice. Position: takeUntilDestroyed() should be the last operator before subscribe, so everything upstream is torn down. Context: called with no argument it needs an injection context — a field initialiser or constructor. Outside one, pass a DestroyRef explicitly: takeUntilDestroyed(this.destroyRef).

Which streams actually leak

Not all of them, and knowing which saves a lot of defensive code. A subscription is cleaned up automatically when the source completes.

SourceCompletes?Needs cleanup?
http.get()Yes, after one valueNo — though you may still want to cancel it
interval() / timer() repeatingNeverYes
fromEvent()NeverYes
A Subject you ownOnly if you complete itYes
route.paramMapNeverYes
form.valueChangesNeverYes
Anything with take(1) / first()YesNo
toSignal() / async pipe—No — Angular handles it
An HTTP subscription is not a leak, but it is a bug It completes, so nothing leaks. What can still go wrong is the callback running after the component is gone — setting a field on a destroyed component, or navigating based on a response the user no longer cares about. takeUntilDestroyed() cancels the request outright, which is usually what you want.

toSignal in practice

import { toSignal, toObservable } from '@angular/core/rxjs-interop';

export class SearchPage {
  term = signal('');

  // signal → observable → time-based operators → back to a signal
  results = toSignal(
    toObservable(this.term).pipe(
      debounceTime(300),
      distinctUntilChanged(),
      switchMap(t => t ? this.api.search(t) : of([])),
    ),
    { initialValue: [] },
  );
}

That round trip is the idiomatic 2026 shape: hold state in signals, drop into RxJS for the part that is genuinely about time, come back to a signal for the template.

OptionEffect
{ initialValue: x }The type is Signal<T> — no undefined

{ requireSync: true }Throws if the source does not emit synchronously. For a BehaviorSubject

The old pattern, for reference

Before v16 — destroy$, and the two ways it went wrong 
export class Widget implements OnInit, OnDestroy {
  private destroy$ = new Subject<void>();

  ngOnInit() {
    this.service.data$.pipe(takeUntil(this.destroy$)).subscribe(/* … */);
  }

  ngOnDestroy() {
    this.destroy$.next();
    this.destroy$.complete();
  }
}

Two failure modes, both common enough to be worth naming:

Forgetting complete(). Calling only next() stops the subscription but leaves the Subject itself alive.

Putting takeUntil in the wrong place. It must be last. Anything after it — a switchMap, a shareReplay — keeps its own subscription upstream, and that one is never torn down. This is subtle enough that lint rules exist purely to enforce operator order.

takeUntilDestroyed() removes both mistakes by removing the Subject.
