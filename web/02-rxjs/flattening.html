RxJS

Flattening

Four operators, one difference: what happens when a new value arrives while the previous one's work is still running.

The whole decision
  • switchMap — cancel the old one. Only the latest matters.
  • mergeMap — run them all at once. They are independent.
  • concatMap — queue them, strictly in order. Order matters.
  • exhaustMap — ignore the new one. Don't start again while busy.

Which one

You are doing…UseBecause
Type-ahead searchswitchMapResults for an abandoned query are worthless, and might arrive last
Loading data for the selected recordswitchMapSame — the previous record's data is no longer wanted
Saving a form on submitexhaustMapA double-click must not submit twice
"Load more" on a paginated listexhaustMapImpatient clicking should not request page 2 three times
Sending analytics eventsmergeMapIndependent, order-irrelevant, throw them all at the network
Uploading several selected filesmergeMapParallel is the point — cap it with the concurrency argument
A queue of edits to the same recordconcatMapReordered writes corrupt the record
Anything writing to a log or a streamconcatMapOrder is the contract
When in doubt, switchMap It is the right answer for the majority of UI cases and its failure mode — cancelling work you wanted — is loud and obvious. mergeMap's failure mode is a race condition that appears only under load, on someone else's slower connection. Reach for mergeMap deliberately, not by default.
Never switchMap a write switchMap cancels the in-flight request. On a POST or PATCH that means the browser aborts the connection — but the server may well have already processed it. You get a cancelled request, no confirmation, and a change that did happen. For writes use concatMap (ordered) or exhaustMap (ignore duplicates).

The shape

// type-ahead: cancel superseded searches
this.searchTerm$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(term => this.api.search(term)),
  takeUntilDestroyed(),
).subscribe(results => this.results.set(results));

// submit: ignore clicks while the save is in flight
this.submit$.pipe(
  exhaustMap(() => this.api.save(this.form().value())),
  takeUntilDestroyed(),
).subscribe();

// uploads: parallel, but no more than three at a time
from(files).pipe(
  mergeMap(file => this.api.upload(file), 3),
).subscribe();

// edits: strictly in order
this.edits$.pipe(
  concatMap(edit => this.api.patch(edit)),
).subscribe();

What changed

The nesting mistake

Every flattening operator exists to replace one anti-pattern: subscribing inside a subscribe. It is worth seeing plainly, because it is still the most common RxJS bug in real code.

// wrong — nothing cancels, nothing is ordered, and the inner
// subscription is never cleaned up
this.route.paramMap.subscribe(params => {
  this.api.load(params.get('id')).subscribe(user => {
    this.user.set(user);
  });
});

// right
this.route.paramMap.pipe(
  switchMap(params => this.api.load(params.get('id'))),
  takeUntilDestroyed(),
).subscribe(user => this.user.set(user));

The nested version has three defects at once: navigating quickly leaves requests racing, the inner subscription outlives the component, and the outer takeUntilDestroyed does not reach the inner one. The flattened version fixes all three because the inner stream is part of the chain.

The rest of the family

Each flattening operator has siblings that take the same strategy but produce something other than the inner values:

The …All forms flatten a stream that already emits Observables, rather than mapping to one. You will meet them rarely; when you do, the strategy names mean exactly the same thing.
