Creating streams

Where an Observable comes from, and the two Subject decisions that trip people up.

Creation functions

FunctionEmitsUse for
of(1, 2, 3)Each argument, then completesConstants, test fixtures, a synchronous default
from([1,2,3])Each item of an array, promise, iterable or another ObservableAdapting anything iterable or thenable
fromEvent(el, 'click')Every eventDOM events — hot, never completes
interval(1000)0, 1, 2… foreverPolling. Remember it never completes
timer(1000)0 after a delay; optionally repeatingDelays, and polling with an initial wait
defer(() => …)Whatever the factory returns, created per subscriberDeferring work that would otherwise run at pipe-construction time
EMPTYNothing, then completesA no-op branch inside switchMap
NEVERNothing, everTests, and "do not proceed"
throwError(() => err)An errorError paths. Note the factory — passing the error directly is deprecated
defer is the fix for "it ran too early" Anything you write inside a pipe() argument runs when the pipe is built, not when it is subscribed. of(Date.now()) captures the time once, at construction. defer(() => of(Date.now())) evaluates per subscription. Same trap as the removed switchMapTo.

Subjects

A Subject is both an Observable and an observer: you can next() values into it by hand. All four are hot. The only difference is what a late subscriber sees.

TypeA subscriber joining late getsTypical use
SubjectNothing — only future valuesEvents: "the user clicked save"
BehaviorSubjectThe current value immediately, then future onesState — though this is what signals replaced
ReplaySubject(n)The last n values, then future onesA short history: recent log lines, undo
AsyncSubjectOnly the final value, and only on completionRare. A one-shot result cached for later subscribers
If you are reaching for BehaviorSubject, reach for a signal "The current value, readable synchronously, that notifies on change" is the exact definition of a signal, and a signal does it without the async pipe, without a subscription, and without a separate read for .value. Keep BehaviorSubject for the case where you genuinely need the value as a stream to pipe time-based operators onto — and even then, consider toObservable() on a signal instead.

Making a cold stream hot

Each subscriber to a cold Observable triggers its own run. When that is wrong — two components both wanting the same HTTP response — you share it.

OperatorBehaviour
share()One shared run while at least one subscriber is active; restarts when it drops to zero
shareReplay({ bufferSize: 1, refCount: true })Shares and replays the last value to newcomers; tears down when everyone leaves
shareReplay(1)The same, but never tears down — see the gotcha
shareReplay(1) leaks by default Without refCount: true the underlying subscription is kept alive forever, even after every subscriber has gone. On an interval or a websocket that is a genuine leak that survives component destruction. Prefer the object form: shareReplay({ bufferSize: 1, refCount: true }).

Adapting other things

// a promise
from(fetch('/api/thing'))

// a signal — needs an injection context
toObservable(this.searchTerm)

// a callback API
new Observable<Position>(subscriber => {
  const id = navigator.geolocation.watchPosition(
    pos => subscriber.next(pos),
    err => subscriber.error(err),
  );
  // the return value is the teardown — this is what makes it cancellable
  return () => navigator.geolocation.clearWatch(id);
});

That teardown function is the part people forget. It runs on unsubscribe, on complete and on error, and returning it is what makes an Observable genuinely cancellable rather than merely ignorable.
