RxJS

Signals or RxJS?

The question this whole section exists to answer. The short version: signals for what is, RxJS for what happens over time.

The one-line test
  • Can you answer "what is the value right now?" — signal.
  • Does the question only make sense as a sequence of events over time — Observable.
  • Do you need to wait, cancel, retry, debounce or sequence — Observable.
  • Both, at different points in the same pipeline — that is normal, and the interop exists for it.

The canonical shape

Most real pipelines look like this — signals at both ends, RxJS in the middle for the part that is genuinely temporal:

export class SearchPage {
  // 1. state is a signal
  term = signal('');
  page = signal(1);

  // 2. drop into RxJS only for the time-based part
  private results$ = toObservable(this.term).pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap(term => term
      ? this.api.search(term).pipe(catchError(() => of([])))
      : of([])),
  );

  // 3. come back to a signal for everything else
  results = toSignal(this.results$, { initialValue: [] });

  // 4. derived state is a plain computed — no combineLatest
  hasResults = computed(() => this.results().length > 0);
  summary = computed(() =>
    `${this.results().length} results for "${this.term()}"`);
}
Do not convert back and forth repeatedly One toObservable → operators → one toSignal is a clean pipeline. Alternating several times in one chain usually means the RxJS part is doing something a computed would do better — conversion is not free, and each hop adds a subscription and a scheduling boundary.

What changed

What NOT to migrate

"Replace RxJS with signals" is a bad project. Specific things that are correct as they are:

  • HTTP calls. HttpClient returns Observables and that is fine. Wrap in httpResource when you want loading state; use firstValueFrom for one-shot commands.
  • Anything with a time operator in it. Signals have no debounceTime and are not going to.
  • Working combineLatest over genuine event sources. If the inputs are streams rather than state, it is already right.
  • Existing async pipes. They work. toSignal is nicer, not urgent.

The migration worth doing is narrower: BehaviorSubject fields that only ever hold "the current value", and combineLatest chains that are really just derived state. Those become signal and computed, and the code gets meaningfully shorter.
