Spring Boot

Testing

The 2026 shape: slices for the edges, one Testcontainers-backed @SpringBootTest for the flows that matter, real Postgres via @ServiceConnection, and the new one-client-everywhere RestTestClient. Boot 4 moved the furniture (JUnit 6, Testcontainers 2, @MockBean gone) — this page is where things stand.

At a glance
  • Boot 4 manages JUnit 6 — for typical suites the rename that matters is none: @Test is still @Test. Custom extensions and version-pinned tooling are where to look.
  • Testcontainers is on the 2.x line — and tests against a real postgres:18 beat any H2 approximation, especially with jOOQ codegen in the loop.
  • @MockBean no longer exists (removed 4.0) — it's @MockitoBean now, with slightly different rules.
  • Test slices went modular with the starters: spring-boot-starter-webmvc-test, -jooq-test, etc.

Do it this way now

// The one integration test that earns its runtime
@Testcontainers
@SpringBootTest(webEnvironment = RANDOM_PORT)
class OrderFlowTest {

    companion object {
        @Container @ServiceConnection
        val pg = PostgreSQLContainer("postgres:18")   // migrations run against it
    }

    @Autowired lateinit var client: RestTestClient    // Boot 4 autowires it

    @Test
    fun `placing an order persists and returns it`() {
        client.post().uri("/orders")
            .body(PlaceOrderJson.valid())
            .exchange()
            .expectStatus().isCreated
            .expectBody(OrderResponse::class.java)
            .value { assertThat(it.status).isEqualTo("PLACED") }
    }
}

What it replaced

MockK or Mockito?

Boot's integration annotations (@MockitoBean) are Mockito-specific. In pure unit tests — no Spring context — MockK is the more Kotlin-native choice: coroutine support (coEvery), final classes without plugins, verification DSL. A workable team rule: MockK in plain unit tests, @MockitoBean where a Spring slice needs a mocked collaborator, and no mocking at all in the Testcontainers flow tests — that's what the real database is for.

Gotcha: container-per-test-class is a tax you configure away A static (companion-object) @Container is shared across a class; sharing across the suite needs singleton containers or Boot's @ServiceConnection with a @TestConfiguration you import everywhere. If the suite got slow after adopting Testcontainers, it's almost always one fresh Postgres per class — reuse it, and put migrations in a @BeforeAll, not per-test.
Reading older test suites

@MockBean/@SpyBean (Boot ≤3.x), @DynamicPropertySource blocks copying container URLs, MockMvc's perform(get(…)).andExpect(…) hamcrest chains (still supported; MockMvcTester and RestTestClient are the modern faces), JUnit 4 @RunWith(SpringRunner::class) in the truly old layers. Each has a mechanical modern form; none needs a big-bang rewrite.
