Data access & transactions

This stack's data layer is jOOQ over JDBC — no JPA. Spring's jobs here are the DataSource, the transaction boundary, and exception translation. Most production incidents in this area are one of the @Transactional gotchas below, none of which changed in years — which is exactly why they're written down.

At a glance
  • spring-boot-starter-jooq wires everything: the Boot-managed DSLContext joins Spring transactions automatically — @Transactional and dsl.transaction { } compose.
  • @Transactional works through proxies — which is the root of every classic surprise: self-invocation, non-public methods, and final classes (Kotlin: the allopen plugin's spring preset handles that).
  • Isolation defaults to the database's — for Postgres that's READ COMMITTED. What each level actually permits is demonstrable, not theoretical.
  • Virtual threads changed the calculus: blocking on JDBC in a transaction is fine — that's the model. Don't suspend inside a blocking transaction.

Do it this way now

@Service
class OrderService(private val dsl: DSLContext) {

    // The service method is the transaction boundary — not the repository.
    @Transactional
    fun place(cmd: PlaceOrder): OrderId {
        val id = dsl.insertInto(ORDERS)
            .set(ORDERS.CUSTOMER_ID, cmd.customer.value)
            .set(ORDERS.STATUS, OrderStatus.PLACED.name)
            .returningResult(ORDERS.ID)
            .fetchSingle().value1()

        dsl.insertInto(OUTBOX)      // same tx: atomic with the order
            .set(OUTBOX.PAYLOAD, cmd.toEventJson())
            .execute()

        return OrderId(id)
    }

    @Transactional(readOnly = true)   // hints the driver + guards intent
    fun find(id: OrderId): Order? =
        dsl.selectFrom(ORDERS).where(ORDERS.ID.eq(id.value)).fetchOne()?.toOrder()
}

What it replaced

In a jOOQ codebase JdbcClient is the odd-jobs tool — the health-check query, the migration backfill script — anywhere codegen types would be ceremony.

The @Transactional gotchas, in one table

SymptomCauseFix
Annotation silently ignored Self-invocation: this.otherMethod() never crosses the proxy Move the boundary to the caller, or inject the bean into itself sparingly
Annotation silently ignored (2) Non-public method, or final class/method without the Kotlin allopen spring preset Public methods on open beans; check the plugin is applied
Data committed despite an exception The exception was caught inside the method — the interceptor never saw it Rethrow, or mark rollback explicitly via TransactionStatus
"Connection is closed" under load Long work (HTTP calls!) inside the transaction holding a pool connection Do I/O outside the boundary; keep transactions to DB work
Deadlocks or 40001 under REPEATABLE READ+ Concurrent writers — expected behaviour, not a bug Retry the transaction; see the isolation demo
Kotlin note All Kotlin exceptions are unchecked — the "checked exceptions don't roll back" rule can't bite …so rollbackFor cargo-cult is unnecessary here
Gotcha: two transaction APIs, one transaction dsl.transaction { } (jOOQ) and @Transactional (Spring) both work — and with the Boot starter they participate in the same Spring-managed transaction, so mixing them nests instead of colliding. Pick one as the team idiom (this reference uses Spring's at service level) and let the other appear only where it reads better.
Reading JPA-era services

If a service you inherit is Hibernate-based: @Entity graphs, lazy loading (and its N+1s), dirty checking and flush timing are a different programming model, not a worse one — but its gotchas (LazyInitializationException, accidental cascades) are exactly the class of implicit behaviour this stack chose jOOQ to avoid.
