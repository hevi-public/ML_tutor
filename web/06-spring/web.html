Controllers & the three web clients

The server side has been stable for years — annotated controllers returning value types. The client side is where three generations coexist in real codebases, and where Framework 7 finally settled the question.

At a glance
  • Server: @RestController + Kotlin data classes. Nothing controversial; validation at the boundary with jakarta.validation.
  • Client, blocking code: RestClient. RestTemplate is docs-deprecated in 7.x; WebClient is for reactive stacks.
  • Client, more than a couple of endpoints: @HttpExchange interfaces, registered as a group with @ImportHttpServices (Framework 7).
  • API versioning is now the framework's job — the mapping declares its version; configuration decides how clients say which one they want.

Do it this way now

@RestController
@RequestMapping("/orders")
class OrderController(private val orders: OrderService) {

    @GetMapping("/{id}")
    fun find(@PathVariable id: OrderId): OrderResponse =
        orders.find(id) ?: throw OrderNotFound(id)

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    fun create(@Valid @RequestBody req: CreateOrder): OrderResponse =
        orders.create(req)
}

// Errors: one @RestControllerAdvice producing ProblemDetail (RFC 9457),
// not per-controller try/catch.

What it replaced

The decision table, compressed: blocking service → RestClient · reactive service → WebClient · several endpoints on one remote API → an @HttpExchange interface (next card), which runs on either client underneath.

Gotcha: WebClient still drags in reactor Adding WebClient to an MVC service pulls the reactive stack onto the classpath for one client — and with virtual threads enabled, buys nothing. The reverse trap: Spring MVC accepts Kotlin suspend handlers (via async dispatch), but the blocking-with-virtual-threads model is simpler unless the handler genuinely orchestrates concurrent work.
RestTemplate-era clients — for reading old code

restTemplate.exchange(url, HttpMethod.GET, entity, typeRef) with hand-built HttpHeaders, per-service *Client classes holding a RestTemplate, and getForObject null-handling by convention. Maintenance mode since Framework 5 (2017); Framework 7's docs mark it deprecated with the annotation to follow in 7.1. Translate to RestClient mechanically when you touch one.
