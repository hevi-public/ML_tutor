Spring Boot

Security 6 → 7

Security's decade-long migration finished: configuration is beans, the DSL is lambdas, and there is exactly one way to write it. If your config compiles unchanged on Security 7, you were already writing it the modern way.

At a glance
  • One idiom: SecurityFilterChain beans + lambda DSL. Security 7 (with Boot 4) removed and() and authorizeRequests() — the old chained style no longer compiles.
  • Method security is @EnableMethodSecurity + @PreAuthorize; the old @EnableGlobalMethodSecurity is a Boot-2-era marker.
  • Passkeys and one-time tokens are built in since Security 6.4 (Boot 3.4) — passwordless stopped being a custom filter project.
  • For a token-secured API the whole config is ~15 lines: resource server + JWT + route rules (below).

Do it this way now

@Configuration
@EnableWebSecurity
@EnableMethodSecurity          // @PreAuthorize on service methods
class SecurityConfig {

    @Bean
    fun api(http: HttpSecurity): SecurityFilterChain {
        http {
            authorizeHttpRequests {
                authorize("/actuator/health", permitAll)
                authorize("/api/admin/**", hasRole("ADMIN"))
                authorize(anyRequest, authenticated)
            }
            oauth2ResourceServer { jwt { } }     // spring.security.oauth2.resourceserver.jwt.*
            sessionManagement { sessionCreationPolicy = STATELESS }
            csrf { disable() }                    // token API: no cookies, no CSRF surface
        }
        return http.build()
    }
}

What it replaced

Gotcha: the filter chain matcher trap With multiple SecurityFilterChain beans, the first chain whose securityMatcher fits the request wins — entirely. A broad chain declared before a narrow one silently swallows the narrow one's routes, and everything looks configured while the wrong rules run. Order chains most-specific first (@Order), and give every chain an explicit securityMatcher.
Reading Boot 2-era security

WebSecurityConfigurerAdapter subclasses, antMatchers() (renamed requestMatchers() in 5.8), @EnableGlobalMethodSecurity(prePostEnabled = true), and .and() chains. The migration is mechanical and one-directional: each configure(…) override becomes a bean, each chained clause becomes a lambda block — the migration guide chip below has the table.
