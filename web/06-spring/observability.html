Spring Boot

Observability

The Boot 3 rebuild put one abstraction (Micrometer's Observation) under metrics and traces, and Boot 4 finished the OpenTelemetry story. What used to be three integration projects is now: add the starter, set the endpoint, instrument the interesting paths.

At a glance
  • HTTP server/client, JDBC and friends are auto-observed — custom Observations are for your domain operations, not for re-instrumenting the framework.
  • OTLP export = one starter (spring-boot-starter-opentelemetry, Boot 4.0) — and since 4.1 the standard OTEL_* environment variables just work.
  • Structured logs are a property (logging.structured.format.*, Boot 3.4): ECS, Logstash or GELF shape with correlation ids included.
  • Actuator hygiene: expose health (and prometheus if you scrape) — not *. The info endpoint gained process/uptime details in 4.1.

Do it this way now

# application.yaml — the 2026 baseline
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
  opentelemetry:
    resource-attributes:
      service.name: order-service
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
  tracing:
    sampling:
      probability: 0.1

logging:
  structured:
    format:
      console: ecs

What it replaced

Gotcha: cardinality is still your problem The Observation API makes tagging easy — including tagging wrongly. lowCardinalityKeyValue values become metric label sets; put a user id or order id there and the metrics backend melts. The rule: enumerable values (status, channel, tenant tier) are low-cardinality tags; identifiers belong on the span (highCardinalityKeyValue) or in the log line.
Reading Boot 2-era observability

Spring Cloud Sleuth for tracing (absorbed into Micrometer Tracing in Boot 3), micrometer-registry-prometheus plus a zoo of exporter-specific config, and log JSON via hand-rolled encoders. The concepts map one-to-one; only the wiring shrank.
