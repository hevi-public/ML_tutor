TestBed in 2026

Standalone components made the setup shorter, signals made assertions simpler, and zoneless made fakeAsync stop working.

At a glance
  • imports: for standalone components, not declarations:.
  • fixture.componentRef.setInput() to set signal inputs.
  • await fixture.whenStable() instead of fakeAsync/tick under zoneless.
  • provideHttpClientTesting() for HTTP — HttpClientTestingModule is the old form.
  • A service with no template dependencies does not need the TestBed at all.

Do it this way now

import { TestBed } from '@angular/core/testing';
import { provideZonelessChangeDetection } from '@angular/core';
import { describe, it, expect, beforeEach } from 'vitest';

describe('UserCard', () => {
  beforeEach(() => {
    TestBed.configureTestingModule({
      imports: [UserCard],                       // standalone: import it
      providers: [
        provideZonelessChangeDetection(),
        { provide: UserService, useValue: { load: vi.fn() } },
      ],
    });
  });

  it('shows the name', async () => {
    const fixture = TestBed.createComponent(UserCard);

    // signal inputs are set through componentRef
    fixture.componentRef.setInput('user', { name: 'Ada', isAdmin: true });

    await fixture.whenStable();

    expect(fixture.nativeElement.textContent).toContain('Ada');
  });
});

Testing without the TestBed

Worth stating plainly, because it is faster and most codebases under-use it: a service or a component whose logic is signals and plain methods can be tested by constructing it. The TestBed exists to give you templates and DI — if a test needs neither, skip it.

it('totals the cart', () => {
  const cart = new Cart();
  cart.add({ price: 3 });
  cart.add({ price: 4 });
  expect(cart.total()).toBe(7);
});

// with dependencies, use runInInjectionContext or just pass fakes in
it('loads a user', async () => {
  const http = { get: vi.fn().mockReturnValue(of({ name: 'Ada' })) };
  const store = TestBed.runInInjectionContext(() => new UserStore());
  // …
});

Signals in tests

Signals make assertions synchronous — a computed is correct the moment you read it, with no change detection required. Change detection is only needed for the DOM.

Asserting onDo
A signal or computed's valueRead it: expect(cmp.total()).toBe(7). No fixture needed
Rendered DOMawait fixture.whenStable() first
An input's effectfixture.componentRef.setInput(…), then whenStable()
An effect() having runawait fixture.whenStable() — effects are scheduled, not immediate
An outputSubscribe to it: cmp.saved.subscribe(spy)
Gotcha: setting an input directly does not work fixture.componentInstance.user = x fails for a signal input — it is read-only, and assigning replaces the signal rather than setting its value. Use fixture.componentRef.setInput('user', x), which is also what the template binding does.

HTTP

TestBed.configureTestingModule({
  providers: [
    provideZonelessChangeDetection(),
    provideHttpClient(),
    provideHttpClientTesting(),
  ],
});

it('requests the user', async () => {
  const http = TestBed.inject(HttpTestingController);
  const store = TestBed.inject(UserStore);

  const promise = firstValueFrom(store.load('1'));
  http.expectOne('/api/users/1').flush({ name: 'Ada' });

  expect(await promise).toEqual({ name: 'Ada' });
  http.verify();       // fails if any request went unhandled
});
Order matters provideHttpClient() must come before provideHttpClientTesting() — the testing provider replaces the real backend, so it has to be applied on top. The reverse order silently makes real requests.

Component harnesses

A harness gives a component a stable API for tests, so an internal markup change does not break every spec that touched it. Angular Material and @angular/aria ship them; you can write your own on @angular/cdk/testing.

const loader = TestbedHarnessEnvironment.loader(fixture);
const tabs = await loader.getHarness(TabGroupHarness);
await tabs.selectTab('Billing');
expect(await tabs.getSelectedLabel()).toBe('Billing');

The argument for them is narrow but real: any test that does querySelector('.tab-button:nth-child(2)') is asserting on markup it does not own, and will break the next time someone adds a wrapper element.

NO_ERRORS_SCHEMA deserves a warning: it silences every unknown element and attribute, including your typos. It was widely used to avoid declaring child components, and it hid real bugs. With standalone components you import what the template uses, and the compiler tells you when something is missing.
