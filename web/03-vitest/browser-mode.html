Vitest

Browser mode

Run the same tests in a real browser instead of jsdom. Out of experimental in Vitest 4, and the answer whenever a test fails because jsdom does not implement something.

At a glance
  • Stable in Vitest 4 — the experimental tag is gone.
  • Providers moved into separate packages: @vitest/browser-playwright, @vitest/browser-webdriverio, @vitest/browser-preview.
  • In an Angular project, set browsers on the builder — you do not usually configure Vitest directly.
  • It is not end-to-end testing. It is component testing with a real layout engine.

When it earns its cost

Browser mode starts slower and is more machinery. Use it for the specific cases where jsdom gives a wrong answer rather than no answer — those are the ones that waste an afternoon:

SymptomCause
getBoundingClientRect() returns all zerosjsdom has no layout engine at all
offsetWidth / offsetHeight are 0Same
A component that measures itself renders wronglySame
IntersectionObserver never firesRequires real scrolling and layout
Canvas or WebGL code throwsNot implemented
CSS-dependent behaviour is not exercisedjsdom parses CSS but does not apply it visually
Scroll position assertions failNo real viewport

Everything else — services, pipes, signal logic, most component tests — belongs in jsdom, where it runs faster.

Setting it up

npm install -D @vitest/browser-playwright playwright
// angular.json
"test": {
  "builder": "@angular/build:unit-test",
  "options": {
    "buildTarget": "::development",
    "browsers": ["chromium"],
    "headless": true
  }
}

Angular also ships an internal schematic used by ng add to wire a browser provider into a project, so adding the provider package is usually enough.

Gotcha: the provider package is separate now In Vitest 3 you named the provider as a string and it came bundled. In Vitest 4 the provider lives in its own package that you must install — naming it without installing gives a resolution error that reads like a config mistake rather than a missing dependency.

Splitting the suite

Most projects want both: fast jsdom tests for the bulk and browser tests for the handful that need real layout. Keep them separate so the fast set stays fast — a naming convention plus include filters, or Vitest projects if you are running Vitest directly.

// two targets in angular.json
"test": {
  "builder": "@angular/build:unit-test",
  "options": { "buildTarget": "::development", "exclude": ["**/*.browser.spec.ts"] }
},
"test-browser": {
  "builder": "@angular/build:unit-test",
  "options": {
    "buildTarget": "::development",
    "include": ["**/*.browser.spec.ts"],
    "browsers": ["chromium"]
  }
}

What changed

Not a replacement for e2e

Browser mode mounts components in a real browser. It does not navigate your application, run against a real backend, or exercise a user journey across pages. If you need that, Playwright or Cypress are still the tools — and the fact that browser mode uses Playwright underneath does not make it the same thing.

jsdomBrowser modePlaywright e2e
ScopeOne component or serviceOne componentThe whole application
Real layoutNoYesYes
Real backendNoUsually mockedTypically yes
SpeedMillisecondsFast per test, slow to startSlow
Use forThe bulk of your testsLayout-dependent componentsCritical user journeys
