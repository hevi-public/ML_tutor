Async testing & marbles

Zoneless removed fakeAsync from the toolbox. Here is what replaces it, and how to test a stream without waiting in real time.

At a glance
  • fakeAsync / tick are zone-based and do not work in a zoneless application.
  • For Angular's own async work: await fixture.whenStable().
  • For timers you control: vi.useFakeTimers() and vi.advanceTimersByTime().
  • For stream timing precisely: RxJS's TestScheduler with marble syntax.
  • Never await new Promise(r => setTimeout(r, 500)) in a test.

The decision

whenStable

it('updates when the input changes', async () => {
  const fixture = TestBed.createComponent(UserCard);
  fixture.componentRef.setInput('user', { name: 'Ada' });

  await fixture.whenStable();

  expect(fixture.nativeElement.textContent).toContain('Ada');
});

whenStable() resolves once Angular has finished the work it knows about — pending change detection, effects, and resolved promises it is tracking. It does not wait for a setTimeout you wrote; that is what fake timers are for.

Fake timers

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

it('debounces the search', async () => {
  const spy = vi.fn();
  service.search$.subscribe(spy);

  service.term.set('a');
  service.term.set('ab');
  service.term.set('abc');

  expect(spy).not.toHaveBeenCalled();      // still inside the debounce window

  await vi.advanceTimersByTimeAsync(300);

  expect(spy).toHaveBeenCalledTimes(1);
  expect(spy).toHaveBeenCalledWith('abc');
});
Use the Async variants when promises are involved advanceTimersByTime() is synchronous: it fires the timers but does not let queued promise callbacks run, so a chain of awaits stays stuck. advanceTimersByTimeAsync() flushes the microtask queue between timers, which is almost always what an RxJS pipeline needs.
Always restore Fake timers are global. Forgetting vi.useRealTimers() in afterEach leaks them into every following test in the file, and the failures appear somewhere unrelated.

Marble tests

When the assertion is genuinely about when things emit — the whole point of an operator like debounceTime or switchMap — marble syntax states it directly and runs in virtual time, so a five-second test finishes instantly.

import { TestScheduler } from 'rxjs/testing';

let scheduler: TestScheduler;

beforeEach(() => {
  scheduler = new TestScheduler((actual, expected) => {
    expect(actual).toEqual(expected);
  });
});

it('debounces', () => {
  scheduler.run(({ cold, expectObservable }) => {
    const source = cold('a-b-c------d|');
    const expected =    '-----------(c|)---d|';

    expectObservable(source.pipe(debounceTime(5, scheduler)))
      .toBe(expected);
  });
});
SymbolMeans
-One frame of virtual time passing
a, b…A value emitted
|Completion
#An error
()Several events in the same frame
^Subscription point (hot observables only)
cold(…)Starts when subscribed
hot(…)Runs regardless of subscription
Inside scheduler.run, time is virtual Operators pick up the test scheduler automatically inside run(), so debounceTime(300) means 300 virtual frames, not 300 milliseconds. Mixing in real timers or vi.useFakeTimers() inside the same block produces confusing results — pick one mechanism per test.

Marble tests are precise and worth it for operator-level logic. For most component tests they are more machinery than the assertion deserves — a fake timer and a spy say the same thing more plainly.

Never sleep in a test await new Promise(r => setTimeout(r, 500)) makes the suite slower and still flaky — it either waits too long or, on a loaded CI machine, not long enough. Every case above has a deterministic alternative.
