Vitest

Vitest setup

Angular drives Vitest through its own builder rather than the Vitest CLI, which changes where configuration lives — and is the first thing that confuses people arriving from a non-Angular project.

At a glance
  • One builder for both runners: @angular/build:unit-test, with runner: "vitest" (the default) or "karma".
  • No vitest.config.ts by default. The builder generates the Vite config from your build target.
  • Tests run in Node with jsdom unless you set browsers.
  • providersFile supplies Angular providers to every test; setupFiles runs global setup. The TestBed is initialised for you either way.

Do it this way now

// angular.json
"test": {
  "builder": "@angular/build:unit-test",
  "options": {
    "buildTarget": "::development",
    "tsConfig": "tsconfig.spec.json",
    "providersFile": "src/test-providers.ts",
    "setupFiles": ["src/test-setup.ts"],
    "coverage": true,
    "coverageThresholds": { "statements": 80 }
  }
}
// src/test-providers.ts — a default export of providers for every test
import { provideZonelessChangeDetection } from '@angular/core';
import { provideHttpClient } from '@angular/common/http';
import { provideHttpClientTesting } from '@angular/common/http/testing';

export default [
  provideZonelessChangeDetection(),
  provideHttpClient(),
  provideHttpClientTesting(),
];

Then ng test. There is no vitest command to run and no config file to write for the common case — which is the point of the builder, and also the thing to know before you go looking for one.

What changed

Worth separating two things that get conflated: switching the runner is a one-line edit to angular.json, and it does not touch your specs. Converting Jasmine assertions to Vitest ones is the separate, larger job — see migrating.

Builder options

The options that matter, from the builder's own schema:

OptionDoes
buildTargetWhich build configuration the tests compile against — this is how the test build inherits your aliases, paths and defines
runner"vitest" (default) or "karma"
runnerConfigA path to a runner config file, or true to auto-detect one. Default false — no config file at all
providersFileA TypeScript file whose default export is an array of Angular providers applied to every test
setupFilesGlobal setup run before test files. Polyfills and the TestBed are initialised regardless
browsersRun in real browsers instead of jsdom. See browser mode
include / exclude / filterWhich spec files to run
coverage, coverageThresholds, coverageReportersCoverage, without needing a config file
watch, ui, debug, headlessHow it runs locally
Gotcha: reaching for vitest.config.ts too early Most Vitest documentation and every blog post assumes you own the config file. In an Angular project you usually do not, and adding one without setting runnerConfig means it is silently ignored — you edit settings and nothing changes. Use the builder options first; add a config file only for genuinely Vitest-specific features, and point runnerConfig at it.

jsdom or a real browser

jsdom (default)Browser mode
SpeedFastSlower to start
Layout & sizingNot implemented — every element measures zeroReal
Canvas, WebGL, mediaAbsent or stubbedReal
CSSParsed, not applied visuallyReal
Good forLogic, services, most component testsAnything measuring, drawing, or depending on real layout

jsdom is the right default. Reach for browser mode when a test fails for a reason that is really "jsdom does not implement this" — most often getBoundingClientRect returning zeros, or anything involving scroll position or intersection observers.

Keeping Karma for now

The same builder runs Karma, so migrating the builder and migrating the runner are separate steps:

"test": {
  "builder": "@angular/build:unit-test",
  "options": {
    "buildTarget": "::development",
    "runner": "karma",
    "runnerConfig": "karma.conf.js"
  }
}

Useful as an intermediate state: you get onto the supported builder immediately, then convert specs at your own pace. Karma is deprecated and receives no new features, so this is a staging post rather than a destination.
