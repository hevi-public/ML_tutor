Vitest

Migrating from Karma & Jasmine

Two separate jobs that get conflated: switching the runner (one line) and converting the assertions (a schematic, plus the cases it cannot do).

The order to do it in
  • 1. Move to @angular/build:unit-test with runner: "karma". Nothing else changes; everything still passes.
  • 2. Run ng generate @schematics/angular:refactor-jasmine-vitest to convert assertions and spies.
  • 3. Switch runner to "vitest" (or drop the option — it is the default).
  • 4. Fix what is left by hand: done callbacks, clock control, and anything zone-dependent.
The schematic is marked experimental refactor-jasmine-vitest is labelled EXPERIMENTAL in the package. Run it on a clean tree, use --report to see what it intends to touch, and read the diff — it does the mechanical bulk well and leaves the interesting cases alone.

The three that need a person

1. spyOn no longer stubs by default In Jasmine, spyOn(obj, 'method') replaces the method — it records calls and returns undefined. In Vitest, vi.spyOn(obj, 'method') records calls and still calls the real implementation. A test that relied on the original not running will now run it, which can mean real HTTP, real navigation, or a thrown error from a method that was never meant to execute. Add .mockImplementation(() => {}) where the stubbing was the point.
2. done callbacks are gone Vitest 4 removed the done parameter. Return a promise instead — which is usually clearer anyway, since a forgotten done() was a timeout rather than a failure. 
// was
it('loads', (done) => {
  service.load().subscribe(v => { expect(v).toBe(1); done(); });
});

// now
it('loads', async () => {
  const v = await firstValueFrom(service.load());
  expect(v).toBe(1);
});
3. fakeAsync and tick are zone-based They come from @angular/core/testing and depend on zone.js. In a zoneless application they do not work. Replace with await fixture.whenStable(), or Vitest's own fake timers for genuine timer control. See async testing.

Globals

Jasmine's describe, it and expect are globals. Vitest can provide globals too, but the Angular builder's default expects explicit imports:

import { describe, it, expect, beforeEach, vi } from 'vitest';

Explicit imports are worth keeping: they give you go-to-definition, they make it obvious which framework a spec uses during a partial migration, and they avoid the ambient type conflicts that arise when Jasmine and Vitest type definitions are both installed.

Remove the Jasmine types when you are done Leaving "types": ["jasmine"] in tsconfig.spec.json alongside Vitest produces conflicting global declarations for expect, and the resulting type errors point nowhere useful. Drop the Jasmine entry once the last spec is converted.
