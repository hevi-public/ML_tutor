Change detection & zoneless

The most-misunderstood part of Angular, and the one where the last three versions changed the answer.

At a glance
  • Zoneless is the default for new applications from v21. provideZonelessChangeDetection() has been stable (without the Experimental prefix) since v20.2.
  • OnPush is the default strategy from v22 — you no longer write changeDetection: at all.
  • Under zoneless, mutating a plain field updates nothing. That is the single thing that breaks during migration.
  • markForCheck() and detectChanges() still exist, and needing them is a signal that some state should be a signal.

Try it

Same tree, same event, three strategies. Watch how many components Angular visits — and pick "Zoneless" with a setTimeout to see the failure mode that catches everyone.

What changed

Note the two-step timeline: the API stabilised in v20.2, but v21 made it the default for new applications. An existing application upgraded to v21 or v22 keeps zone.js until you remove it — nothing is taken away from you on upgrade.

How each strategy decides

What schedules a passWhat gets checked
zone.js + Default Any patched async API: events, timers, XHR, promises Every component, every time
zone.js + OnPush Same Components marked dirty — an event in the component, a changed input reference, an async pipe emission, a signal read in the template — plus their ancestors
Zoneless A signal write, an async pipe emission, markForCheck(), or a template event handler Only the views that read the changed signal

Migrating to zoneless

The work is not the provider — it is finding the places that relied on zone.js noticing something. In rough order of how often they bite:

1. State mutated outside signals A field set in a setTimeout, a websocket callback, a third-party library's callback, or a promise .then(). Under zone.js all four triggered a pass. Under zoneless none of them do. Make the state a signal and the problem disappears at the source.
2. Array and object mutation this.items().push(x) does not change the array's identity, so the signal's equality check says nothing happened. This is the same bug as on the signals page and it accounts for a surprising share of "zoneless broke my app" reports. Replace the reference: items.update(list => [...list, x]).
3. Tests that relied on the zone fakeAsync and tick() are zone-based. In a zoneless test you await fixture.whenStable() instead. See TestBed in 2026.

A pragmatic order: turn on OnPush everywhere first (v22 does this for you), fix whatever breaks, then move state to signals, and only then remove zone.js. Each step is independently shippable.

// 1. the provider
bootstrapApplication(App, {
  providers: [provideZonelessChangeDetection()],
});

// 2. remove zone.js from the polyfills in angular.json,
//    and from package.json dependencies

// 3. any state that used to rely on the zone becomes a signal
export class Ticker {
  elapsed = signal(0);          // was: elapsed = 0;

  constructor() {
    setInterval(() => this.elapsed.update(n => n + 1), 1000);
  }
}

markForCheck and detectChanges

Both still exist and both still work. The distinction, since it is routinely confused:

CallDoesUse when
markForCheck() Marks this component and its ancestors dirty for the next pass Something outside Angular's knowledge changed state. Rare once state is signals.
detectChanges() Runs a pass over this component now, synchronously Almost never in application code. Mostly in tests.
ApplicationRef.tick() Runs a pass over the whole application now Effectively never.
Before v18 — the zone.js model, and why it existed

zone.js patched setTimeout, setInterval, addEventListener, Promise, XMLHttpRequest and more, so that Angular got a callback whenever any of them completed. Its guess was: something asynchronous finished, therefore state may have changed, therefore re-check everything.

The guess was almost always wrong in detail and right in aggregate, which is what made it usable — you never had to tell Angular anything. The costs were the bundle size, a globally patched environment that confused debuggers, profilers and third-party libraries, and a full tree check after events that changed nothing at all.

ChangeDetectionStrategy.OnPush was the escape hatch, and the reason so much older code is littered with markForCheck(): with OnPush and non-signal state, you had to tell Angular manually whenever anything changed.
