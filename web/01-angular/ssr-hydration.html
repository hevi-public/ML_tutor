SSR & hydration

Render on the server, then take over on the client without throwing the server's work away — and, since v22, without downloading the JavaScript for parts of the page nobody has looked at.

At a glance
  • provideClientHydration() is the whole setup. Incremental hydration is on by default from v22.
  • withEventReplay() records clicks that happen before hydration and replays them afterwards.
  • Incremental hydration reuses @defer triggers — the same syntax now decides when this becomes interactive, not just when it loads.
  • The usual breakage is code that touches window or document during construction.

Do it this way now

bootstrapApplication(App, {
  providers: [
    provideClientHydration(withEventReplay()),
    provideRouter(routes),
  ],
});
<!-- Server-rendered immediately, but its JavaScript is not downloaded
     until the user scrolls to it. -->
@defer (hydrate on viewport) {
  <comment-thread [postId]="postId()" />
}

<!-- Rendered and hydrated only on interaction. -->
@defer (hydrate on interaction) {
  <rich-text-editor />
}

<!-- Never hydrated: static server output, zero client cost. -->
@defer (hydrate never) {
  <marketing-footer />
}

What changed

If you adopted incremental hydration early, this is a deletion rather than a migration: remove withIncrementalHydration() and the behaviour stays the same. The schematic does it for you.

Hydration, in one paragraph

The server renders your components to HTML and sends it. The browser paints it — fast, and without any application JavaScript. Then Angular boots and needs to take ownership of that DOM. Without hydration it discards everything the server produced and re-renders from scratch, which causes a visible flicker and wastes the server's work. With hydration it walks the existing DOM, matches it against what it would have rendered, and attaches event listeners and reactive state in place.

Incremental hydration extends that: rather than hydrating the whole page at once, blocks marked @defer (hydrate …) wait for their trigger. A page can be fully rendered and readable while most of its JavaScript has never been fetched.

Event replay

Between paint and hydration the page looks ready but is not listening. A user who clicks in that window gets nothing. withEventReplay() records those events and dispatches them once the relevant component is hydrated, which matters far more on a slow connection than on your laptop.

What breaks

ProblemWhyFix
window is not definedNode has no DOM Move it to afterNextRender(), which never runs on the server
Hydration mismatch (NG0500 family)The client rendered different DOM than the server Usually random values, dates or Math.random() in a template — make them deterministic or pass them from the server
Direct DOM manipulationHydration expects the DOM it rendered Do it in afterNextRender, or mark the subtree ngSkipHydration
Data fetched twiceServer fetches, then the client fetches again Angular's HttpClient transfers responses automatically; check the interceptor chain if it is not happening
Invalid HTML nestingThe browser silently repairs it, so the DOM no longer matches Fix the markup — a <div> inside a <p> is the classic
ngSkipHydration is a last resort It tells Angular to destroy and re-render that subtree, which is the pre-hydration behaviour for that part of the page. Useful as an escape hatch for a third-party widget that insists on owning its DOM; not a fix for a mismatch you could resolve properly.
Gotcha: hydrate never still renders The block is server-rendered and appears in the HTML — it simply never becomes interactive and its JavaScript is never fetched. Excellent for a static footer; wrong for anything with a click handler, which will silently do nothing.

Deciding what to defer

Roughly: anything the user has not scrolled to, anything behind an interaction, and anything genuinely static. Be careful with content near the top of the page — deferring something the user sees immediately trades a smaller bundle for a visible pop-in, which is usually a bad trade.

ContentTrigger
Comments, related items, anything below the foldhydrate on viewport
Editors, date pickers, complex inputshydrate on interaction
Menus and popovershydrate on hover
Static footers, legal text, marketing copyhydrate never
Above-the-fold interactive contentDo not defer it
