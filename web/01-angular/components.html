Angular

Components

What a component looks like in v22, and everything that has been stripped out of it since v14.

At a glance
  • No standalone: true — it is the default since v19.
  • No changeDetection — OnPush is the default since v22.
  • Dependencies come from imports on the component, not a module.
  • Host bindings go in the host object, not @HostBinding/@HostListener decorators.
  • DOM work goes in afterNextRender, not ngAfterViewInit.

Do it this way now

import { Component, input, output, computed, signal } from '@angular/core';
import { DatePipe } from '@angular/common';

@Component({
  selector: 'user-card',
  imports: [DatePipe],
  host: {
    'class': 'user-card',
    '[class.is-admin]': 'user().isAdmin',
    '(keydown.escape)': 'dismissed.emit()',
  },
  template: `
    
{{ user().name }}

    
Joined {{ user().joined | date }}


    @if (canEdit()) {
      <button (click)="edit()">Edit</button>
    }
  `,
})
export class UserCard {
  user = input.required<User>();
  readOnly = input(false);

  dismissed = output<void>();
  edited = output<User>();

  canEdit = computed(() => !this.readOnly() && this.user().isAdmin);

  edit() { this.edited.emit(this.user()); }
}

Nothing above is boilerplate you could remove. Compare it with the same component written for Angular 15 and roughly a third of the lines were ceremony.

What changed

Components written between v15 and v18 carry an explicit standalone: true. It still compiles — it is simply redundant now, and the ng generate @angular/core:standalone schematic will strip it along with any NgModules that existed only to declare components.

This is the one v22 change that can alter runtime behaviour rather than just syntax. A component that mutated an object in place and relied on the old check-everything default to notice will stop updating. If that bites, the change-detection-eager schematic pins the old strategy explicitly so you can migrate component by component rather than all at once.

Host bindings

The host object in the decorator replaced the @HostBinding and @HostListener decorators. Both still work, but mixing them is a known source of confusion: when the same property is bound in both places, the decorator wins, which is rarely what anyone expects.

IntentNowPreviously
Static class'class': 'card'@HostBinding('class.card') card = true
Conditional class'[class.active]': 'isActive()'@HostBinding('class.active') get isActive()
Attribute'[attr.aria-expanded]': 'open()'@HostBinding('attr.aria-expanded')
Event'(click)': 'onClick($event)'@HostListener('click', ['$event'])
Key-filtered event'(keydown.escape)': 'close()'@HostListener('keydown.escape')
Gotcha Host binding expressions are strings evaluated in the component's context, so a typo is a runtime failure, not a compile error — the template type checker does not cover them the way it covers a template. Keep them to a single property or method call and put the logic in a computed().

Lifecycle

Most lifecycle hooks are still there and still fine. Two things have changed about how they are used.

First, ngOnChanges is largely obsolete: with signal inputs you derive from an input in a computed() and it recalculates itself. Second, DOM measurement moved to afterNextRender and afterRenderEffect, which — unlike ngAfterViewInit — do not run during server-side rendering, so they are the safe place to touch the real DOM in an app that might later add SSR.

You want to…UseNot
Derive a value from an inputcomputed()ngOnChanges

Measure or touch the DOM onceafterNextRender()ngAfterViewInit
Keep the DOM in sync with stateafterRenderEffect()ngAfterViewChecked
Clean up on destroyinject(DestroyRef).onDestroy() or takeUntilDestroyed()ngOnDestroy
Before v15 — the NgModule era, for reading old code

Every component had to be declared in exactly one NgModule, and could only use another component if that module imported the module that exported it. This is why old codebases have SharedModule, and why adding one component to one template used to mean editing three files.

@NgModule({
  declarations: [UserCard, UserList],
  imports: [CommonModule],
  exports: [UserCard],
})
export class UserModule {}

The mental translation: declarations became nothing at all, and the module's imports moved onto each component that actually needed them. NgModules are not deprecated and large applications still contain them, but nothing new requires one.
