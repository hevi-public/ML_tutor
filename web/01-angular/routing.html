Routing

Guards became functions, lazy loading became per-component, and route parameters became inputs — so a routed component no longer needs to know the router exists.

At a glance
  • Guards and resolvers are plain functions. The class-based interfaces were removed in v16 — one of the few hard deadlines.
  • loadComponent lazy-loads a single standalone component; loadChildren still loads a group of routes.
  • withComponentInputBinding() binds route params, query params, data and resolved values to component inputs.
  • Route config is a plain array — no RouterModule.forRoot.

Do it this way now

// app.routes.ts
export const routes: Routes = [
  { path: '', loadComponent: () => import('./home').then(m => m.Home) },
  {
    path: 'users/:id',
    loadComponent: () => import('./user-detail').then(m => m.UserDetail),
    canActivate: [authGuard],
    resolve: { breadcrumb: breadcrumbResolver },
  },
  {
    path: 'admin',
    canMatch: [adminGuard],           // skip the route entirely if it fails
    loadChildren: () => import('./admin/routes').then(m => m.adminRoutes),
  },
  { path: '**', component: NotFound },
];

// main.ts
bootstrapApplication(App, {
  providers: [
    provideRouter(
      routes,
      withComponentInputBinding(),
      withViewTransitions(),
      withInMemoryScrolling({ scrollPositionRestoration: 'enabled' }),
    ),
  ],
});

What changed

This one has a real deadline attached, unlike most of the changes in this reference: CanActivate and friends were deprecated in v15 and removed in v16. Code still implementing those interfaces does not compile on any currently supported Angular version.

The testing payoff is the real argument. A component that takes id as an input can be tested by setting an input. A component that reads ActivatedRoute needs the router harness, or a mock whose shape you have to get right.

Guards

GuardRunsUse for
CanMatchFnBefore the route is even matchedFeature flags, role-based routes — the lazy chunk is never downloaded if it fails
CanActivateFnAfter matching, before activatingAuthentication
CanActivateChildFnBefore activating any childGuarding a whole section
CanDeactivateFnBefore leaving"You have unsaved changes"
ResolveFnBefore activatingData the route cannot render without

All return boolean, UrlTree, or a Promise/Observable of either. Returning a UrlTree redirects — prefer it to calling router.navigate() inside a guard, which races with the navigation already in progress.

Prefer canMatch over canActivate for authorisation canActivate runs after the route matched, which means the lazy chunk has already been fetched before you decide the user may not see it. canMatch runs first, so a failed check downloads nothing and falls through to the next matching route — which also gives you a clean way to serve different components to different roles at the same path.

Resolvers vs. resource()

A resolver blocks navigation until its data arrives. That is occasionally what you want and usually not: the user clicks and nothing visibly happens until the slowest resolver finishes.

With httpResource() in the component, navigation is instant and the component renders its own loading state. Keep resolvers for the narrow case where the route genuinely cannot exist without the data — for instance, to redirect to a 404 before showing a shell for a record that is not there.

Route params as inputs

// routes: 'users/:id?tab=orders', data: { section: 'admin' }
export class UserDetail {
  id = input.required<string>();      // path param
  tab = input('profile');             // query param
  section = input<string>();          // static route data
  breadcrumb = input<Crumb>();        // resolved value

  user = httpResource<User>(() => `/api/users/${this.id()}`);
}
Gotcha: names collide silently Path params, query params, static data and resolved values all bind into the same input namespace, so two sources with the same key means one quietly wins. Keep the names distinct, especially between data and resolvers.

And in the component, the parameter subscription that withComponentInputBinding() replaces:

ngOnInit() {
  this.route.paramMap.subscribe(params => {
    this.id = params.get('id')!;
    this.load();
  });
}

Worth remembering why that had to be a subscription rather than a one-time read: navigating from /users/1 to /users/2 reuses the component instance rather than recreating it, so a value read in ngOnInit would never update. Signal inputs handle that case by construction.
