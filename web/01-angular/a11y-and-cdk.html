Accessibility & the CDK

@angular/aria went stable in v22: accessible interaction patterns with no styling attached, so you can build your own design system without re-implementing keyboard navigation from scratch.

At a glance
  • @angular/aria — headless, unstyled primitives that implement the WAI-ARIA interaction patterns. Stable in v22.
  • @angular/cdk — the lower-level toolkit: overlays, portals, drag and drop, virtual scrolling, focus management, test harnesses.
  • @angular/material — a full design system built on both. Use it if you want its look; use the other two if you don't.
  • Every aria primitive ships a test harness alongside it (@angular/aria/tabs/testing and so on).

What @angular/aria gives you

Eight families of primitive, each a set of directives that supply roles, ARIA attributes, keyboard handling and focus management — and no CSS whatsoever:

ImportPatternWhat it handles for you
@angular/aria/listboxListboxArrow keys, typeahead, single/multi selection, aria-activedescendant
@angular/aria/comboboxComboboxPopup wiring, filtering, the expanded/collapsed contract
@angular/aria/menuMenuSubmenus, roving focus, escape and click-away
@angular/aria/tabsTabsTab/panel association, arrow-key navigation, lazy panel content
@angular/aria/accordionAccordionTrigger/panel association, expansion state
@angular/aria/treeTreeExpand/collapse, level and set-size attributes, navigation
@angular/aria/gridGridTwo-dimensional cell navigation
@angular/aria/toolbarToolbarRoving tabindex across controls
 
<!-- your markup, your classes; the behaviour comes from the directives -->
<div ngTabs class="tabs">
  <div ngTabList class="tab-row">
    <button ngTab value="profile" class="tab">Profile</button>
    <button ngTab value="billing" class="tab">Billing</button>
  </div>

  <div ngTabPanel value="profile">…</div>
  <div ngTabPanel value="billing">…</div>
</div>

Arrow-key navigation, role attributes, the aria-controls/aria-labelledby pairing and focus management all come from the directives. You supply the markup and the CSS.

Why this matters more than it looks Custom tabs, comboboxes and menus are where accessibility usually breaks — not because people do not care, but because the ARIA authoring practices are long, subtle, and hard to verify by eye. Before v22 the choice was adopt Angular Material's visual design or reimplement all of it. Headless primitives remove that trade.

Accessibility without a library

Most of it is not a library problem. The recurring issues in Angular applications specifically:

IssueWhat to do
A route change announces nothing to a screen reader Move focus to the new page's heading on navigation, and use LiveAnnouncer for the title
<div (click)> Use a <button>. It brings keyboard, focus and role for free
Content revealed by @if with no announcement aria-live on the container, or move focus into it
Loading states invisible to assistive tech aria-busy, and announce completion
Focus lost when an element is removed Move focus deliberately before removing it
Animations that ignore user preference Respect prefers-reduced-motion

Images

NgOptimizedImage is worth knowing about here because the largest contentful paint is usually an image. Swap src for ngSrc and it enforces width and height (preventing layout shift), sets sensible loading and fetch priorities, generates srcset, and warns in development when a above-the-fold image is missing priority.

<img ngSrc="/hero.jpg" width="1200" height="600" priority alt="…">
