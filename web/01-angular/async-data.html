Async data & HTTP

The resource API turns "fetch this, and tell me while it is loading" into three signals — and gets cancellation right, which hand-rolled versions rarely do.

At a glance
  • httpResource(url) for the common case; resource({ params, loader }) when the source is not HTTP; rxResource when the loader returns an Observable.
  • All three expose value(), isLoading(), error() and status() as signals, plus reload().
  • The request is reactive: read a signal in it and it re-fetches when that signal changes, abandoning the previous result.
  • HttpClient uses fetch by default from v22.
  • Interceptors are functions, not classes.

Do it this way now

import { httpResource, resource } from '@angular/core';

export class UserDetail {
  userId = input.required<string>();

  // Re-fetches whenever userId() changes; the previous request is abandoned.
  user = httpResource<User>(() => `/api/users/${this.userId()}`);

  // Conditional: return undefined and the resource stays idle.
  orders = httpResource<Order[]>(() =>
    this.user.hasValue() ? `/api/users/${this.userId()}/orders` : undefined);

  // Non-HTTP sources use resource() with a loader.
  location = resource({
    params: () => ({ id: this.userId() }),
    loader: ({ params, abortSignal }) =>
      navigator.geolocation ? getPosition(params.id, abortSignal) : Promise.resolve(null),
  });
}
@if (user.isLoading()) {
  <app-spinner />
} @else if (user.error()) {
  <p class="error">Couldn't load that user.</p>
  <button (click)="user.reload()">Try again</button>
} @else {
  <h2>{{ user.value()?.name }}</h2>
}

What changed

The cancellation point deserves emphasis because it is the bug the hand-rolled version always has. Type quickly in a search box and you fire five requests; without cancellation, whichever server responds last wins, and that is not necessarily the one matching what is on screen. A resource abandons superseded requests, and the abortSignal passed to a custom loader lets you actually abort them.

Worth checking if you have interceptors or tests that assume XHR-specific behaviour — upload progress events in particular behave differently. The http-xhr-backend schematic pins the old backend explicitly if you need time.

Choosing between resource, Observable and signal

SituationReach for
Load data for whatever the user is looking athttpResource()
Same, but the loader is not HTTPresource()
Same, but your loader already returns an ObservablerxResource()
A one-shot command (POST a form, delete a thing)firstValueFrom(http.post(…))
A genuine stream — websocket, polling, server-sent eventsRxJS, then toSignal()
Debounce, throttle, retry with backoff, raceRxJS — this is what it is for
Gotcha: a resource is for reads Resources re-run when their request changes, which is exactly wrong for a mutation — you do not want deleting a record to re-fire because a signal moved. Use HttpClient directly for writes, then reload() the resource that displays the result.
Gotcha: value() can be undefined Before the first successful load there is no value. Either give resource() a defaultValue — which narrows the type and removes the undefined — or branch on isLoading() / hasValue() in the template.
Before v19 — the three-field pattern

Every codebase wrote this, and every codebase wrote it slightly differently:

user?: User;
loading = false;
error?: unknown;

ngOnInit() {
  this.route.paramMap.pipe(
    switchMap(p => {
      this.loading = true;
      return this.http.get<User>(`/api/users/${p.get('id')}`);
    }),
    takeUntil(this.destroy$),
  ).subscribe({
    next: u => { this.user = u; this.loading = false; },
    error: e => { this.error = e; this.loading = false; },
  });
}

The switchMap version above is the good one — it cancels correctly. The common version used mergeMap or a bare nested subscribe, and shipped the out-of-order bug.
