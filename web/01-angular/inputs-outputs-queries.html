Inputs, outputs & queries

A component's public surface. All three moved from decorators to signal-returning functions, and all three got simpler in the process.

The swap
  • @Input() → input() / input.required()
  • @Output() … EventEmitter → output()
  • @ViewChild() → viewChild() / viewChild.required()
  • @ContentChild() → contentChild(), and the plural forms viewChildren() / contentChildren()
  • Two-way binding: @Input() x + @Output() xChange → model()

Do it this way now

import { Component, input, output, model, viewChild, computed, ElementRef } from '@angular/core';

@Component({ /* … */ })
export class RangeSlider {
  // required: a missing binding is a compile error, not an undefined at runtime
  label = input.required<string>();

  // optional, with a default
  min = input(0);
  max = input(100);

  // transform: accept what the template can easily give you
  disabled = input(false, { transform: booleanAttribute });

  // alias: the public binding name differs from the field name
  step = input(1, { alias: 'stepSize' });

  // two-way: template writes [(value)]="x"
  value = model(50);

  // an event out
  committed = output<number>();

  // a DOM reference, as a signal
  track = viewChild.required<ElementRef<HTMLElement>>('track');

  // derive freely — no ngOnChanges, no setter
  percent = computed(() =>
    (this.value() - this.min()) / (this.max() - this.min()) * 100);

  commit() { this.committed.emit(this.value()); }
}

What changed

The migration is mechanical enough to automate, but it cannot convert an @Input() set foo(v) setter that does work — a setter with a side effect becomes an effect(), and one that derives a value becomes a computed(). The schematic leaves those for you.

The static: true flag disappears entirely, which is worth dwelling on: it existed only to tell Angular whether the queried element could be resolved before change detection ran. With a signal query the question never comes up, because you read the signal at the moment you need it rather than at a moment Angular chose.

Gotcha: inputs are read-only input() returns an InputSignal, which has no set() — a child cannot write to its own input, by design. If you need "starts from the input but the user can change it", that is model() for a two-way binding, or linkedSignal() for local state that resets when the input changes.
Gotcha: required inputs are not available in the constructor input.required() guarantees the binding exists, not that it has been set by the time your constructor runs. Reading one too early throws. Read it in a computed(), an effect(), or the template — all of which run after bindings are applied.

The plural forms return a plain readonly array rather than a QueryList, so .changes, .first, .toArray() and forEach are gone. Use array methods, and use a computed() where you would have subscribed to .changes.

View vs. content

Worth restating because it trips people up in both the old and new APIs: view queries search the component's own template; content queries search what a parent projected in through <ng-content>. A tab group finds its tabs with contentChildren(), because the tabs were written by whoever used the tab group.

Before v17 — decorators, and the timing problems that came with them 
export class RangeSlider implements OnChanges, AfterViewInit {
  @Input({ required: true }) label!: string;
  @Input() min = 0;
  @Input() max = 100;

  @Input()
  set value(v: number) {          // a setter, because you needed to react
    this._value = v;
    this.percent = (v - this.min) / (this.max - this.min) * 100;
  }

  @Output() valueChange = new EventEmitter<number>();
  @ViewChild('track', { static: false }) track!: ElementRef;

  ngOnChanges(changes: SimpleChanges) { /* recompute on min/max change too */ }
  ngAfterViewInit() { /* only here is `track` guaranteed to exist */ }
}

Three separate mechanisms — a setter, ngOnChanges and ngAfterViewInit — existed to answer the question "has this value arrived yet?". Signals answer it by construction.
