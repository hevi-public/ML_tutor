Signals

A value that knows who is reading it. That one property is what lets Angular update exactly what depends on a change — and what makes zoneless possible.

The whole API
  • signal(v) — writable state. Read with (), write with .set() or .update().
  • computed(fn) — derived, read-only, cached, lazy.
  • effect(fn) — a side effect that re-runs when what it read changes. For talking to the outside world, not for deriving state.
  • linkedSignal(…) — derived and writable: resets when its source changes, but can be overwritten in between.
  • untracked(fn) — read without creating a dependency.

Do it this way now

import { signal, computed, effect, linkedSignal, untracked } from '@angular/core';

export class Cart {
  private items = signal<Item[]>([]);

  // Derived state: cached, and recomputed only when `items` actually changes.
  total = computed(() => this.items().reduce((n, i) => n + i.price, 0));
  isEmpty = computed(() => this.items().length === 0);

  // Writable, but resets whenever the cart changes.
  selected = linkedSignal({
    source: this.items,
    computation: (items) => items[0] ?? null,
  });

  constructor() {
    // Talking to the outside world — not deriving state.
    effect(() => localStorage.setItem('cart', JSON.stringify(this.items())));
  }

  add(item: Item) {
    // update() when the new value depends on the old one; set() otherwise.
    this.items.update(items => [...items, item]);
  }
}

Try it

Two signals feed two branches. full → greeting has an effect at the end of it; initials has nothing reading it. The recompute counters are real — this is a working signal graph, not a recording.

Three things worth doing in that demo, because they are the three things people get wrong:

  • Type in a box, then look before clicking anything. initials goes dirty and stays there — nobody has asked for it, so nothing is computed. Click "Read initials" and it recomputes on the spot. A computed() nobody reads costs nothing, ever. The other branch does recompute, because the effect at the end of it is a reader and it wants an answer immediately.
  • Click "change both". Two signals change, and the effect still runs once — after the graph has settled. It never observes full updated against a stale first. That property is called glitch-free, and a naive listener-based system does not have it.
  • Click "set to the same value". Nothing happens at all. Signals compare with Object.is before propagating.
Gotcha: that equality check is by reference items.update(list => { list.push(item); return list; }) returns the same array, so Object.is says nothing changed and nothing updates. Always produce a new reference — [...list, item] — or pass a custom equal function. This is the single most common signal bug.

What changed

The BehaviorSubject pattern it replaces is still perfectly good RxJS — it is just the wrong tool for synchronous state that a template reads. It needs an async pipe or a subscription, it has no laziness, and deriving from two of them means combineLatest for what is really just an expression.

computed vs. effect: the decision

Almost every signal mistake is an effect() that should have been a computed(). The test is simple: if the function produces a value, it is a computed. An effect exists to cause something outside the reactive graph to happen.

You want to…UseWhy not the other
Show a total derived from a listcomputed() An effect writing to another signal runs a frame later and can loop.
Persist to localStorageeffect() Nothing reads the result — there is no value to cache.
Log or send analyticseffect()Same.
Sync a third-party chart libraryeffect() or afterRenderEffect() Use the latter if it touches the DOM.
Keep a form field in step with a selectionlinkedSignal() A computed cannot be written to; an effect would fight the user's typing.
Fetch data when an id changesresource() An effect gives you no loading state and no cancellation.
Gotcha: writing signals inside an effect It is allowed but almost always wrong — it is how you get an infinite loop or a value that lags one cycle behind. If you find yourself doing it, the answer is usually computed() for pure derivation or linkedSignal() for "derived but the user can override it".

untracked

Inside a computed or effect, every signal you read becomes a dependency. untracked() reads without subscribing — useful when you need a current value for context but do not want changes to it to trigger a re-run.

effect(() => {
  const item = this.selected();              // re-run when the selection changes
  const user = untracked(() => this.user()); // but not when the user changes
  analytics.track('selected', item, user);
});

Reading a signal in a template

Signals are called as functions in templates: {{ count() }}, not {{ count }}. Forgetting the parentheses renders the function itself and is a common first-day mistake — though with strict templates the type checker usually catches it.

Before v16 — how component state used to work

Two patterns, both of which you will still meet:

Plain fields plus zone.js. You mutated this.count and zone.js noticed that something happened, so Angular re-checked the whole component tree. Simple to write, impossible to make efficient, and the reason OnPush existed.

BehaviorSubject plus the async pipe. More correct and OnPush-friendly, at the cost of RxJS ceremony for state that was never really a stream:

private count$ = new BehaviorSubject(0);
double$ = this.count$.pipe(map(n => n * 2));

// template: {{ double$ | async }}

Both still work. Neither gives Angular the dependency information that makes zoneless change detection possible.
