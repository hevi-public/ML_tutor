What is an algorithm?

A recipe precise enough for a machine — that's the easy half of the definition. The interesting half is that two correct recipes for the same job can differ so much that one is fine at a hundred names and hopeless at a billion.

Before you start Nothing. This page is the course's thesis statement, played out on a phone book.

The idea

You already write algorithms every day — every function that transforms input to output is one. So this course isn't going to teach you what an algorithm is. It's going to teach you the two questions computer science asks about them, questions that working code alone never answers:

How do we know it's right? Not "the tests pass" — certain, for every input, including the ones nobody wrote a test for. That's what invariants and proofs are for, and they're lighter than their reputation.

What does it cost? Not on your laptop, on this dataset — as a law: what happens to the work as the input grows? That's the theory of the next unit, and it decides which systems survive contact with production traffic.

Here's the whole story in one artifact your grandparents owned: the phone book. Ten thousand names, alphabetical. Two correct ways to find "Marlowe, Ada": start at page one and read every entry — or open the middle, decide which half holds M, and repeat. Both work. Watch what "both work" hides.

Where you'll meet this

Every "why is this endpoint slow?" ticket you've ever triaged. The same job — find the record — is a table scan or an index lookup, a list.find() or a Map.get(), a grep through logs or a query against the system that indexed them. The vocabulary you're about to learn (unit 1) is how engineers say "the second one, obviously, and here's the proof" in one line of a design review.

The details (open as much as you like)

So what will this course actually make you able to do?

Three things, compounding: name costs precisely (unit 1's notation, measured live on every page after it); choose structures and algorithms deliberately (units 2–7 — the catalogue, with graphs as the centerpiece); and recognise all of it in the systems you ship (units 8–9, from force-directed layouts to vector search). The labs (unit 10) make you implement the load-bearing ones; the expert track (unit 11) teaches the limits — problems where no fast algorithm is known, and what to do about it.

The definition, done properly

An algorithm is a finite, unambiguous procedure that transforms input to output. Each word earns its place: finite — it must halt (unit 11 meets problems where even that is undecidable); unambiguous — every step fully determined (randomized algorithms, also unit 11, relax this on purpose and win by it); procedure — independent of any programming language, which is why a 1945 description of merge sort and your JavaScript are the same algorithm.
