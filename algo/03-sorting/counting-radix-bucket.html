Sorting without comparing

The next page proves comparison sorts can't beat n log n. This page is the loophole, visited first on purpose: when keys are small integers, you don't have to compare at all — you can address.

Before you start Hash tables — the "compute where it goes" move is about to sort things.

The idea

Counting sort: if every key is an integer in [0, k], make an array of k+1 tallies, count each key's occurrences in one pass, then walk the tallies in order writing keys back out. No key is ever compared with another — each key IS its own address, the array-indexing superpower yet again. Cost: Θ(n + k) time and Θ(k) space. For n = a million grades in [0, 100]: two linear passes. For n keys in [0, 2⁶⁴]: ruinous — k in the cost is the entire catch.

Radix sort lifts the k limit: sort by the last digit with a stable counting sort, then the next digit, and so on — d passes for d-digit keys, Θ(d·(n + base)). Stability is load-bearing: each pass must preserve the order the previous passes earned (the elementary page's "chained stable sorts" trick, industrialized). Bucket sort is the continuous cousin: scatter uniformly distributed values into n ranges, insertion-sort the (tiny) buckets, concatenate — expected Θ(n) when the distribution cooperates.

Where you'll meet this

Radix sort runs where keys are machine words and n is huge: graphics pipelines sorting draw calls, GPU sorting libraries, network gear binning packets, suffix-array construction (unit 7), and columnar databases sorting fixed-width encoded values. Counting sort's tally pass moonlights everywhere as a histogram: percentile estimation, load reports, "requests per status code" — half of observability is a counting sort that never bothers with phase two.

The details (open as much as you like)

So is the next page's proof wrong?

No — dodged, honestly. The lower bound governs sorts whose ONLY window into the data is "is a < b?" — sorts that must work for any orderable type: strings, dates, custom comparators. Counting and radix demand more: keys that are small integers (or fixed-width digit strings), i.e. extra structure beyond orderability. The recurring bargain, one more time: stronger assumptions buy lower bounds' loopholes. When someone says "you can't sort faster than n log n", the sharp reply is "…by comparisons; what do we know about the keys?"

Why radix needs stability, precisely

After sorting by the ones digit, 23 precedes 21? No — but 21 and 23 differ in the ones digit, fine. Consider 21 and 25 → ones pass orders them 21, 25. Tens pass: both have tens digit 2 — if that pass scrambles equal keys, the ones-pass work is destroyed. Stable passes preserve it, so after the final (most significant) pass, ties on every higher digit stand resolved by the lower digits — a full lexicographic sort, built backwards. Least-significant-first + stable is the whole design.

The code

// The demo's exact generator (assets/js/algo/sorts.js):
function* countingSort(a, maxKey) {
  const counts = new Array(maxKey + 1).fill(0);
  for (let i = 0; i < a.length; i++) {
    counts[a[i]]++;                      // the key IS the address
    yield { type: "count", key: a[i], i, counts: counts.slice() };
  }
  let out = 0;
  for (let key = 0; key <= maxKey; key++)      // walk keys in order
    for (let c = 0; c < counts[key]; c++) {
      a[out] = key;                      // write, don't compare
      yield { type: "set", i: out, value: key };
      out++;
    }
}
