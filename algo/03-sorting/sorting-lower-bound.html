Unit 3 · Sorting & searching

Why n log n is the floor

Not "nobody has found a faster comparison sort" — nobody ever will, and we can prove it. This is the course's first impossibility result: a fence around an entire infinite space of algorithms, including all the ones not invented yet.

Before you start Factorials and logs from the math toolkit. The proof is one counting argument; every symbol is introduced below.

The idea

How do you prove something about every possible algorithm, including ones no one has imagined? You find something they all must do, and count it. For comparison sorts the shared anatomy is this: since the only question they may ask is "is a < b?", any such algorithm — however clever its control flow — is, for a fixed n, a decision tree: a binary tree where each internal node is one comparison, each branch is an answer, and each leaf is a final verdict about the input's ordering.

Two counts collide. Count the verdicts needed: n items can arrive in n! different orders, and the algorithm must treat every one differently (each needs a different rearrangement) — so the tree needs at least n! leaves. Count the verdicts available: a binary tree of height h has at most 2ʰ leaves. The worst-case number of comparisons IS the tree's height, so:

2^h \ge n! \;\;\Longrightarrow\;\; h \ge \log_2(n!) = \Theta(n \log n)

In plain English: there are astronomically many possible orderings to tell apart, each comparison at best halves your uncertainty, and halving your way down from n! possibilities takes n log n halvings. Any comparison sort, on its worst input, must ask that many questions — merge sort and heapsort are therefore optimal, not merely good.

Where you'll meet this

Directly: when a teammate proposes "a clever O(n) dedupe-by-sorting of arbitrary strings", this page is the two-line review comment. More broadly, the argument style — "count the distinguishable outcomes, count the information per operation, divide" — prices other things too: any comparison-based search of an unordered n-item set needs Ω(n) looks; log₂(k) bits genuinely are needed to distinguish k states (the information-theory floor under compression and encodings); and unit 11's hardness results are this page's worldview, escalated: some fences are around whole complexity classes.

The details (open as much as you like)

The proof, walked slowly

1. Every comparison sort is a decision tree (for fixed n). Run the algorithm; whenever it compares, branch on the answer. All its loops and recursion unroll into this tree — the tree is just "every path the code could take", with the input's ordering deciding which path runs.

2. It needs n! leaves. Two different input orderings can't share a leaf: a leaf dictates one specific rearrangement, and the same rearrangement applied to two different orderings can't sort both. (If two orderings reached the same leaf, at least one would come out unsorted — a correctness bug.)

3. Height bounds leaves. Each level at most doubles the leaf count: h levels ⇒ ≤ 2ʰ leaves. Combining: 2ʰ ≥ n!, so h ≥ log₂(n!).

4. log₂(n!) is Θ(n log n). Upper: n! < nⁿ so log(n!) < n log n. Lower: the top half of the factors are each ≥ n/2, so n! ≥ (n/2)^{n/2}, giving log(n!) ≥ (n/2)log(n/2). Squeezed both sides. ∎

What the fence does and doesn't enclose

Enclosed: every algorithm whose only data access is pairwise comparison — all of units 3's comparison sorts, all future ones, on worst-case inputs. Not enclosed: integer-key sorts (last page's loophole — they extract more than one bit per operation by indexing), nearly-sorted inputs (the bound is worst-case; insertion sort's adaptive linear run doesn't violate it because SOME input still forces the staircase), and average-case… almost: an averaging refinement of the same counting shows even the average over random inputs is Ω(n log n). The fence is precise about its model — which is exactly what makes it usable in an argument.

The same argument, aimed at searching

Searching a sorted array by comparisons: n+1 possible verdicts ("it's at index 0…n−1, or absent"), each comparison at most halves the candidates ⇒ Ω(log n) — binary search is optimal, unit 0's punchline now proven. Searching an UNsorted array: an adversary argument (the proof style's sibling) — any unexamined element could have been the target, so Ω(n) looks are forced. Sortedness doesn't just help; it changes the information-theoretic floor.
