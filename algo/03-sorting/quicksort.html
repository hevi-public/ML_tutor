Quicksort: brilliant, fragile, fixed by a coin flip

The fastest comparison sort in practice, in-place, and the best story in the unit: a hidden worst case that ambushes exactly the inputs production loves to produce — and a one-line randomized repair.

Before you start Merge sort (the divide-&-conquer frame) and the BST degeneration demo from unit 2 — you're about to see its twin.

The idea

Merge sort does its work on the way up (the merge). Quicksort does it on the way down: pick a pivot, then partition — one linear pass moving everything smaller to the pivot's left and everything larger to its right. After the pass, the pivot sits in its final sorted position (green in the demo), and the two sides can be sorted independently. No merge needed, no scratch array: the combine step is free because partitioning already put every element on the correct side.

The cost hinges entirely on the split quality. Balanced splits: the merge-sort recurrence, Θ(n log n). But this implementation picks the last element as pivot — and on already-sorted input that's always the maximum: one side gets everything, the other nothing, and the "recursion tree" is unit 2's degenerate BST chain wearing a different hat. n levels × n work = Θ(n²), triggered by the most common input shape in production data.

Randomization doesn't dodge this one input — it makes every input equally safe: no fixed input is bad anymore, only unlucky coin flips, and those wash out exponentially. This idea — "make your own luck so the adversary can't choose your worst case" — is a unit 11 headline, met here first.

Where you'll meet this

C++'s std::sort (introsort = quicksort + a heapsort parachute), Go's and Rust's pdqsort variants, V8's Timsort predecessor — quicksort's descendants sort most of the world's in-memory data. The ambush is real history: sorted-input quadratic quicksorts have caused production incidents, and crafted-input attacks on known pivots are a documented DoS class (the hash-flooding page's sibling). Partitioning alone — split by a predicate, order within sides unimportant — is everywhere: quickselect (two pages on), Lomuto/Hoare passes inside databases, even "move failed items to the front of the retry queue".

The details (open as much as you like)

Why random pivots give n log n on average

A random pivot lands in the middle half of the values with probability ½ — and a middle-half pivot leaves both sides ≤ ¾n. So on average every couple of rounds the problem shrinks geometrically: expected depth O(log n), each level linear. (The precise constant: expected comparisons ≈ 1.39 n log₂ n — the same 1.39 as the random-BST height, because they are literally the same analysis.) The worst case still exists — you can flip tails forever — but no input causes it, and its probability vanishes exponentially.

Engineering the real thing: introsort's three safety nets

Production quicksorts add: median-of-three pivots (cheap split insurance), a depth limit that bails to heapsort if recursion exceeds ~2 log n (capping the worst case at n log n — that's introsort), and insertion sort below ~16–32 elements. Also worth knowing: Lomuto's partition (taught here for its clarity) does more swaps than Hoare's (used in practice), and plain quicksort is not stable — the long-range swaps leapfrog equal keys, which is why stable-sort APIs are merge-descended instead.

The code

// The demo's exact partition (assets/js/algo/sorts.js) — Lomuto scheme:
const pivot = a[hi];                    // ← the fragile line; randomized fix:
let i = lo;                             //    swap a random index into hi first
for (let j = lo; j < hi; j++) {
  yield { type: "compare", i: j, j: hi };
  if (a[j] < pivot) {                   // belongs on the left
    if (i !== j) { [a[i], a[j]] = [a[j], a[i]]; yield { type: "swap", i, j }; }
    i++;                                // left region grows
  }
}
[a[i], a[hi]] = [a[hi], a[i]];          // pivot lands between the regions —
yield { type: "sorted", i };            //   its FINAL sorted position
