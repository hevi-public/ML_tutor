Heapsort: the guarantee, in place

Merge sort's promise without merge sort's memory: n log n worst case, zero extra space. The trick is unit 2's heap, built inside the very array being sorted — and its role today is mostly to stand behind quicksort as the parachute.

Before you start Heaps — especially "the array IS the tree" and the O(n) bottom-up build.

The idea

The heaps page ended on a tease: drain a heap and the values come out sorted. Heapsort does it without leaving the array. Phase one: heapify in place — reinterpret the unsorted array as a complete tree and sift-down from the last parent up to the root; O(n) by the geometric-series argument. Now a[0] is the max (max-heap this time). Phase two, n−1 times: swap the max into its final slot at the end, shrink the heap by one, sift the new root down. The sorted region grows from the right; the heap shrinks from the left; they never overlap — no scratch array, ever.

Every extraction costs one root-to-leaf sift — ≤ log n swaps — so the total is n log n with no lucky or unlucky inputs: like merge sort, no input shape can hurt it.

Where you'll meet this

Mostly as the safety net: introsort (C++ std::sort and kin) runs quicksort but switches any recursion that exceeds ~2 log n depth to heapsort — capping the worst case at n log n while keeping quicksort's average speed. Heapsort alone also fits tight-memory and hard-real-time niches (embedded, kernels) where merge sort's buffer or quicksort's variance is unacceptable. And partial heapsort — stop after k extractions — is the top-K pattern from the heaps page, running your "10 biggest" dashboards.

The details (open as much as you like)

Why doesn't heapsort just win the whole unit?

On paper it has everything: worst-case n log n, in place. In benchmarks it loses to quicksort by ~2× anyway, and unit 2's arrays page said why: the sift-down path jumps i → 2i+1 → 4i+3 — strides that leave the cache line behind, while quicksort's partition streams sequentially. It's also unstable (long-range swaps). So: quicksort for speed, merge for stability and streams, heapsort as the bounded-depth insurance — which is exactly the hybrid your standard library ships.

Show the math — both phases priced

Heapify: sift cost is a node's height; summing heights over a complete tree gives ∑ h·n/2^{h+1} ≤ 2n = O(n) (the halving series again). Extraction phase: n−1 sift-downs on a shrinking heap, each ≤ log n — O(n log n), and it dominates. Lower levels can't save you here the way they did in heapify, because every extraction starts at the root. Total: Θ(n log n) worst case, Θ(1) extra space, and that's tight.

The code

// The demo's exact generator (assets/js/algo/sorts.js), shape only:
for (let i = (n >> 1) - 1; i >= 0; i--) siftDown(i, n);   // heapify: O(n)
for (let end = n - 1; end > 0; end--) {
  swap(0, end);          // current max → its FINAL slot (sorted region grows)
  siftDown(0, end);      // restore the heap rule on what's left: O(log n)
}
