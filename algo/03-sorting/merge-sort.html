Merge sort: the first n log n

Split in half, sort each half, zip the sorted halves together. Nothing here is clever in isolation — the power is structural, and it's the same structure behind big-data pipelines and your database's spill-to-disk sorts.

Before you start Recurrences — merge sort is T(n) = 2T(n/2) + n, the balanced tree whose every level sums to n.

The idea

Two observations carry everything. First: merging two already-sorted lists is easy and linear — look at the two front items, take the smaller, repeat; each comparison permanently retires one element. Second: a single element is already sorted. Recursion connects them: split until trivially sorted, then merge your way back up. Correctness is unit 1's induction verbatim — assume the halves come back sorted, verify the merge preserves it.

The cost is the recurrence page's centerpiece: log n levels of splitting, each level's merges touching all n elements once — Θ(n log n) with no ifs. Not "usually", not "if the input cooperates": always, worst case included. And the merge takes equal-from-the-left first, so it's stable — the property the elementary page taught you to demand. The price: the merge needs O(n) scratch space; sorting truly in place is what the next two pages trade for.

The measurement

Merge sort's dots ride the n log n curve while insertion's head for the parabola — and unlike quicksort (next page), NO input can push merge sort off its curve. Guaranteed bounds are a real engineering property: they're why merge-descended sorts serve latency-sensitive and adversarial-input settings.

Where you'll meet this

Merging sorted streams is a load-bearing wall of infrastructure: external sorting (data too big for RAM: sort chunks, then k-way merge — every serious database does this for big ORDER BYs), LSM storage engines compacting sorted runs (unit 9), log aggregators merging per-host sorted-by-time streams, and merge joins. Timsort — the actual sort() in Python, Java and V8 for objects — is merge sort that finds naturally-sorted runs and merges them, with insertion sort in the small cases: the last two pages, hybridized.

The details (open as much as you like)

Why the merge is the whole trick

The elementary sorts move information one adjacent step at a time, so they can't beat the inversion count. A merge moves an element arbitrarily far in one write, guided by the sortedness already earned in the halves. That's the divide-&-conquer bargain everywhere: pay to establish structure in the parts, then let the combine step exploit it wholesale. (Same bargain as binary search exploiting sortedness — unit 0's "structure converts to saved work", now purchasable at runtime.)

Show the math — the recurrence, retired

T(n) = 2T(n/2) + cn. Recursion tree: level i has 2ⁱ merges of size n/2ⁱ, summing to cn per level; ⌈log₂n⌉ levels; total cn·log₂n + n·T(1) = Θ(n log n). Master theorem case 2 agrees on sight (a=2, b=2, f=n ties n^{log₂2}). Space: the merge buffer is n/2 at the top level and can be reused throughout — Θ(n) extra, and the recursion stack adds Θ(log n). Both worth stating in an interview; only the first usually matters.

The code

// The demo's exact generator (assets/js/algo/sorts.js), merge shown:
const left = a.slice(lo, mid + 1), right = a.slice(mid + 1, hi + 1);
let i = 0, j = 0, k = lo;
while (i < left.length && j < right.length) {
  yield { type: "compare", i: lo + i, j: mid + 1 + j };
  const takeLeft = left[i] <= right[j];   // <= — equal takes LEFT: stability
  a[k] = takeLeft ? left[i++] : right[j++];
  yield { type: "set", i: k, value: a[k] };
  k++;
}
// then copy whichever side has leftovers — they're already sorted

Where this goes next

Merge sort pays memory for its guarantee. Quicksort flips the bargain: in-place and typically faster — with a worst case you can be ambushed by, and a one-line randomized fix that's a small masterpiece of algorithm design.
