Unit 3 · Sorting & searching

Binary search, done right

You've met it twice already. This page exists because binary search holds a famous record: tiny, ancient, obviously correct — and botched by most programmers who write it from scratch. The invariant is the vaccine.

Before you start Proving an algorithm correct — this page is that technique earning rent.

The idea

Jon Bentley asked professional programmers to write binary search; the majority produced a version with a bug. Knuth noted the first correct published version appeared twelve years after the first published version. The bugs are always the same species: boundary confusion — < vs <=, mid vs mid±1, loops that skip an element or never terminate on two-element ranges.

The cure is not memorization, it's the method from unit 1: write the invariant first, then make every line honor it. Ours: if the target exists, its index is in [lo, hi] — both ends inclusive. Every line of the implementation is now forced: the loop runs while the region is non-empty (lo <= hi); a too-small middle moves lo to mid + 1 (mid itself is cleared — keeping it would be timid and break termination); and emptiness means provably absent.

Where you'll meet this

Beyond lookups: git bisect binary-searches your commit history for the one that broke the build — the "array" is time, the "comparison" is your test. Autoscalers and load tests binary-search for capacity limits. Every "find the first version where…", "lowest latency that fails", "boundary between OK and broken" is binary search over a predicate — the pattern below generalizes far beyond sorted arrays: it needs only monotonicity (false…false, true…true).

The details (open as much as you like)

The bug gallery — each one is a broken invariant clause

hi = mid (instead of mid−1): the region no longer shrinks when hi−lo is 0 — infinite loop on some inputs. Termination was a clause of the proof. while (lo < hi) with inclusive bounds: exits with a one-element region unchecked — misses targets at the boundary. Check 3 of the proof fails. mid = (lo + hi) / 2 in fixed-width languages: overflows when lo+hi exceeds the integer max — the famous JDK bug that sat in Arrays.binarySearch for nine years. Write lo + (hi − lo) / 2. (JavaScript's numbers dodge this one until 2⁵³ — but write the safe form anyway; you won't stay in JavaScript forever.)

The upgrade: binary search over any monotone predicate

Replace "a[mid] vs target" with any test that flips once from false to true along the range, and binary search finds the flip point in log n tests. "First bad commit", "smallest capacity that survives the load", "first timestamp after midnight" — same loop, new predicate. This form (find the first true) uses the half-open convention [lo, hi): while (lo < hi) { if (test(mid)) hi = mid; else lo = mid + 1; } — note how the invariant changed ("answer in [lo, hi], hi may BE the answer") and the code changed with it, consistently. Pick a convention by writing its invariant; never mix halves of two conventions — that's the bug gallery's origin story.

The code

// Inclusive convention: INVARIANT — if present, target's index is in [lo, hi]
function binarySearch(a, target) {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {                      // loop while region non-empty
    const mid = lo + ((hi - lo) >> 1);    // overflow-safe middle
    if (a[mid] === target) return mid;
    if (a[mid] < target) lo = mid + 1;    // mid is cleared — exclude it
    else hi = mid - 1;                    // ditto
  }
  return -1;                              // region empty ⇒ provably absent
}
