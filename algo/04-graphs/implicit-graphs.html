Implicit graphs: the graph that's never stored

The biggest graphs software searches don't have node lists or edge lists — they have a rule. "From this maze cell you can step to these neighbors." "From this game position these moves are legal." The graph exists only as a neighbor function, computed on demand — and every algorithm from this unit runs on it unchanged.

Before you start BFS — this page reruns it on a graph made of thin air.

The idea

Look back at BFS's code: the only thing it ever asked the graph was adj.get(u) — "who are u's neighbors?". Nothing requires that answer to come from a stored list. Replace it with a function neighbors(u) that computes the answer, and the algorithm neither knows nor cares. A maze is the cleanest example: a cell's neighbors are "the adjacent cells that aren't walls" — four array lookups, no edge list anywhere. The seen-set does quietly grow with territory actually explored, but the graph itself costs nothing.

This is more than a memory trick — it's what makes enormous state spaces searchable at all. A Rubik's cube has ~4.3×1019 positions; nobody stores that graph. Nodes are states, edges are legal moves, and BFS from the solved state answers "how many moves away am I?" while materializing only the sliver it touches. "States as nodes, moves as edges" is the single most transferable modeling idea in this unit.

Where you'll meet this

Game pathfinding (every RTS click is a grid search); robot motion planning; sliding-puzzle and word-ladder solvers; crawlers, whose "graph" is discovered one fetched page at a time; model checkers exhaustively searching a program's state space for a reachable bug. LLM-era search is implicit-graph-shaped too: in beam search (unit 9) the nodes are partial token sequences and the neighbor function is "append one token" — a graph with more nodes than atoms, searched by materializing almost none of it.

The details (open as much as you like)

Complexity when |V| is astronomical

O(|V| + |E|) is honest but useless when |V| is 1019. The working bound for implicit search is O(reached · b): states actually dequeued, times the branching factor b (neighbors per state — 4 in this maze, ~13 raw moves for a cube). The whole craft is shrinking "reached": prune states that can't lead anywhere (walls), canonicalize states that are secretly identical (board symmetries), or aim the search so it reaches the goal before it reaches everything else — that last idea is A*, one unit ahead, on this very maze. The frontier's memory is the other constraint: BFS's ripple in a huge state space can outgrow RAM long before time runs out — the reason depth-first variants (iterative deepening) exist.

The code

// The demo's exact code (assets/js/algo/maze.js), events elided.
// THE implicit-graph move: neighbors are computed, never stored.
function neighbors(maze, x, y) {
  const out = [];
  for (const [dx, dy] of [[0, -1], [0, 1], [-1, 0], [1, 0]]) {
    const nx = x + dx, ny = y + dy;
    if (inBounds(nx, ny) && !maze.walls.has(key(nx, ny))) out.push([nx, ny]);
  }
  return out;
}

// BFS is UNCHANGED — it just calls the function instead of an index:
while (queue.length) {
  const [x, y] = queue.shift();
  for (const [nx, ny] of neighbors(maze, x, y)) {
    const k = key(nx, ny);
    if (!parent.has(k)) { parent.set(k, key(x, y)); queue.push([nx, ny]); }
  }
}
