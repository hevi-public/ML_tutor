Depth-first search: follow one thread to its end

Change one word in BFS — stack instead of queue — and exploration flips personality: instead of rippling outward evenly, it dives down one path as far as it can go, then backtracks. Worse at distances, but far better at seeing structure: cycles, ordering, connectivity, components.

Before you start BFS — this page is one edit away from it — and recursion, DFS's native habitat.

The idea

Same frontier loop as BFS, but take the newest entry instead of the oldest (last in, first out). Since the newest entry is a neighbor of whatever you just processed, the algorithm keeps pushing deeper along the current path — and only when it runs out of unseen neighbors does it fall back to the previous branch point. That fall-back is backtracking, and you already own the perfect machine for it: the call stack. Written recursively, DFS is four lines, and "backtrack" is just return.

Same O(|V| + |E|) bound, same seen-set, same cycle-proofing. What changes is the order — and the order is the payload. The exact moments DFS enters and leaves each node turn out to encode the graph's deep structure, which the next two pages will cash in for topological ordering and component detection.

Where you'll meet this

Everything tree- or nesting-shaped: directory walks, JSON/AST traversal, compilers resolving imports, dead-code elimination. Dependency resolution is DFS (a package's dependencies install before the package — that's the "leave" order). Deadlock detectors run DFS over waits-for graphs hunting cycles. Maze solvers and puzzle searchers go depth-first because the answer is deep and memory is precious: DFS holds one path, BFS holds a whole ripple — the same reason agent frameworks exploring tool-call trees go depth-first with backtracking.

The details (open as much as you like)

Recursive vs explicit stack — the same algorithm

Recursive DFS uses the language's call stack as the frontier: the stack frames ARE the current path. That's the clearest version and the one to write by default. The explicit-stack version (what this demo runs, so it can yield events) matters when the graph is deep enough to overflow the call stack — a linked-list-shaped graph of 100,000 nodes will crash a recursive walker in most runtimes. Production traversals of untrusted structure (crawlers, serializers) use the explicit stack for exactly that reason. Unit 1's call-stack page is this trade-off's home.

Entry/exit times and edge classification

Give each node a clock tick when DFS first enters it and another when it finally leaves (all neighbors exhausted). These timestamps classify every edge in the graph: tree edges (led to a new node), back edges (point at a node still on the current path — still "open"), forward/cross edges (everything else, pointing at already-closed nodes). One theorem does a lot of work: a directed graph has a cycle if and only if DFS finds a back edge — a back edge closes a loop with the path above it. And sorting nodes by descending exit time yields a valid topological order of a DAG — the next page builds exactly this, from a different angle. Nesting structure is why this works: any two nodes' [entry, exit] intervals either nest or don't overlap at all, like well-formed parentheses.

The code

// One loop, two data structures, two algorithms
// (the demo's exact code — assets/js/algo/graphs.js, events elided):
function traverse(graph, start, container) {
  const adj = adjacency(graph);
  const seen = new Set([start]);
  const frontier = [start];
  while (frontier.length) {
    const u = container === "queue"
      ? frontier.shift()    // oldest first → BFS, the ripple
      : frontier.pop();     // newest first → DFS, the deep dive
    for (const { to } of adj.get(u)) {
      if (!seen.has(to)) { seen.add(to); frontier.push(to); }
    }
  }
}

// The recursive twin — the version you'd actually write:
function dfs(adj, u, seen = new Set()) {
  seen.add(u);
  for (const { to } of adj.get(u))
    if (!seen.has(to)) dfs(adj, to, seen);
}   // returning = backtracking
