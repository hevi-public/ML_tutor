Unit 4 · Graphs

Graphs: the data structure for relationships

Arrays store things; graphs store how things relate. Services calling services, packages depending on packages, pages linking to pages, entities in a knowledge base — once you see the dots-and-lines shape, you see it everywhere. This unit is the course's centerpiece, and it starts with a drawing tool you'll keep using: every graph page runs its algorithm on a graph you can edit.

Before you start Hash tables and arrays & lists — the two ways we'll store a graph are built from exactly those.

The idea

A graph G = (V, E) is just two sets: vertices (nodes — the things) and edges (the relationships between pairs of things). Everything else is qualifiers:

  • Directed vs undirected — does the relationship have an arrow? "A follows B" is directed; "A and B are friends" is not.
  • Weighted — does each edge carry a number? Distance, cost, latency, capacity, similarity.
  • Degree — \deg(v) counts the edges touching a vertex. In plain English: how connected is this node?

We write |V| for the number of nodes and |E| for the number of edges. Graph running times are quoted in both — O(|V| + |E|) means "touch every node and every edge a constant number of times", and you'll be seeing a lot of it.

Two ways to store it

The drawing is for humans. Code needs one of two representations, and the choice is a classic space-vs-question trade-off:

Adjacency list

For each node: a list of its neighbors. Space O(|V| + |E|).

Adjacency matrix

A |V|×|V| grid: cell (u,v) = 1 if the edge exists. Space O(|V|²).

The adjacency list answers "who are u's neighbors?" in time proportional to the answer — perfect for the traversal algorithms this unit runs, which is why every generator in this course uses it. The adjacency matrix answers "is u connected to v?" in O(1) — but eats |V|² space even when almost no edges exist. Real graphs are usually sparse (|E| far below the |V|² maximum: your service mesh has hundreds of services but each calls a handful), so the list wins by default. Reach for the matrix when the graph is small and dense, or when the algorithm itself is matrix-shaped (Floyd-Warshall, unit 5).

Where you'll meet this

Package managers (npm's dependency graph), service meshes and call graphs, social networks, web link graphs, database foreign keys, workflow engines — and the LLM stack is graph-shaped end to end: knowledge graphs relate entities for retrieval, agent frameworks wire tools into orchestration DAGs, and vector indexes like HNSW are literally graphs whose edges connect similar embeddings, searched with the exact traversals you're about to learn. The details (open as much as you like)

How many edges can there be?

An undirected graph on n nodes has at most \binom{n}{2} = n(n-1)/2 edges — every pair, once. In plain English: edge count can grow with the square of node count, which is why "sparse or dense?" is the first question to ask of any graph and why O(|V| + |E|) and O(|V|²) can be worlds apart. A directed graph doubles the bound (each pair, both arrows); allow self-loops and multi-edges and you're in "multigraph" territory — fine, but say so.

A third representation: the edge list

Sometimes the graph is just an array of (u, v, w) triples — no index at all. Useless for "who are u's neighbors?", but exactly right when an algorithm processes edges in bulk regardless of endpoints: Kruskal sorts all edges by weight, Bellman-Ford sweeps all edges repeatedly. It's also the natural wire/storage format — an edge table in a database IS an edge list. This course's graph model stores edges as a list and builds the adjacency index on demand.

The code

// The course's shared graph model, and the index every algorithm builds first
// (assets/js/algo/graphs.js):
const graph = {
  directed: false,
  nodes: [{ id: "a", x: 0.2, y: 0.3 }, ...],   // x,y only for drawing
  edges: [{ u: "a", v: "b", w: 4 }, ...],       // w optional
};

function adjacency(graph) {
  const adj = new Map(graph.nodes.map((n) => [n.id, []]));
  for (const e of graph.edges) {
    adj.get(e.u).push({ to: e.v, w: e.w ?? 1 });
    if (!graph.directed) adj.get(e.v).push({ to: e.u, w: e.w ?? 1 });
  }
  return adj;   // adj.get(u) → u's neighbors, in O(1)
}
