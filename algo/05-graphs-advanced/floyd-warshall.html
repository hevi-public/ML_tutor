Floyd-Warshall: every pair at once

Three nested loops, one line of logic, and every node knows its distance to every other. No frontier, no priority queue, no cleverness you can point at — the intelligence is entirely in which loop is on the outside, and that choice is this course's first real taste of dynamic programming.

Before you start Dijkstra and Bellman-Ford, so "all pairs" has something to be compared against. The adjacency matrix finally gets its algorithm.

The idea

Number the nodes 1…n. Define the subproblem by which stopovers are allowed: let dk(i, j) be the shortest i→j distance using only nodes 1…k as intermediate stops. Base case d₀: direct edges only. Then admit stopover k, one at a time. A best path either ignores k — distance unchanged — or routes through it exactly once: d(i,k) + d(k,j), both halves already optimal over stops 1…k−1. So:

d_k(i,j) = \min\big(d_{k-1}(i,j),\; d_{k-1}(i,k) + d_{k-1}(k,j)\big)

In plain English: "is it cheaper to go through k?" — asked for every pair, once per possible stopover.

Three loops, k outermost — that ordering IS the algorithm: every pair must finish absorbing stopover k before anyone reasons about k+1. O(|V|³) time, O(|V|²) space, negative edges welcome (a negative diagonal entry appearing is the negative-cycle alarm). For the 30-node graphs where all-pairs answers are actually wanted, n³ = 27,000 steps is nothing.

Where you'll meet this

Anywhere the full distance table is the product: network capacity planning ("latency between every pair of regions"), transit-network analysis, precomputed lookup tables in games, graph metrics like betweenness that consume all-pairs distances. Its transitive-closure twin (same loops, OR instead of min) computes reachability matrices — "can role X ever escalate to permission Y?" in one sweep. For large sparse graphs, though, run Dijkstra from every node instead (or Johnson's algorithm if weights go negative) — n³ loses to n·(n log n) badly when the matrix wouldn't even fit in memory.

The details (open as much as you like)

Why this is dynamic programming

The unreasonable-looking move — solving n² shortest-path problems simultaneously in n³ steps — works because the problems overlap massively, and Floyd-Warshall organizes the overlap instead of recomputing it. The recipe: define a subproblem family with a dimension you can grow (allowed stopovers), solve in an order where each answer needs only already-finished answers, store everything. That recipe has a name and a whole unit (unit 6) — when you get there, remember this page: you've already done DP on a real problem.

The k-loop must be outermost — see it fail

Put k innermost and the recurrence reads from the wrong version of the table: pair (i, j) would consider routing through k using d(i, k)-values that haven't yet absorbed stopovers below k. Concretely, a path i → 3 → 1 → j gets missed if the (i, j) cell asks about stopover 3 before d(3→j) has learned to route through 1. With k outermost, by the time anyone asks "through k?", every path into and out of k is already optimal over 1…k−1. Loop order as correctness — not style — is a hallmark of DP code, and a classic source of subtly-wrong reimplementations.

The code

// The demo's exact code (assets/js/algo/graphs.js), events elided:
function floydWarshall(graph) {
  const dist = {};                       // dist[i][j], seeded with edges
  for (const i of ids) for (const j of ids)
    dist[i][j] = i === j ? 0 : edgeWeight(i, j) ?? Infinity;

  for (const k of ids)                   // admit stopover k  (MUST be outer)
    for (const i of ids)
      for (const j of ids)
        if (dist[i][k] + dist[k][j] < dist[i][j])
          dist[i][j] = dist[i][k] + dist[k][j];   // cheaper through k

  return dist;                           // the complete distance table
}
