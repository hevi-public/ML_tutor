Bipartite matching: assignment, solved by plumbing

Reviewers to pull requests, jobs to machines, students to projects — pair up two camps, each member used at most once, as many pairs as possible. It looks like a fresh problem needing a fresh algorithm. It isn't: three lines of graph surgery turn it into max flow, and the surgery — a reduction — is the real lesson of the page.

Before you start Max flow (the engine underneath) and bipartite graphs (the two-camp shape, and how to verify it).

The idea

Given workers on the left, jobs on the right, and edges for "this worker can do this job", a matching picks edges sharing no endpoint. To maximize it, build a flow network: a source with a capacity-1 edge to every worker, a capacity-1 edge from every job to a sink, and capacity 1 on all the "can do" edges. Run max flow. Every unit of flow must cross one worker→job edge, and the capacity-1 collars mean no worker or job carries two units — integer flows ARE matchings, value for value. Max flow = max matching, and the saturated middle edges name the pairs.

Better yet, the flow machinery explains matching's classic trick. An augmenting path here alternates unmatched-matched-unmatched edges: "give worker 1 the job worker 2 held; move worker 2 to a free job" — the residual reverse edge is what lets assignments be stolen and cascaded. The rerouting you watched on the last page is reassignment wearing overalls.

Where you'll meet this

Assignment is a daily shape: reviewers↔PRs, on-call slots↔engineers, ads↔impressions, riders↔drivers, GPUs↔training jobs, org-donor exchanges. Weighted versions (maximize total preference, not just count) get the Hungarian algorithm or min-cost flow — same family. The dual result (König's theorem, layered below) powers scheduling proofs; and stable matching — where both sides have preferences and you want no pair tempted to elope — is the Gale-Shapley algorithm running hospital-residency and school-choice systems, a cousin worth knowing exists.

The details (open as much as you like)

Why integer flows are exactly matchings

Two directions. Matching → flow: push 1 unit along src → worker → job → snk for each pair; disjoint endpoints mean no capacity is exceeded — a valid flow of the same value. Flow → matching: with integer capacities, Edmonds-Karp only ever pushes integer bottlenecks (an easy induction), so every edge carries 0 or 1; the capacity-1 source edge means each worker emits at most one unit, sink edges likewise for jobs — the saturated middle edges share no endpoints. Values match both ways, so the maxima coincide. This "solutions correspond, values agree" argument is what makes a reduction trustworthy — unit 11 builds a whole theory on arguments of exactly this shape.

König's theorem, and the faster specialist

Max-flow = min-cut, translated into matching language, becomes König's theorem: in bipartite graphs, max matching = minimum vertex cover (fewest nodes touching every edge). Your demo's unplaceable candidate isn't bad luck — there's a 3-node cover certifying no 4th pairing exists. When you outgrow the generic engine: Hopcroft-Karp finds augmenting paths in batches (all shortest ones per BFS phase), and only O(√|V|) phases are ever needed — O(|E|√|V|) total, the standard for big bipartite instances. Not animated here (the phase batching is bookkeeping-heavy on screen); it is Edmonds-Karp's idea, specialized and accelerated.

The code

// The whole reduction — the demo builds this then calls maxFlow unchanged:
function maxMatching(workers, jobs, canDo) {
  const g = { directed: true, nodes: [], edges: [] };
  g.nodes.push({ id: "src" }, { id: "snk" }, ...workers, ...jobs);
  for (const w of workers) g.edges.push({ u: "src", v: w.id, w: 1 });  // 1 job each
  for (const j of jobs)    g.edges.push({ u: j.id, v: "snk", w: 1 });  // 1 worker each
  for (const [w, j] of canDo) g.edges.push({ u: w, v: j, w: 1 });      // the options
  return maxFlow(g, "src", "snk");   // flow value = matching size;
}                                    // saturated middle edges = the pairs
