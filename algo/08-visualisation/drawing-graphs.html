Force-directed layout: let physics untangle it

General graphs have no root, no depth, no natural coordinates. So don't compute positions — grow them: pretend edges are springs and nodes repel like charges, then simulate until the system relaxes. Communities clump, bridges stretch, symmetry emerges — nobody told the algorithm about any of it.

Before you start The encoding mindset. The graphs being drawn are unit 4's; the editor's "arrange in a circle" button is about to get its promised upgrade.

The idea

Fruchterman-Reingold (1991), the standard recipe. Two forces with an ideal length k ≈ √(area/n): every pair of nodes repels with strength k²/d (strong when close, fading with distance); every edge attracts its endpoints with strength d²/k (stronger the more stretched). Each tick sums forces and moves every node — but capped by a temperature that starts generous and cools each tick: big rearrangements early, fine tuning late, then frozen. That's simulated annealing's schedule applied to aesthetics.

The claim being optimized is implicit: at equilibrium, edge lengths approximate k, connected things sit near each other, and everything else is pushed apart — so screen distance comes to mean graph distance, which is exactly the encoding a viewer's eye assumes. When that assumption holds, clusters in the picture are communities in the data. When the layout hasn't converged (or the graph is too dense), the picture claims things the data doesn't — the honest failure mode to watch for.

Where you'll meet this

Every "network diagram" you've seen — dependency explorers, Kubernetes service maps, social-graph tools, Obsidian's graph view, Neo4j Browser — runs a force simulation (d3-force powers half of them). Knowledge-graph UIs lay out entities this way, and embedding visualizations borrow the same intuition (the next-next page makes that precise). It's also this site's own machinery: the concept map of this course is laid out by the exact generator in the demo — and the graph editor's circle button can now be understood as "the layout you use when you refuse to run one".

Costs, scaling, and the n² elephant

Each tick is O(n²) for repulsion (all pairs) plus O(|E|) for springs; a few hundred ticks for convergence. Fine for hundreds of nodes, painful at tens of thousands. The standard fix imports unit 2's spatial thinking: a Barnes-Hut quadtree groups distant nodes and approximates their combined push as one pseudo-node — O(n log n) per tick, at ~1% position error nobody can see. (d3-force does this.) Multilevel methods coarsen the graph, lay out the small version, then refine. Determinism note: random initial positions mean every run looks different unless you seed — this site seeds (unit 0's reproducibility rule), which is why the demo converges to the same picture every time.

Reading (and distrusting) a force layout

Trustworthy: clusters (dense subgraphs really do clump), bridges (long stretched edges are real bottlenecks), hubs (high degree gathers neighbors). Not trustworthy: absolute positions (arbitrary), left/right/up/down (meaningless), precise distances (only ordinal at best), and apparent "outliers" that are just low-degree nodes pushed to the rim. Hairballs — dense graphs where everything overlaps — aren't a layout failure so much as a signal that node-link is the wrong encoding entirely; the next pages (layers for DAGs, matrices for dense graphs) are the escape hatches.

The code

// The site's actual layout engine (assets/js/viz/layout.js), events elided:
for (let tick = 0; tick < iterations; tick++) {
  for (each pair a, b)  push(a, b, k * k / dist(a, b));   // repel: k²/d
  for (each edge u–v)   pull(u, v, dist(u, v) ** 2 / k);  // attract: d²/k
  for (each node) move(node, capAt(temperature));         // bounded step
  temperature *= 0.96;                     // cool: anneal toward stillness
  if (avgMovement < ε) break;              // converged early
}
