Unit 8 · Visualisation

Why visualise? Because eyes run O(1) queries

This course has been drawing at you for seven units — bars, trees, graphs, grids, tables. This unit opens the hood: drawing data well is itself algorithms (layout is optimization), and choosing what kind of picture is a design decision with rules. First, the case for pictures at all — and for when to refuse them.

Before you start Nothing formal. This unit explains machinery you've already used: every renderer in assets/js/viz/ becomes a lesson.

The idea

Human vision is a massively parallel preattentive processor: outliers, clusters, trends, and gaps in a good picture are perceived in milliseconds, before conscious attention — a query engine that runs O(1) on questions that cost code O(n log n). A visualization is an encoding: data values mapped onto visual channels. The channels are not equal, and their accuracy ranking (Cleveland & McGill's experiments, 1984) is the field's core result:

  1. Position along a common scale (scatter, dot plots) — best;
  2. Length (bars) — nearly as good;
  3. Angle / slope (pie charts, line slopes);
  4. Area (bubbles, treemaps);
  5. Color hue / saturation (heatmaps) — worst for reading values, still superb for spotting categories and anomalies.

Design rule one: spend the best channels on the most important quantities. Rule two: a picture that can't mislead beats a prettier one that can — axis truncation, area-for-value, and rainbow colormaps are the classic lies. Rule three: sometimes the answer is a table; if the task is "look up exact values", drawing is overhead.

Where you'll meet this

Dashboards live or die by channel choice: p99 latency as position (line chart) versus as a color badge is the difference between seeing a regression trend and missing it. Distributed-trace waterfalls are Gantt encodings of span trees; flame graphs encode call stacks as nested lengths — both are unit-8 layout algorithms in daily ops use. And in ML work, embedding projections (this unit's last page), attention heatmaps, and training-curve dashboards are how anyone debugs what a model is doing. The skill of "which picture answers this question" is as transferable as any algorithm in the course.

The details (open as much as you like)

This course's own choices, annotated

Every demo you've used was a channel decision. Arrays → bars (length: values readable, swaps visible). Sorting's settled elements → color (category "done", not a value). Graph distances → text labels above nodes — numbers beat any channel when exact values matter and n is small. The DP tables → literal tables, because the recurrence reads cell values and you should too. The complexity chart → position on a shared scale, measured dots versus claimed curve, because comparing two growth shapes is exactly what position does best. Maze search → a color grid, because the question is regional (where has the frontier reached?), not numeric. When you build an internal tool, run this audit: what's the user's question, which channel answers it at a glance, what could the encoding accidentally claim?
