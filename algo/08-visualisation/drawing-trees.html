Drawing trees: tidiness is an algorithm

Depth going down is obvious. The hard question is x: place every node so nothing overlaps, siblings sit in order, parents center over children — and the drawing wastes no width. This page is the algorithm behind every org chart, AST viewer, and this course's own tree renderer.

Before you start DFS (layout passes are tree walks); the trees themselves came from unit 2.

The idea

Fix y = depth. For x, the classic aesthetic rules (Wetherell-Shannon, then Reingold-Tilford 1981): (1) no overlaps, (2) siblings left to right in order, (3) a parent centered over its children, (4) identical subtrees drawn identically wherever they appear, (5) as narrow as possible. The workable core is two DFS passes. Pass 1 (post-order): lay out each subtree independently, as if alone. Pass 2: when subtrees become siblings, slide the right one leftward until it just barely clears the left one, then center the parent over the group.

The refinement that made R-T famous is how "just barely clears" is computed: each subtree keeps a contour — the leftmost/rightmost x at every depth — so sibling separation is a single walk down two contours instead of comparing every pair of nodes. With one more trick (threads linking contour nodes), the whole layout is O(n). This site's renderer implements the honest simplified version — leaf slots plus parent centering — which satisfies rules 1–3 and is what the demo below runs; the contour machinery is what you'd add for rule 4/5 perfection.

Where you'll meet this

Org charts, file-tree views, AST/expression debuggers, decision trees in ML tooling, phylogenies, DOM inspectors — d3's d3.tree() is literally Reingold-Tilford (via Buchheim's O(n) variant), so every d3 tree on every dashboard runs this algorithm. Flame graphs are the icicle variant (width = a metric instead of leaf count). And this course used the simplified version before you knew: unit 6's Huffman forest and the trie page laid out their trees with this exact code — pages teaching pages.

The details (open as much as you like)

Why greedy per-subtree layout is safe here

A layout algorithm optimizing "minimum width without overlap" sounds like it could need global search. The R-T insight is a separator argument (tree DP's cousin): subtrees interact only through their contours — the deepest silhouettes facing each other. Once siblings are pushed together contour-to-contour, nothing outside that pair can create an overlap between them, so local packing composes into a global optimum (for fixed sibling order). Compare unit 6: same reason tree DP needed only (incl, excl) per subtree. Trees keep being the structure where local reasoning is enough — which is also why the next page, on general graphs, has to abandon exactness entirely.

The code

// The site's actual renderer (assets/js/viz/layout.js):
function tidyTree(root) {
  let slot = 0;
  (function place(node) {
    if (!node.children.length) {
      node.x = slot++;                    // leaves claim slots left to right
    } else {
      node.children.forEach(place);      // post-order: children first
      node.x = (node.children[0].x +     // parent centers over its kids
                node.children.at(-1).x) / 2;
    }
  })(root);
  // y = depth; normalize x by total slots. Full R-T adds contour-merging
  // so identical subtrees render identically and width is optimal.
}
