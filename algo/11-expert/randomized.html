Randomized algorithms: the adversary can't aim at a coin

Every worst case in this course was somebody choosing the input after reading your code — sorted input for naive quicksort, colliding keys for your hash table. A randomized algorithm makes its choices after the input is fixed, so no input is reliably bad. The price: guarantees become expectations. The proof obligations change, the code barely does.

Before you start Quicksort (whose worst case this page dissolves) and hash tables (whose whole design is an expected-case bet).

The idea

Two species, worth keeping apart by name. Las Vegas algorithms are always correct, randomly fast: quicksort with a random pivot sorts correctly every time, and its expected cost is O(n log n) on every input — the expectation is over the algorithm's own coins, not over hoping your users' data is nice. Monte Carlo algorithms are always fast, probably correct: Miller–Rabin says "prime" with error ≤ 4⁻ᵏ after k rounds; unit 9's Bloom filter answers membership with a tunable false positive rate. You pick which side of the guarantee bends.

And one algorithm every working engineer should know by name: Fisher–Yates, the only correct way to shuffle. Walk from the last index down; swap position i with a uniformly random position in [0..i]. Every permutation gets probability exactly 1/n!. The tempting "swap each element with a random index anywhere" is biased — nⁿ equally likely paths cannot land uniformly on n! outcomes, because n! doesn't divide nⁿ.

The bug is invisible in any single output and glaring in aggregate — which is precisely how it ships to production.

Where you'll meet this

Everywhere reliability engineering lives: jittered exponential backoff (randomness prevents synchronized retry stampedes), power-of-two-choices load balancing (random two servers, pick the less loaded — expected max load drops exponentially versus one random choice), per-process hash seeds (the standard defense against the hash-flooding attacks your hash-table lab simulated), Miller–Rabin behind every TLS key generation, reservoir sampling for "pick a fair sample from a stream you can't store". Redis sorted sets run on skip lists — the layered coin-flip structure in the fold-out below. And the shuffle demo is a true cautionary tale: a major browser's randomized ballot for default-browser choice once used a biased comparator shuffle, visibly favoring some vendors.

The details (open as much as you like)

Why random-pivot quicksort is expected O(n log n) on every input

Fix any input. Consider elements of rank i and j (i < j) in sorted order; they get compared at most once, and only if one of them is the first pivot chosen from the ranks i..j. That's 2 favorable outcomes among j − i + 1 equally likely first-choices, so the probability is 2/(j − i + 1). Summing over all pairs: E[comparisons] = Σ 2/(j − i + 1) ≈ 2n ln n. No assumption about the input anywhere in that sentence — the expectation is over pivots. This indicator variable pattern (probability per pair, summed by linearity of expectation) is the workhorse of expected-case analysis; the same three lines analyze hashing's expected chain length and quickselect's expected O(n).

Skip lists: a balanced tree from coin flips

A sorted linked list is O(n) to search. Now flip a coin per element: heads, it also joins a second, sparser list; heads again, a third, and so on. Search from the top lane: skim until you'd overshoot, drop a lane, repeat — expected O(log n), because each lane has expected half the density of the one below, exactly like binary search's halving but enforced by probability instead of by rotation gymnastics. Compare unit 2's AVL/red-black machinery: skip lists get the same expected bounds with ~20 lines and no rebalancing cases, which is why Redis chose them for sorted sets. The trade: worst case O(n) with vanishing probability, versus guaranteed O(log n) with implementation pain. Randomness as a complexity-of-code reducer.

Where the randomness itself comes from — and when mulberry32 is a crime

This site's demos use mulberry32, a seeded PRNG chosen so prose and demo agree forever — determinism as a feature. Games and simulations want exactly that. Security wants the opposite: session tokens, key generation and shuffling anything with money on it need a cryptographically secure source (crypto.getRandomValues in the browser) whose future outputs can't be predicted from past ones. mulberry32's entire future is its 32-bit seed — observing a few outputs reconstructs everything. The classic incident category: online poker sites whose shuffle seed was the server clock, letting observers reconstruct every hand. Fisher–Yates was correct; the coin was counterfeit.

The code

// Fisher–Yates — the site's own shuffle (assets/js/algo/random.js):
function shuffle(array, rand) {
  const a = array.slice();
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));   // uniform in [0..i] — i+1 choices
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;    // each of the n! orders: probability exactly 1/n!
}
// The biased version differs by ONE character class: rand() * a.length —
// swapping with anywhere instead of [0..i]. n^n paths, n! outcomes, no fit.
