P, NP and NP-completeness

Some problems in your backlog have no fast exact algorithm — not because nobody clever has looked, but because they are provably as hard as thousands of other problems that fifty years of clever people haven't cracked. This page gives you the vocabulary to recognize them, and the single most misunderstood definition in computer science: NP is about checking answers, not finding them.

Before you start The sorting lower bound (your first impossibility proof) and choosing a strategy (where "this smells NP-hard" was foreshadowed).

The idea

Everything here is about decision problems — questions with yes/no answers ("is there a schedule meeting all constraints?") — and cost measured as a function of input size, exactly as in unit 1.

P is the class of decision problems solvable in polynomial time — O(n), O(n²), O(n³)… Sorting-related questions, shortest paths, max flow, 2-coloring: everything this course has solved with an efficient algorithm lives here.

NP is the class of problems whose yes-answers are verifiable in polynomial time: if the answer is yes, there exists a short certificate (a witness — the schedule itself, the subset itself) that a polynomial-time checker can confirm. The name means nondeterministic polynomial — not "not polynomial". Every problem in P is also in NP (solving is one way of verifying), so the real question is whether the containment is strict.

NP-complete problems are the hardest in NP: every NP problem reduces to each of them (next page's subject). Find a polynomial algorithm for any one — SAT, traveling salesman, subset-sum, graph coloring, thousands more — and every problem in NP collapses into P. Nobody has. Nobody has proved it impossible either. That is the P vs NP question, and there is literally a million-dollar prize on it.

Where you'll meet this

More often than you'd think. Package managers solve dependency resolution as SAT (Conda and Cargo's resolvers are literal SAT/CDCL solvers). Compilers hit NP-hard register allocation (graph coloring) and ship heuristics. Schedulers, timetablers, load balancers, chip placers, route optimizers — all NP-hard in their exact forms. The engineering tell: when a PM asks for "the optimal assignment" and the honest answer is "we can have optimal-for-small-inputs, or good-enough-fast, pick one," you are usually standing on an NP-hard problem. Naming it changes the conversation from "work harder" to "choose a trade-off" — and the next two pages are exactly those trade-offs.

The details (open as much as you like)

Why "nondeterministic", and the formal picture

The original definition imagines a machine that can guess: a nondeterministic machine solves a problem in polynomial time if some sequence of lucky guesses reaches a yes-answer in polynomially many steps. Guess the certificate, then verify it — which is why "verifiable in polynomial time given a certificate" and "solvable in nondeterministic polynomial time" are the same class. The verifier view is the one to keep: it needs no imaginary hardware.

Formally: a language L is in NP if there's a polynomial-time verifier V and a polynomial p such that x ∈ L exactly when there exists a certificate c, with |c| ≤ p(|x|), making V(x, c) accept. Note the one-sidedness: certificates witness yes. The class of problems with short no-certificates is co-NP ("this number is composite" has a yes-certificate: a factor; "this formula is unsatisfiable" has no known short witness).

Cook–Levin: why SAT is the first domino

NP-completeness needs one problem proved hard from scratch, and that's the Cook–Levin theorem (1971): SAT — is there a true/false assignment satisfying a Boolean formula? — is NP-complete. The proof idea is mechanical rather than mysterious: any polynomial-time verifier is a machine; a machine's step-by-step execution on a given input can be written out as a (large but polynomial) Boolean formula whose variables are "bit b of the machine's state at step t"; the formula is satisfiable exactly when some certificate makes the verifier accept. So every NP problem's solving reduces to SAT-solving. After that first domino, nobody proves hardness from scratch again — you reduce SAT (or any fallen domino) to your problem, which is the next page.

Terminology worth keeping straight: NP-hard = at least as hard as everything in NP (may not itself be in NP — e.g. optimization versions, or halting-type problems); NP-complete = NP-hard and in NP.

What would P = NP actually mean?

Less "faster apps", more "different civilization": public-key cryptography as deployed assumes certain NP problems (factoring-like) have no polynomial algorithm; mathematical proof search becomes feasible (a proof is a certificate — checking one is easy, finding one is the hard part); most of operations research collapses into exact optimization. The expert consensus leans strongly toward P ≠ NP — partly because half a century of independent attacks from logic, combinatorics and geometry all bounced — but a proof of either direction would be one of the results of the century. Meanwhile, engineering proceeds as if P ≠ NP, which is what units 6 and this one train you to do well.

The code

// The demo's two halves — the entire point of this page is their gap.
function solve(values, target) {              // O(2^n · n): try every subset
  let checks = 0;
  for (let mask = 1; mask < 1 << values.length; mask++) {
    checks++;
    let sum = 0;
    for (let i = 0; i < values.length; i++)
      if (mask & (1 << i)) sum += values[i];
    if (sum === target) return { found: true, checks };
  }
  return { found: false, checks };            // "no" costs the full 2^n − 1
}

function verify(certificate, target) {        // O(n): NP's defining move
  return certificate.reduce((a, b) => a + b, 0) === target;
}

Unit 6's dynamic programming gives subset-sum an O(n·target) algorithm — pseudo-polynomial, exponential in the bit length of the target, exactly as the knapsack page warned. It doesn't put subset-sum in P, but it's why "NP-hard" never means "give up"; it means "know which lever you're pulling".
