When theory meets the clock: caches and memory

Big-O counts steps as if all memory were one flat pool at one price. Real machines serve memory through a hierarchy — L1 cache in ~1ns, main memory in ~100ns — so two algorithms with identical operation counts can differ by an order of magnitude on the clock. This page runs that experiment on your machine, right here, and then reconciles the result with everything unit 1 taught you.

Before you start Big-O (the model being stress-tested) and arrays vs linked lists (whose real-world verdict this page finally explains).

The idea

Memory arrives by the cache line — 64 bytes at a time. Touch one number and its seven neighbors arrive free; hardware prefetchers then notice sequential patterns and fetch ahead. So the same N accesses cost wildly different amounts depending on order: march straight through an array and almost every access is a cache hit; hop unpredictably and every access is a ~100ns miss. Big-O is not wrong — it predicts how cost scales, and a cache-hostile O(n) still beats a cache-friendly O(n²) eventually. But between two O(n) designs, memory layout is frequently the whole ballgame — and "eventually" can be further out than your actual n.

Honesty note

This is a real measurement of a real effect, but browsers are noisy laboratories: JIT warm-up, garbage collection and timer coarsening all wobble the numbers, which is why each benchmark runs a warm-up pass and reports a best-of-three. Expect the ratio to be stable and meaningful (typically 2–10× here; larger in lower-level languages) even when individual milliseconds bounce around.

Where you'll meet this

This effect is why unit 2's verdict on linked lists was so harsh — O(1) insertion loses to O(n) array shifting for realistic sizes once every list hop is a cache miss. It's why databases and column stores obsess over layout (unit 9's B-trees exist to match storage's block size; columnar formats exist so scans touch only needed bytes), why game engines rearranged themselves around data-oriented design (structure-of-arrays vs array-of-structures), why matrix code loops in row-major order, and why "we switched from a hash map to a sorted array and got 5× faster" is a real code-review story at small n: the hash map's O(1) hides pointer chases; the array's O(log n) rides cache lines.

The details (open as much as you like)

The numbers every engineer ends up memorizing

Rough, durable orders of magnitude: L1 hit ~1ns; L2 ~4ns; L3 ~10–30ns; main memory ~100ns; NVMe read ~100μs; datacenter network round trip ~500μs; spinning disk seek ~10ms. The gaps are the story: RAM is ~100× L1, disk is ~1000× RAM. An algorithm's "steps" can span five orders of magnitude in real cost depending on where its operands live — which is why unit 9's storage engines treat "reads from disk" as the only number worth optimizing, and why the external-memory model on the next-but-one page redefines cost as block transfers outright.

Reconciling with Big-O — the model didn't break

Formally, the flat-memory RAM model underlying unit 1 assumes uniform access cost; caches violate the assumption by a bounded constant (~100×), and Big-O absorbs constants — so every theorem in this course survives intact. What changes is engineering judgment inside a complexity class, where constants are the contest. There is also honest theory for the hierarchy itself: the external-memory model counts block transfers (B-trees are optimal there), and cache-oblivious algorithms achieve optimal transfers without knowing the cache's parameters — recursive divide-and-conquer layouts like unit 3's merge sort are naturally close to cache-oblivious, one more reason recursion earns its keep.

The code

// Both loops: exactly N additions of the same N numbers. Only ORDER differs.
function sumSequential(a) {
  let s = 0;
  for (let i = 0; i < a.length; i++) s += a[i];          // prefetcher heaven
  return s;
}
function sumStrided(a, stride) {   // stride coprime to length ⇒ visits every index once
  let s = 0, i = 0;
  for (let k = 0; k < a.length; k++) {
    s += a[i];
    i += stride; if (i >= a.length) i -= a.length;       // ~every access a miss
  }
  return s;
}
