Very big and very parallel

Two ways data outgrows this course's model: it stops fitting in memory, or one processor stops being enough. Both got their own theory, and both theories run on algorithms you already own — mostly unit 3's merge, wearing progressively heavier armor. This page is a guided tour, honestly narrated rather than fully built: the ideas transfer, even where a browser can't truthfully simulate a datacenter.

Before you start Merge sort (the hero of both halves), heaps (the k-way merge's engine) and the memory-hierarchy page (this is its logical conclusion).

The idea, half one: count block transfers, not steps

When data lives on disk, the expensive unit isn't an operation — it's a block transfer (last page's ratios, escalated: one disk read buys millions of CPU instructions). The external-memory model makes that official: memory holds M items, transfers move B at a time, and cost = number of transfers. The champion is external merge sort: read M-sized chunks, sort each in memory, write them back as sorted runs; then merge all runs in one pass with a heap of size k (one "current block" per run — unit 2's heap doing I/O triage). Every block is read once and written once per pass, and with realistic M/B even petabyte inputs need only a pass or two.

Honesty note

Nothing here touches a real disk — the demo counts simulated transfers, which is exactly what the external-memory model does too. That's the model's power and its caveat in one: it predicted B-trees and external sort decades before SSDs, but real systems also juggle caching layers, compression and parallel I/O that the clean model ignores.

The idea, half two: parallel — count work and span

With p processors, wall-clock cost splits into two numbers. Work: total operations (what one processor would do). Span: the longest chain of operations that must happen in order — the critical path no army of processors can compress. Merge sort again shows well: the two recursive halves are independent (run them in parallel!), giving Θ(n log n) work but only ~Θ(log³ n) span with a parallel merge — nearly all of it parallelizable. Contrast a running sum, where each step seems to need the previous one — span Θ(n)? — until the parallel prefix trick (unit 1's associativity, weaponized) computes partial sums up and down a tree in Θ(log n) span. And Amdahl's law keeps everyone honest: if fraction s of the job is inherently serial, no processor count beats 1/s speedup — 5% serial caps you at 20×, forever.

Where you'll meet this

External merge sort is inside every database's ORDER BY on big tables, every sort(1) on a large file, and unit 9's LSM compaction (which is external merging as a lifestyle). MapReduce/Spark are the parallel half industrialized — the shuffle between map and reduce is a distributed sort/group-by, which is why "big data" began as a sorting benchmark. GPU programming lives on parallel prefix (scan) the way CPUs live on loops. And your build system's dependency graph (unit 9 again) has a critical path — that's span, and it's why 16 more CI runners stopped helping after the third one.

The details (open as much as you like)

The external-memory arithmetic, and where B-trees fit

Sorting N items costs Θ((N/B) · logM/B(N/B)) transfers — read "number of blocks, times a logarithm whose base is how many runs fit in memory". The base is the quiet monster: with 1 GB of memory and 1 MB blocks, M/B ≈ 1000, so each pass multiplies manageable size by a thousand — one merge pass handles a terabyte, two handle an exabyte. This is also unit 9's B-tree story retold: branching factor B turns log₂ into logB, collapsing tree height to 3–4 disk reads. Same logarithm-base lever, pulled by storage instead of search.

MapReduce in this course's vocabulary

Map: apply a function to every record, emitting (key, value) pairs — embarrassingly parallel, zero span cost. Shuffle: route all pairs with equal keys to the same machine — a distributed bucket sort (unit 3's counting/bucket ideas at warehouse scale), and the expensive part, since it's all network I/O. Reduce: fold each key's values — parallel across keys. Word-count, joins, inverted-index building and PageRank iterations all fit the template. Its limitation is span in disguise: iterative algorithms (graph traversals!) pay a full shuffle per round, which is why later systems (Spark, Pregel-style engines) keep state in memory between rounds. The lesson transfers whole: decompose into independent pieces, pay for the coordination, respect the critical path.

The code

// The k-way merge at the heart of external sorting — heap of "next item per run".
function* kWayMerge(runs, B) {                  // runs: arrays on "disk", B: block size
  const buf = runs.map(() => []), at = runs.map(() => 0);
  let out = [], transfers = 0;
  const refill = (i) => {                       // one BLOCK READ — the priced unit
    buf[i] = runs[i].slice(at[i], at[i] + B); at[i] += B; transfers++;
  };
  runs.forEach((_, i) => refill(i));
  const heap = /* min-heap of [buf[i][0], i] — unit 2 verbatim */ makeHeap(runs, buf);
  while (heap.size()) {
    const [v, i] = heap.pop();                  // comparisons: free in this model
    out.push(v);
    buf[i].shift();
    if (!buf[i].length && at[i] < runs[i].length) refill(i);
    if (buf[i].length) heap.push([buf[i][0], i]);
    if (out.length === B) { transfers++; out = []; }   // one BLOCK WRITE
  }
}
