DP beyond tables: subtrees and subsets

The recipe never said "table". A subproblem can be anything with a well-founded ordering: prefixes, budgets — or subtrees of a tree, or subsets encoded as bits. Two short case studies stretch the DP muscle onto the shapes production data actually has.

Before you start The recipe, DFS (tree DP rides on it), and bits as sets (that page can be read later; the idea is one sentence here).

The idea: DP on trees

The showcase: maximum independent set on a tree — pick nodes of maximum total value such that no two picked nodes are adjacent. (Folklore version: invite employees to a party, nobody with their direct manager, maximize fun.) On general graphs this is NP-hard; on trees, DP kills it in linear time, because subtrees only talk to each other through one node — their root.

The sentence — two per node this time: incl(v) = best for v's subtree if v IS picked; excl(v) = best if v is NOT picked. Recurrence, computed by DFS on the way back up: incl(v) = value(v) + Σ excl(child) — picking v bans its children; excl(v) = Σ max(incl(child), excl(child)) — a free choice per child. Answer: max at the root. Post-order position IS the dependency order, so "fill order" comes free from unit 4's DFS.

The idea: DP on bitmask subsets

When subproblems are "which subset of these k things have I already handled", encode the subset as k bits of an integer: subset {0, 2} = binary 101 = 5. Now an array indexed 0…2ᵏ−1 memoizes every subset. The famous instance is Held-Karp for the traveling salesman: best[S][j] = shortest route that visits exactly the cities in S, ending at j. Recurrence: arrive at j from some i ∈ S: best[S][j] = min over i of best[S∖{j}][i] + dist(i, j). O(2ᵏ·k²) — exponential, but a disciplined exponential: 2²⁰·400 ≈ 4×10⁸ beats brute-force 20! ≈ 2×10¹⁸ by ten orders of magnitude. Bitmask DP is how "impossible" problems get exact answers at k ≤ ~22.

Where you'll meet this

Tree DP runs on real trees: file-system quota rollups, org-chart aggregations, AST cost analysis in compilers and query optimizers (join-order planning is tree/bitmask DP inside every serious database — PostgreSQL literally switches from DP to a genetic heuristic above a join-count threshold). Bitmask DP ships in route optimization for small fleets, register allocation, and feature-flag interaction testing. The meta-lesson for architects: the same problem can be NP-hard in general and linear on your data's shape — "our dependency graph is a tree" is a performance fact worth protecting.

Why trees make hard problems easy — separators

The independent-set recurrence worked because removing one node (the subtree root) fully disconnects a subtree from the rest — the root is a separator of size 1, so the DP state needs only "is the root in or out": two numbers per subtree. General graphs have no small separators, so a subproblem would need to remember the pick-status of a whole frontier — exponentially many states. This is the actual boundary between "DP applies" and "NP-hard": not problem names, but how much boundary information subproblems must carry. (The generalization — treewidth, DP on "almost-tree" graphs — is the parameterized-complexity rabbit hole, flagged in further reading.)

The code

// Tree DP — the demo's exact code (inline on this page), events elided:
function solve(v) {                    // returns [incl, excl] for v's subtree
  let incl = v.value, excl = 0;
  for (const child of v.children) {
    const [ci, ce] = solve(child);     // post-order: children settle first
    incl += ce;                        // picking v bans each child
    excl += Math.max(ci, ce);          // not picking v: best of both per child
  }
  return [incl, excl];
}

// Bitmask DP skeleton (Held-Karp inner loop):
for (let S = 1; S < (1 << k); S++)            // subsets in increasing order
  for (let j = 0; j < k; j++) if (S & (1 << j))
    for (let i = 0; i < k; i++) if (i !== j && (S & (1 << i)))
      best[S][j] = Math.min(best[S][j],
        best[S ^ (1 << j)][i] + dist[i][j]);  // S∖{j}: one bit flipped off
