Knapsack: optimizing under a budget

Items with weights and values, a capacity, take-it-or- leave-it choices: the canonical resource-allocation problem, and DP's most-reused table. It also carries the course's most instructive asterisk — an algorithm that looks polynomial, is technically exponential, and taught complexity theory a new word.

Before you start The DP recipe and 2-D tables. The greedy page's warning gets its sharpest example here.

The idea

Greedy fails first, instructively: taking by best value-per-weight ratio is beaten by a capacity-5 example — item A (w2, v3), B (w3, v4), C (w4, v5). Ratios say take C (1.25/kg) then nothing else fits: value 5. Optimal is A+B: value 7. Density greed can't see that two mediocre items compose better than one good one.

The DP sentence: best[i][c] = the most value achievable using only the first i items within capacity c. Each item poses one binary question — skip it (inherit best[i−1][c]) or take it (its value plus best[i−1][c−wᵢ], the best the earlier items manage in the space that remains):

best[i][c] = \max\big(best[i{-}1][c],\; v_i + best[i{-}1][c - w_i]\big)

n·W cells, O(1) each: O(nW). Traceback (did the value change from the row above?) names the chosen items.

Where you'll meet this

Budgeted selection is everywhere once you see the shape: cloud cost optimization (which workloads fit the reserved-instance budget), cargo and bin planning, ad-slot allocation, feature selection under a latency budget, portfolio construction. In LLM systems it's the context-window packing problem: retrieved chunks have token costs and relevance scores, the window is the knapsack — RAG pipelines solve (usually greedily, now you know the caveat) exactly this. Cutting-stock and scheduling variants run manufacturing. Cryptographers even built (broken) cryptosystems on its hardness.

The details (open as much as you like)

The asterisk — "pseudo-polynomial", honestly

O(nW) looks polynomial. It isn't. Complexity is measured against input size in bits, and the number W occupies only log₂ W bits — so W itself is exponential in its own description length. Capacity 1,000,000 is seven characters of input but a million table columns. Algorithms polynomial in the numeric value but exponential in the bit-length are pseudo-polynomial. Practical consequences: knapsack DP is superb when W is human-scale (budgets in dollars, weights in kilograms, tokens in a context window) and useless when W is a cryptographic-scale number. Knapsack is NP-complete (unit 11) with a pseudo-polynomial escape hatch — "NP-complete" and "solvable in practice" coexist, a nuance worth carrying into any hardness conversation.

The family: unbounded, subset-sum, and the 1-D space trick

Unbounded knapsack (unlimited copies per item): same recurrence but "take" stays on row i — best[i][c−wᵢ] — because taking doesn't use the item up. Subset-sum ("can these numbers hit total T exactly?"): knapsack with values dropped and max replaced by OR — the reduction workhorse of unit 11. Space: like edit distance, only the previous row is read, so one array suffices — with a trap: iterate capacity downward for 0/1 (so this row's takes can't cascade), upward for unbounded (so they deliberately can). A direction bug silently converts one problem into the other — a genuinely common wild bug, and a nice interview tell.

The code

// The demo's exact code (assets/js/algo/dp.js), events elided:
function knapsack(items, W) {
  const d = table(items.length + 1, W + 1, 0);
  for (let i = 1; i <= items.length; i++) {
    const { w, v } = items[i - 1];
    for (let c = 0; c <= W; c++) {
      d[i][c] = d[i - 1][c];                     // skip item i
      if (w <= c) d[i][c] = Math.max(d[i][c],
        d[i - 1][c - w] + v);                    // take it: value + best fit
    }                                            //   of the OTHERS in what's left
  }
  return d[items.length][W];   // traceback: rows where the value changed
}
