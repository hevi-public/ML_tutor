Unit 6 · Design strategies

Backtracking: brute force with manners

When no recurrence collapses the problem and no greedy key is safe, you search: build a solution one choice at a time, and the instant a partial solution becomes indefensible, undo the last choice and try the next — abandoning the entire subtree of futures that hung off it. The move is called pruning, and it's the difference between "finishes before the heat death" and not.

Before you start DFS — backtracking IS depth-first search over the implicit tree of partial solutions (states as nodes, one more payoff).

The idea

The classic: N-Queens — place N queens on an N×N board, none attacking another. Brute force over all placements of 6 queens on 36 squares is ~2 million boards. Backtracking reframes: place one queen per row, and after each placement check immediately — same column as an earlier queen? same diagonal? If yes, don't descend: every board extending this prefix is already dead, so the whole branch is skipped unexplored. The counters in the demo tell the story: solving 6-Queens visits a few hundred placements, not millions.

The general template is three verbs: choose (extend the partial solution), check (still viable? if not, skip), unchoose (undo on the way out — state must be restored exactly, the classic source of backtracking bugs). Recursion handles the rest, because the call stack IS the partial solution's history.

Where you'll meet this

SAT solvers — the engines inside package-dependency resolvers (Cargo, pip's resolver, apt), hardware verification, and config validators — are industrial backtracking (DPLL/CDCL: choose a variable, propagate, backtrack on conflict, learn the conflict so it prunes forever after). Regex engines backtrack (catastrophically, on evil patterns — that's what ReDoS is). Query planners, puzzle generators, layout solvers, type inference — constraint problems everywhere. And an LLM agent retrying a failed tool-call plan by revising its last step is running choose/check/unchoose over an implicit plan tree — with an unreliable checker, which is why loops need budgets.

Pruning arithmetic — why early checks dominate

A prune at depth d kills the entire subtree below it — roughly b^(N−d) nodes for branching factor b. Pruning one row earlier is therefore worth a factor of b, which compounds: the demo's few hundred visits versus ~2 million brute-force boards is entirely early rejection. This is also why variable ordering is the big lever in real solvers: choosing the most-constrained thing next ("fail first") moves contradictions toward the root, where discovering them is exponentially cheaper. Same principle as putting the cheapest, most-likely-to-fail validation first in a request pipeline.

Backtracking vs DP vs branch-and-bound

DP requires overlapping subproblems worth caching; backtracking assumes each path is essentially unique (or the state too big to memoize — remember the frontier argument from the tree-DP page). Branch-and-bound is backtracking for optimization: keep the best complete solution so far, and prune any partial solution whose optimistic bound (an admissible estimate — A*'s idea again) can't beat it. TSP exact solvers, integer-programming solvers (CPLEX/Gurobi), and query optimizers all run this. The strategies unit closes the loop: greedy = one path, DP = all distinct subproblems once, backtracking = all paths minus the provably doomed, branch-and-bound = minus the provably non-optimal too.

The code

// The demo's exact code (assets/js/algo/dp.js), events elided:
function place(row) {
  if (row === n) { report(cols); return; }        // a full, valid board
  for (let c = 0; c < n; c++) {
    const ok = cols.every((qc, qr) =>             // check BEFORE descending:
      qc !== c && Math.abs(qc - c) !== row - qr); //   column & diagonal attacks
    if (!ok) continue;                            // prune: subtree never built
    cols.push(c);                                 // choose
    place(row + 1);                               // explore
    cols.pop();                                   // unchoose — restore exactly
  }
}
