Unit 6 · Design strategies

Choosing a strategy: what kind of problem is this?

Units 2–5 handed you algorithms. This unit hands you the thing above algorithms: the four or five recurring shapes of attack that generate them, and — the actually hard skill — how to read a fresh problem and guess which shape it wants. Senior engineers usually know the algorithms; what the missed CS years mostly cost is this taxonomy.

Before you start Units 1–5 in spirit — this page names patterns you've already met and tells you where each one is headed.

The idea

Nearly every algorithm in this course is an instance of one of these strategies, distinguished by how much of the decision space they explore:

  • Divide & conquer — split into independent subproblems, solve, recombine. You've done it: merge sort, quicksort, binary search. Signature: subproblems don't overlap.
  • Greedy — one pass, best local choice each step, never look back. Dijkstra's settle, Kruskal's cheapest edge, Huffman. Explores exactly one path through decision space — only legal when a proof says the local best can't lock you out of the global best.
  • Dynamic programming — the subproblems overlap, so solve each once, store it, reuse it. Floyd-Warshall was your first; this unit builds the discipline. Explores the whole space, but pays only once per distinct subproblem.
  • Backtracking / exhaustive search — walk the tree of partial solutions, abandon branches the moment they're provably doomed. The honest strategy when nothing smarter is known — and for the NP-complete crowd (unit 11), often nothing smarter is.
  • Reduce to a solved problem — reshape yours into one with a known algorithm: matching became max flow, arbitrage became negative cycles. Always the first thing to try.

The decision questions

Interrogate the problem in this order — each yes narrows the field:

  1. Does it smell like something solved? Shortest path, matching, connectivity, sorting-shaped? → reduce and stop. (Most production "algorithm problems" end here.)
  2. Do subproblems overlap? Would naive recursion re-solve the same smaller instance many times? → DP. If they don't overlap → divide & conquer.
  3. Is there an ordering that makes commitments safe? Sort by some key so that taking the best-now provably never hurts? → greedy, but demand the exchange argument before you trust it.
  4. Is the answer a combinatorial needle? Constraints to satisfy, exponential haystack, no structure above? → backtracking with aggressive pruning — and check unit 11 for whether the problem is NP-hard before promising a deadline.
Where you'll meet this

This taxonomy is a code-review instrument. "This retry logic recomputes the same subresult exponentially" → memoize (DP). "This scheduler commits to the biggest job first with no proof" → greedy without a license, the classic production bug. "This search has no pruning" → backtracking done naive. And in the LLM stack: beam search is greedy-with-a-budget over generation; agent planners that re-derive identical sub-plans need exactly the memoization instinct; and knowing a subtask is NP-hard is what stops a team from promising an exact optimizer by Friday.

The details (open as much as you like)

The same problem, four ways — coin change

Make 63¢ with the fewest coins. Greedy (largest first): works for US denominations {25, 10, 5, 1} — 25+25+10+1+1+1 — and this is provable. Change the coins to {25, 21, 10, 5, 1} and greedy gives six coins for 63 while 21+21+21 uses three: greed's license depends on the data, not just the problem. DP: best[n] = 1 + min over coins c of best[n−c] — always correct, O(amount·coins). Backtracking: try every combination, prune when over — correct, exponential. Reduction: it's shortest path on a graph where states are amounts and coins are edges — BFS if you squint. One problem, four costs, one lesson: strategy choice is a claim about structure, and wrong claims produce wrong answers or wrong bills.
