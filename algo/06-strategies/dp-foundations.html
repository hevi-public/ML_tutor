Unit 6 · Design strategies

Dynamic programming: stop solving the same problem twice

The most feared name in algorithms, for what is ultimately a caching discipline. When a recursion keeps re-deriving the same subanswers, store them — and an exponential computation collapses to the count of distinct subproblems. The two demos on this page are the entire argument.

Before you start Recursion and its call stack. You've already run one industrial-strength DP: Floyd-Warshall.

The idea

Fibonacci, the drosophila of DP: fib(n) = fib(n−1) + fib(n−2). Code the definition directly and fib(7) spawns a tree of 41 calls — fib(3) alone is computed five times, each recomputation spawning its own subtree. Run time: exponential, ~φⁿ.

But there are only eight distinct questions being asked: fib(0) through fib(7). Cache each answer the first time (memoization) and every later request is a lookup — 13 calls and 5 instant hits, against the naive 41. Same code plus a Map: exponential → linear. DP in one sentence: cost collapses from "number of calls in the naive tree" to "number of distinct subproblems", provided answers are reusable.

Two prerequisites make a problem DP-able. Overlapping subproblems — the naive tree repeats itself (merge sort's doesn't; fib's does). Optimal substructure — the best answer to the whole is assembled from best answers to parts (shortest paths have it; longest simple paths famously don't, because parts interact through the no-repeats rule).

Where you'll meet this

Every place a computation graph has shared nodes: build systems caching artifacts (Bazel's action cache is memoization with a content hash), React/Vue memoized renders, spreadsheet recalculation, functools.lru_cache on that one slow function. Diff algorithms (git, React reconciliation) are edit-distance DP — next page. In the LLM stack, the KV-cache is memoization verbatim: attention keys/values for a prefix are computed once and reused for every subsequent token — without it, generation would be quadratic per token. Prompt caching: same idea, one level up.

The details (open as much as you like)

Memoization (top-down) vs tabulation (bottom-up)

Two dialects, one discipline. Top-down: write the recursion, add a cache — the demo above. Pros: only reachable subproblems get computed; the code mirrors the math. Cons: recursion depth, per-call overhead. Bottom-up: figure out dependency order and fill a table with a loop — for i: f[i] = f[i-1] + f[i-2]. Pros: no stack, often cache-friendly, enables space tricks (fib needs only the last two cells — O(1) space). Cons: you must know the fill order (it's a topological sort of the subproblem DAG — unit 4 pays rent again). Floyd-Warshall's "k must be outermost" was exactly a fill-order constraint. Interviews prefer bottom-up tables; production code usually starts top-down because it's harder to get wrong.

The 4-step recipe (used on every DP page that follows)

1. Define the subproblem in words — "best[i] = the best answer using only the first i items". The sentence is the hard part; everything else is transcription. 2. Write the recurrence — best[i] in terms of strictly smaller subproblems, with base cases. 3. Count — distinct subproblems × work per subproblem = the complexity, before writing code. 4. Order or memoize — fill bottom-up in dependency order, or recurse with a cache. A useful check on step 1: if you can't say what table cell (i, j) means in one sentence, the design isn't done — a rule that catches most wrong DP attempts before any code exists.

The code

// The demos' exact code (assets/js/algo/dp.js), events elided:
function fibNaive(n) {
  if (n <= 1) return n;
  return fibNaive(n - 1) + fibNaive(n - 2);   // recomputes everything, ~φⁿ
}

function fibMemo(n, memo = new Map()) {
  if (memo.has(n)) return memo.get(n);        // the hit — O(1), no subtree
  const result = n <= 1 ? n
    : fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
  memo.set(n, result);                        // pay once per DISTINCT n
  return result;                              // exponential → O(n)
}
