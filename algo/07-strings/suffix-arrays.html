Suffix arrays: index once, search forever

Flip the unit's question. Instead of scanning a text per query, spend effort once building an index that answers every future substring query in logarithmic time. The index is almost embarrassingly simple: the text's suffixes, sorted. Everything else is consequences.

Before you start Binary search does the querying; tries explain the family resemblance (a suffix array is a flattened suffix trie).

The idea

Key fact: every substring of a text is a prefix of some suffix. nan occurs in banana because nan… starts the suffix at index 2. So: list all n suffixes, sort them lexicographically, store only their starting indexes — that integer list is the suffix array. Now any pattern's occurrences form one contiguous run in the sorted order (everything starting with an sorts together), and binary search finds the run in O(m \log n) comparisons. The text stays untouched; the index is n integers.

Where you'll meet this

Genome browsers and read aligners (BWA — the B is for Burrows-Wheeler, the suffix array's compressed sibling) index 3-billion-character genomes for instant substring lookup; bioinformatics could not exist on per-query scanning. Full-text search of code (early Google Code Search famously ran on suffix arrays), plagiarism detection, and data-compression analysis (the longest-repeated-substring question) all live here. The Burrows-Wheeler transform inside bzip2 IS a suffix sort. And LCP analysis over corpus suffixes is one way training pipelines hunt duplicated passages before they hit the model.

The details (open as much as you like)

Construction cost — the honest ladder

This demo sorts suffixes with plain string comparison: O(n² log n) worst case — fine for a banana, hopeless for a genome. The classic fix is prefix doubling: rank all suffixes by their first character, then use those ranks to sort by the first 2, then 4, then 8… — each doubling is a sort of integer pairs (rank of first half, rank of second half), so O(n log n) overall, log n rounds. Linear-time constructions exist (SA-IS is the modern standard, and is what real libraries ship). The ladder — naive, doubling, SA-IS — is a nice case study in how far an index that "is just sorting" can be engineered when n is three billion.

The LCP array — the index's second half

Store alongside: LCP[k] = the length of the longest common prefix between the k-th and (k−1)-th suffixes in sorted order. For banana's order [5 a, 3 ana, 1 anana, 0 banana, 4 na, 2 nana], LCP = [—, 1, 3, 0, 0, 2]. With it: the longest repeated substring is just max(LCP) (ana, length 3 — note the two occurrences overlap!); counting distinct substrings, document similarity, and faster binary search all become array arithmetic. Kasai's algorithm builds LCP in O(n) from the suffix array — the pair together are "the poor man's suffix tree": nearly all of that structure's power, a fraction of its memory and code.

The code

// Build (teaching version — see the layer for the real ladder):
const sa = Array.from({ length: n }, (_, i) => i)
  .sort((a, b) => text.slice(a) < text.slice(b) ? -1 : 1);

// Query: binary search for the run of suffixes starting with `pat`
function lowerBound(pat) {
  let lo = 0, hi = n;
  while (lo < hi) {                       // unit 3's loop, verbatim
    const mid = (lo + hi) >> 1;
    if (text.slice(sa[mid], sa[mid] + pat.length) < pat) lo = mid + 1;
    else hi = mid;
  }
  return lo;      // first suffix ≥ pat; a matching run starts here (if any)
}
