Rabin-Karp: compare fingerprints, not characters

A different escape from re-comparison: reduce each m-character window to one number — a hash — and compare numbers instead. The trick that makes it viable is the rolling update: slide the window one character and refresh its hash in O(1), no re-reading. That one primitive outgrew string search entirely; it's in your sync tools, your dedup storage, and your git hosting.

Before you start Hashing (what collisions are and why they're inevitable) and the naive baseline.

The idea

Treat a window of m characters as an m-digit number in base B, taken modulo a large prime: h = (c_0 B^{m-1} + c_1 B^{m-2} + \dots + c_{m-1}) \bmod p. In plain English: the window's characters, read as one big number, squashed to fixed size. Hash the pattern once; slide over the text comparing hashes. Equal hashes don't prove a match (collisions exist — spurious hits), so verify by direct comparison; unequal hashes do prove a non-match, and that's the common case, dismissed in O(1).

The rolling step: dropping the left character and adding one on the right is arithmetic — subtract c₀·Bᵐ⁻¹, multiply by B, add the newcomer, all mod p. Expected time O(n + m); worst case O(n·m) only if collisions pile up, which random-looking hashes make vanishingly rare (and an adversary-resistant variant just randomizes p or B at startup).

Where you'll meet this

The rolling hash is the star. rsync finds which file blocks changed by rolling a checksum over the receiver's copy; content-defined chunking in dedup storage and backup tools (restic, borg) cuts files where the rolling hash hits a magic value, so an insert early in a file doesn't reshuffle every chunk boundary; git's packfile delta engine hunts matching slices the same way. Plagiarism/similarity detection (MOSS) fingerprints documents with rolling k-gram hashes — the same n-gram shingling that dedups LLM training corpora. Multi-pattern search gets it too: hash all k patterns into a set, roll once over the text.

The details (open as much as you like)

Spurious hits, and how rare "rare" is

With a prime p and decently mixing base, two unequal windows collide with probability about 1/p. For p ≈ 10⁶ and a million windows, expect roughly one spurious verify per run — each costing O(m) and finding out. Expected total: O(n + m + (spurious)·m) ≈ O(n + m). Two footnotes worth engineering respect: (1) if the inputs are adversarial, fixed constants can be attacked — randomize them per process (this is precisely why language runtimes randomized their string-hash seeds after the 2011 hash-flooding DoS); (2) if you skip verification entirely — trusting the hash — you've traded correctness for speed; sometimes right (dedup with SHA-256-sized hashes), sometimes a data-loss story.

The code

// The demo's exact code (assets/js/algo/strings.js), events elided:
function rabinKarp(text, pat) {
  const m = pat.length;
  let ph = hash(pat), th = hash(text.slice(0, m));
  const pow = B ** (m - 1) % MOD;                 // precomputed top-digit weight
  const hits = [];
  for (let s = 0; s + m <= text.length; s++) {
    if (th === ph && verify(text, s, pat)) hits.push(s);  // hash hit → confirm
    if (s + m < text.length) {                    // ROLL in O(1):
      th = (th - text.charCodeAt(s) * pow) mod;   //   drop the left char
      th = (th * B + text.charCodeAt(s + m)) mod; //   shift, add the right char
    }
  }
  return hits;
}
