Tries: the dictionary that shares its prefixes

Store words as paths in a tree — one character per edge — and words sharing a prefix share a path. Lookup costs the word's length, independent of how many words are stored, and the structure answers a question hash tables can't touch: "what starts with car?" — the query behind every autocomplete box.

Before you start Hash tables — the rival to beat on the prefix question — and trees generally.

The idea

The root is the empty string; each edge adds a character; a node is marked when the path spelling it is a stored word. Insert = walk the word's characters, creating nodes as needed; lookup = the same walk without creating. Both O(word length) — not O(dictionary size). The prefix superpower falls out structurally: everything starting with car lives in the subtree under the c-a-r path, so autocomplete is "walk the prefix, then enumerate the subtree" — impossible for a hash table, whose scattering of keys is the exact opposite of prefix locality.

The cost is per-node child pointers — naive arrays of alphabet size burn memory, so real tries use child maps, or compress single-child chains into multi-character edges (radix/Patricia trees), the variant production systems actually run.

Where you'll meet this

Autocomplete and typeahead everywhere; IP routing tables — longest- prefix match over bit-tries is how routers pick next hops (Patricia tries were born for this); spell-checkers and word games; the inverted-index term dictionaries inside search engines (often as FSTs — tries with shared suffixes too). In the LLM stack: tokenizer vocabularies are trie-shaped — encoding walks the trie for the longest known token at each position (unit 9's tokenizer page runs on this idea), and constrained/guided decoding walks a trie of allowed continuations to force valid JSON or grammar. Aho-Corasick (KMP's failure links grafted onto a trie) scans for thousands of patterns at once in moderation pipelines.

The details (open as much as you like)

Trie vs hash table — the honest matchup

Exact lookup: both O(word length) in practice (the hash also reads every character to hash it) — the hash table usually wins on constants and memory locality. Prefix queries, ordered iteration, longest-prefix match: trie only. Memory: naive tries lose badly (a node per character, pointer-heavy); radix compression, alphabet reduction (bit-tries), and array-packed layouts (double-array tries, FSTs) close the gap and then some — a production FST can be smaller than the sorted word list itself. Rule of thumb: hash for "is this exact key present", trie family the moment the word "prefix" appears in the requirements.

const trieNode = () => ({ children: {}, word: false });

function insert(root, word) {
  let node = root;
  for (const ch of word) {
    if (!node.children[ch]) node.children[ch] = trieNode();  // extend path
    node = node.children[ch];              // shared prefixes walk, not build
  }
  node.word = true;                        // mark "a word ends here"
}

function completions(root, prefix) {
  let node = root;
  for (const ch of prefix) {
    if (!node.children[ch]) return [];     // nothing starts with this
    node = node.children[ch];
  }
  return collect(node, prefix);            // everything below = the answers
}
