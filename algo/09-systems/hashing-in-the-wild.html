Hashing in the wild: sharding and throttling the internet

Two more places the humble hash function quietly runs everything. Spreading data across servers sounds like hash(key) % N — until a server joins and that innocent modulo reshuffles nearly everything you stored. And letting a million clients each make "a reasonable number" of requests is an algorithm too — a beautiful O(1) one.

Before you start Hash tables — this page is what happens when the "table" is a fleet of machines.

The idea: consistent hashing

The modulo disaster, concretely: with hash(k) % 4, adding a fifth server changes the answer for ~80% of keys — a self-inflicted stampede of cache misses and data migration. Consistent hashing re-frames placement as geometry: hash both servers and keys onto a circle (0…2³²); each key belongs to the first server clockwise from it. Add a server and it captures only the arc between itself and its predecessor — K/N of the keys move, the theoretical minimum; everything else is untouched. Because a few random points slice the circle unevenly, each real server gets ~100–200 virtual nodes (multiple ring positions), which evens the arcs and lets bigger machines take more of them.

The idea: token-bucket rate limiting

Give each client a bucket holding at most burst tokens, refilled at rate tokens/second; a request spends one, an empty bucket means 429. The elegance is the implementation: no timer, no queue — store just (tokens, lastSeen) and compute the refill lazily on each request from the elapsed time. O(1) time and memory per client, allows honest bursts, enforces the long-run average. It's the algorithm behind almost every API limit you've hit, including per-token LLM quotas.

Where you'll meet this

Consistent hashing: memcached/Redis client sharding (its original 1997 use case at Akamai), Cassandra/DynamoDB partition rings, Kafka consumer assignment, load balancers with session affinity, and sharding vector indexes or KV-cache state across inference servers — "which GPU owns this session?" is a ring lookup. Token buckets: nginx/Envoy limiters, every cloud API quota, LLM tokens-per-minute budgets (a bucket where the spend per request is the token count — same math), and client-side backoff logic negotiating with all of the above. Both compose: the rate limiter for a sharded service often lives per-shard, placed by the ring.

Virtual nodes, hot shards, and rendezvous hashing

Virtual nodes fix arc-size variance but not key skew — if one tenant is 40% of traffic, its shard is hot no matter the geometry (fixes: split the hot key's keyspace, or cache it in front). Worth knowing: rendezvous hashing — for each key, score every server with hash(key, server) and pick the max — achieves the same minimal-movement property with no ring at all, and is often simpler when N is small. And jump consistent hash (a 5-line integer trick) places keys with zero memory for fixed-size fleets. The shared principle: make placement a pure function of (key, current fleet) with the property that fleet changes perturb few outputs — "minimal disruption" as an explicit algorithmic goal.

The code

// Token bucket — the whole limiter, O(1) per request, no timers:
function allow(client, now) {
  const b = buckets.get(client) || { tokens: BURST, last: now };
  b.tokens = Math.min(BURST, b.tokens + (now - b.last) * RATE);  // lazy refill
  b.last = now;
  if (b.tokens < 1) { buckets.set(client, b); return false; }    // 429
  b.tokens -= 1;
  buckets.set(client, b);
  return true;
}

// Consistent hashing lookup — binary search on the ring (unit 3!):
function ownerOf(key) {

}
