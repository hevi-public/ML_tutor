Tokenizers: how text becomes what models read

Every prompt you have ever sent was first chopped into tokens — subword pieces from a fixed vocabulary. The algorithm that learned that vocabulary is greedy compression (Huffman's cousin); the one that applies it is a merge loop you can watch. Token counts are billed, context windows are measured in them, and more model quirks than you'd expect trace back to this page.

Before you start Huffman ("frequent things should be cheap to say") and tries (the vocabulary's natural index).

The idea

Byte-pair encoding (BPE), the dominant scheme (GPT-family, Llama-family): start with single characters (bytes, in practice) as the vocabulary. Count all adjacent pairs in the training corpus; merge the most frequent pair into a new vocabulary entry; repeat until the vocabulary hits its budget (~50k–200k entries). Frequent words end up as single tokens, rare words as several pieces, arbitrary garbage as many bytes — graceful degradation with no out-of-vocabulary failures ever.

Note the inversion of Huffman: Huffman keeps symbols fixed and assigns frequent ones short codes; BPE keeps the "code" fixed (one token = one ID) and makes frequent strings into single symbols. Same force — spend representation on what occurs often — pointed at the vocabulary instead of the bits. Encoding new text then replays the learned merges in order (or equivalently, greedily matches the longest vocabulary entry at each position — a trie walk, which is how fast implementations do it).

Where you'll meet this

Everything LLM: billing (tokens are the meter), context limits (8k/128k/1M are token counts), speed (generation is per-token), and a bestiary of quirks — models miscounting letters in "strawberry" (the letters aren't visible; tokens are), arithmetic stumbling when digits group oddly, code models favoring certain indentation (whitespace tokenization), multilingual cost differences (languages poorly covered by the vocabulary pay 2–4× more tokens for the same meaning). Variants: WordPiece (BERT — merge by likelihood, not raw count), Unigram/SentencePiece (T5, Llama — start big, prune). And the trie connection is production-real: fast tokenizers compile the vocabulary into an automaton; constrained decoding walks a trie of legal continuations to force valid JSON.

The details (open as much as you like)

Why subwords at all — the vocabulary trilemma

Characters only: no out-of-vocabulary problem, but sequences get long (attention cost grows with length — quadratically in classic transformers) and each symbol carries little meaning. Whole words: short meaningful sequences, but an unbounded vocabulary, embedding tables in the billions, and instant failure on any new word, name or typo. Subwords are the engineered middle: bounded vocabulary, no OOV (worst case: bytes), frequent words still one token. The budget knob (~50k–200k) trades embedding- table memory against sequence length — an honest-to-goodness space/time trade-off, priced in GPU memory and attention FLOPs. Compression view: BPE is a dictionary coder (LZ-family kin), and "tokens per byte" is literally a compression ratio — which is why tokenizer quality is measured in exactly those units.

The code

// The demo's exact training loop, events elided:
function trainBPE(words, rounds) {
  let seqs = words.map((w) => w.split(""));        // start: characters
  const merges = [];
  for (let r = 0; r < rounds; r++) {
    const pairCount = new Map();                    // count adjacent pairs
    for (const s of seqs)
      for (let i = 0; i + 1 < s.length; i++)
        bump(pairCount, s[i] + " " + s[i + 1]);
    const best = argmax(pairCount);                 // most frequent pair
    if (!best) break;
    merges.push(best);                              // vocabulary grows by 1
    seqs = seqs.map((s) => applyMerge(s, best));    // replace pair everywhere
  }
  return merges;   // encoding new text = replay these merges in order
}
