Caching: remembering is cheaper than recomputing

Unit 6 taught memoization with an unlimited cache. Real memory is finite, so caching's actual algorithmic content is the eviction policy: when full and something new arrives, who leaves? The answer decides your hit rate, and hit rate decides whether your database melts and your LLM bill doubles.

Before you start Hash tables (the lookup half of every cache) and memoization (the unlimited-memory special case).

The idea

The oracle policy is Bélády's: evict the entry whose next use is farthest in the future — provably optimal, impossible to run (it needs tomorrow's requests), invaluable as the yardstick your real policy is benchmarked against. Practical policies bet on patterns: LRU (evict least-recently-used) bets on temporal locality — what was touched recently will be touched again. Its classic implementation is a course reunion: hash table for O(1) lookup + doubly-linked list for O(1) recency reordering, glued so each hash entry points at its list node. LFU bets on frequency; FIFO/CLOCK approximate LRU cheaper. Modern engines (ARC, TinyLFU in Caffeine) blend recency and frequency because each pure bet has a famous failure.

Where you'll meet this

Redis/Memcached in front of every hot database; CDN edges; CPU caches (hardware LRU approximations — unit 11's cache-and-memory page measures them); the page cache under your filesystem; HTTP caching headers. The LLM stack is cache-stacked: the KV-cache (per-request memoization of attention state — evicting it mid-conversation is why long chats slow or truncate), prompt caching (persisting KV state for a shared prefix across requests — system prompts priced cheaper for exactly this reason), and semantic caching (vector-search this unit's earlier page — over past queries: serve a cached answer when a new question embeds near an old one, an approximate cache with approximate correctness worth naming honestly). Eviction there is literally dollars.

The details (open as much as you like)

Every policy has an adversary

LRU dies on scans: looping over N+1 items with capacity N evicts each entry just before its reuse — 0% hits where random eviction would do better (the demo's second phase shows the shape). LFU dies on drift: yesterday's hot keys hoard frequency counts and squat while today's rising keys can't get established (aged/windowed counts are the fix; TinyLFU is this idea productionized). FIFO ignores popularity entirely. This is why serious caches are hybrids, and why the honest procedure is unit 1's: replay YOUR trace against candidate policies and against Bélády's oracle, and read the hit rates — the gap to the oracle tells you whether policy tuning is even worth it, or the cache is simply too small for the working set.

The code

// The classic O(1) LRU — hash table + doubly-linked recency list.
// (JS Maps iterate in insertion order, which makes them a compact LRU.)
class LRU {
  constructor(cap) { this.cap = cap; this.map = new Map(); }
  get(k) {
    if (!this.map.has(k)) return undefined;          // miss
    const v = this.map.get(k);
    this.map.delete(k); this.map.set(k, v);          // re-insert = most recent
    return v;                                        // hit, O(1)
  }
  set(k, v) {
    if (this.map.has(k)) this.map.delete(k);
    else if (this.map.size === this.cap) {
      this.map.delete(this.map.keys().next().value); // evict oldest = LRU
    }
    this.map.set(k, v);
  }
}
