Vector search: nearest neighbors at RAG scale

Embeddings turn meaning into geometry: similar texts become nearby points in a high-dimensional space, and "find relevant documents" becomes k-nearest-neighbor search. At a million vectors, comparing the query against everything is too slow — so production retrieval runs on a graph whose edges connect similar vectors, searched greedily. That structure, HNSW, is this unit's flagship — and you already know every idea inside it.

Before you start Graph search, best-first frontiers, and what embeddings are. This page assembles them.

The idea

Exact kNN is a linear scan: distance to every vector, keep the k best — O(n·d) per query, unbeatable in the worst case (and genuinely the right answer below ~100k vectors; libraries call it "flat"). Beyond that, everyone trades a sliver of accuracy for orders of magnitude of speed: approximate nearest neighbors.

HNSW (Hierarchical Navigable Small World) is the dominant ANN index, and it is graph search from unit 4 wearing production clothes. Build: insert vectors one at a time, connecting each to its M nearest existing neighbors — a "small-world" graph where similar things link. Search: start anywhere, repeatedly move to the neighbor closest to the query — greedy descent through similarity space — keeping a best-first frontier of candidates (a beam, size ef) rather than a single position, which is exactly A*'s frontier discipline with h = distance-to-query. The "hierarchical" part: upper layers hold sparse long-range links (an express network) so the search crosses the space in a few hops before descending to the dense ground layer for precision — binary search's instinct, rebuilt inside a graph.

Where you'll meet this

This IS the retrieval in retrieval-augmented generation: your documents are chunked, embedded, and indexed (pgvector, Pinecone, Qdrant, FAISS, Elasticsearch/OpenSearch kNN — HNSW under almost all of them); each user question becomes a query vector; the index returns the k nearest chunks for the prompt. Same machinery drives semantic code search, recommendation ("users near you in taste space"), image/audio similarity, deduplication, and memory systems for agents. The engineering surface you'll actually tune: M (graph degree), efSearch (beam width — recall vs latency dial), and the metric (cosine vs dot vs L2 — must match how the embedding model was trained).

Why greedy graph search works here — and when it doesn't

Greedy descent can strand in a local minimum: a node whose neighbors are all farther from the query than it is, while the true nearest sits elsewhere. Three mitigations stack: the beam (ef > 1 candidates explored, not a single walker — misses need to escape the whole beam); long-range links from the layer hierarchy (escape routes past local clutter); and the small-world build discipline (each insertion wires to diverse near neighbors, keeping the graph navigable — the property, from network science, that greedy routing finds short paths, as in Milgram's six-degrees experiment). Recall isn't guaranteed — it's measured: real deployments benchmark recall@k against a flat scan on a sample, then set ef to the cheapest value that clears the bar. That measure-don't-assume loop is unit 1's counters, grown up.

The ANN menagerie, honestly

HNSW: best recall/latency at moderate memory; the default. IVF (inverted file): k-means the space into cells, search only the query's few nearest cells — cheaper memory, a recall dial (nprobe), loved at billion scale, often combined with PQ (product quantization: compress vectors to bytes; distances computed on codes — accepts more error for 10–30× memory savings). ScaNN/DiskANN: engineering refinements of the same ideas for TPU/disk. Trees (KD, ball) — unit 2's instincts — win at low dimension but collapse in high dimension (the "curse": everything becomes almost equidistant), which is precisely why the field moved to graphs. Rule of thumb: flat < 100k; HNSW to ~100M in RAM; IVF-PQ/DiskANN beyond.

The code

// The demo's exact search loop — greedy best-first over the kNN graph:
function graphSearch(query, entry, ef) {
  const visited = new Set([entry]);
  const frontier = [entry];                  // best-first, sorted by dist
  let best = [entry];                        // running top-ef candidates
  while (frontier.length) {
    const cur = popNearest(frontier, query); // A*'s move, h = dist to query
    if (dist(cur, query) > worstOf(best) && best.length >= ef) break;  // beam done
    for (const nb of knnGraph[cur]) {
      if (visited.has(nb)) continue;
      visited.add(nb);
      frontier.push(nb);
      best = topEf([...best, nb], query, ef); // keep the ef closest seen
    }
  }
  return best;                               // top-k ⊆ best, almost always
}
