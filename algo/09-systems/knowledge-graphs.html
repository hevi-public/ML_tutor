Knowledge graphs: retrieval by relationship

Vector search finds what's similar; it cannot answer "who acquired the company that employs the author of this document" — that's three hops of relationships, and it needs data stored as a graph of facts. Knowledge graphs are unit 4 deployed as a database, and "graph RAG" is BFS feeding an LLM's context window.

Before you start BFS and graph modeling; vector search as the retrieval sibling this page contrasts with.

The idea

The data model is triples: (subject, relation, object) — (ada, works_at, acme), (acme, acquired_by, globex). A pile of triples IS a directed labeled graph: entities are nodes, each triple an edge. Queries are path patterns: "companies acquired by whoever employs ada" = start at ada, follow works_at, follow acquired_by — a constrained traversal, executed by exactly the machinery of unit 4. Multi-hop question answering, recommendation-by-relationship, fraud rings, org-chart queries: all path patterns.

Graph RAG composes the two retrieval styles: (1) link the user's question to entity nodes (string/vector matching — units 7 and 9 both reporting); (2) expand n hops around those entities — plain BFS with a depth cap and relation filters; (3) serialize the harvested subgraph into text for the LLM's context. The LLM gets connected facts, not just similar paragraphs — which is the difference on questions whose answer spans documents that never mention each other.

Where you'll meet this

Google's Knowledge Panel and Wikidata; enterprise graphs over customers/products/incidents (Neo4j, Neptune, TigerGraph — their query languages, Cypher/Gremlin/SPARQL, are traversal-pattern DSLs); fraud detection (rings are cycles, unit 4); drug discovery (protein-interaction paths). In the LLM stack, graph RAG variants (Microsoft's GraphRAG among them) build the graph with an LLM — extracting triples from documents — then retrieve by community and path; agent memory systems store "what happened" as an ever-growing entity graph. The quality bottleneck is honest and upstream: entity resolution — deciding that "Acme Corp" and "ACME Inc." are one node — which unit 2's union-find and unit 4's components already gave you the tools to audit.

Vector RAG vs graph RAG — the honest decision table

Vector RAG wins when the answer lives in some paragraph's wording: cheap to build (chunk-embed-index), robust to mess, fails soft (a merely-similar chunk). Graph RAG wins when the answer is a composition of facts across sources — multi-hop questions, aggregations ("all products of subsidiaries of…"), provenance-sensitive domains — at the cost of an extraction pipeline that is itself LLM-powered and error-prone: a wrong triple is a confidently wrong fact forever, where a bad chunk is just noise. Production systems increasingly run both and route: similarity questions → vectors; relationship questions → graph; let the LLM see each source labeled. The skill this course gave you is recognizing WHICH failure a bad answer came from — retrieval-by-similarity missing, or a hop that doesn't exist.

The code

// Graph RAG's retrieval core (the demo's exact code, events elided):
function harvest(graph, seeds, maxHops, allowedRelations) {
  const seen = new Set(seeds);
  let frontier = [...seeds];
  const facts = [];
  for (let hop = 1; hop <= maxHops; hop++) {         // BFS with a depth cap
    const next = [];
    for (const u of frontier) {
      for (const { rel, to } of edges(u)) {
        if (!allowedRelations.has(rel)) continue;     // relation filter
        facts.push(`${u} —${rel}→ ${to}`);            // harvest the triple
        if (!seen.has(to)) { seen.add(to); next.push(to); }
      }
    }
    frontier = next;
  }
  return facts;    // serialized into the LLM's context window
}
