Probabilistic structures: tiny memory, honest error bars

Exact answers have a memory floor: remembering a billion URLs takes billions of bytes, period. The escape is a different contract — answers that are usually right, with error you can calculate and tune, in kilobytes. The flagship is the Bloom filter: set membership with one-sided error, and one of the most deployed data structures on the planet.

Before you start Hashing — everything here is hash functions pointed at bits instead of buckets. Rabin-Karp's one-sided-error idea (unit 7) is the same shape.

The idea

A Bloom filter is a bit array of m bits plus k hash functions. Add x: set the k bits that x's hashes point at. Query x: are all k of x's bits set? If any is 0, x was definitely never added — a certain no. If all are 1, x was probably added — but other items' bits can overlap into a false positive. The error is one-sided (no false negatives), and its rate is arithmetic, not hope: about (1 - e^{-kn/m})^k after n insertions — in plain English, pick bits-per-item and the failure odds follow. Ten bits per item and optimal k ≈ 0.7·m/n gives ~1% false positives: a billion URLs summarized in ~1.2 GB instead of ~60 GB of exact storage.

Where you'll meet this

Databases first: LSM engines (RocksDB, Cassandra, the storage-engines page ahead) keep a Bloom filter per file so a read can skip files that certainly lack the key — the single trick that makes LSM reads viable. Chrome's Safe Browsing pre-check, CDN "have I cached this?", spellcheckers, spam filters, crawl frontiers ("seen this URL?"), and dedup in LLM training pipelines ("seen this n-gram/document?") at corpus scale, where exactness would cost more than the training run. Siblings with the same contract: count-min sketch (approximate counts — heavy-hitter detection, trending topics, per-key rate stats) and HyperLogLog (count distinct in 1.5 KB — Redis PFCOUNT, unique-visitor analytics). All three are hashes + a small array + a theorem.

Why one-sided error is the load-bearing feature

Systems compose safely around an error that only points one way. The LSM read path: filter says no → skip the file, guaranteed safe; filter says yes → do the real read, wasting work only the false-positive fraction of the time. The pattern — cheap certain-no filter in front of an expensive exact check — is Rabin-Karp's hash-then-verify generalized, and it never returns a wrong final answer; it only occasionally fails to save you money. Contrast a cache (can return stale data) or a semantic cache (can return wrong data): knowing WHICH side of an approximate structure can err is the systems-design skill this unit keeps drilling. Two footnotes: classic Blooms can't delete (bits are shared; counting Blooms and cuckoo filters fix it), and capacity is a promise — overfill past the design n and the false- positive rate climbs the curve.

The code

// The demo's exact code — a Bloom filter is barely code at all:
class Bloom {
  constructor(m, k) { this.m = m; this.k = k; this.bits = new Array(m).fill(0); }
  hashes(x) {              // k hashes from 2 via double hashing (standard trick)
    const h1 = djb2(x) % this.m, h2 = (fnv(x) % (this.m - 1)) + 1;
    return Array.from({ length: this.k }, (_, i) => (h1 + i * h2) % this.m);
  }
  add(x)   { for (const b of this.hashes(x)) this.bits[b] = 1; }
  query(x) { return this.hashes(x).every((b) => this.bits[b] === 1); }
}          // query=false → certainly absent; true → probably present
