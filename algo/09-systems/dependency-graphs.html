Dependency graphs: the DAG that runs your stack

Unit 9 begins where the theory units end: each page takes algorithms you now own and shows them running, load-bearing, inside systems you ship with. First up, the most ubiquitous: the dependency DAG — in build tools, data pipelines, and every LLM agent framework — and the two questions asked of it a billion times a day: what can run now? and what's making everything late?

Before you start Topological sort is the engine; this page is its production deployment.

The idea

Everything orchestrated is the same object: nodes = tasks, edges = "needs the output of". make and Bazel over build targets; Airflow/Dagster/dbt over data jobs; Terraform over resources; and LangGraph-style agent pipelines over tool calls and LLM steps. The scheduler inside all of them is Kahn's algorithm run live: a task becomes ready when its unfinished-dependency count hits zero, and everything ready runs concurrently — the ready set is the worker pool's feed.

The second question is scheduling's oldest: with parallelism unlimited, how fast can the whole graph finish? Answer: the critical path — the longest chain of dependent tasks, weighted by duration. Nothing can beat it; everything off it has slack. Computing it is longest-path-on-a-DAG, which is shortest-path with max instead of min — a two-line DP over the topological order (negative-weight fears don't apply: no cycles).

Where you'll meet this

Every -j8 build, every CI fan-out, every dbt run. Agent orchestration is the newest tenant: frameworks like LangGraph literally hold a graph of LLM/tool nodes and execute exactly this ready-set loop — parallel tool calls are "in-degree hit zero" wearing a trenchcoat, and a slow chain of dependent LLM calls is a critical path measured in seconds and dollars. Terraform plans, Kubernetes operators reconciling resource dependencies, Excel recalculation, package installs — the DAG scheduler may be the single most-executed algorithm pattern in software operations.

The details (open as much as you like)

Critical path, precisely

In topological order: finish(v) = duration(v) + max(finish(u)) over v's dependencies (0 for sources). The overall makespan is the max finish; walking the argmaxes backward names the critical chain. Everything else has slack = (latest start that wouldn't delay anyone) − (earliest start) — the formal version of "this task can be slow for free". Ops translation: profiling a pipeline without computing the critical path invites optimizing a task with hours of slack; the honest target list is the critical chain, and it can CHANGE after each improvement — re-run the DP, don't trust last quarter's bottleneck. (Same math as PERT charts, 1958 — the DAG outlived the acronym.)

What real orchestrators add on top

The classroom loop assumes tasks succeed and workers are infinite. Production adds: bounded workers (choosing WHICH ready tasks run first is NP-hard scheduling → list-scheduling heuristics, usually critical-path-first); failure semantics (retry, skip-downstream, or halt — Airflow's trigger rules); caching (Bazel skips tasks whose input hashes match — memoization over the DAG, unit 6 again); dynamic graphs (agent frameworks add nodes mid-run as the model decides on tools — Kahn's handles this fine as long as new edges never point backward in time); and backpressure/rate limits for API-calling nodes. Each is an engineering layer over the same two primitives you now own.

// The live scheduler (this page's exact demo code, events elided):
let ready = tasks.filter((t) => indegree(t) === 0);
let clock = 0;
while (ready.length) {
  for (const t of ready) {                      // the whole set, in parallel
    finish[t] = clock + duration[t];
  }
  clock = Math.min(...ready.map((t) => finish[t]));   // next completion
  // decrement dependents of everything finished; newly-zero → ready
}
