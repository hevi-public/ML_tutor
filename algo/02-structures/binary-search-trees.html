Binary search trees: keeping order without paying for it

The hash table bought O(1) by shredding order. The binary search tree keeps everything sorted and stays fast — binary search, rebuilt as a shape you can insert into. With one famous failure mode you're about to cause on purpose.

Before you start Binary search from counting steps — a BST is that idea, made into a structure — and the tree height = log n fact from the math toolkit.

The idea

One rule makes the whole structure: at every node, everything in the left subtree is smaller, everything in the right subtree is larger. That rule is binary search's invariant frozen into pointers — standing at any node, one comparison tells you which subtree the target must be in, and you've discarded the other one wholesale. Search, insert, min, max, "smallest key ≥ x", ordered iteration: all just walks down (or along) the tree, all proportional to its height.

And there's the catch. Height is only log n if the tree is bushy. Nothing in the BST rule forces bushiness — the shape is decided entirely by insertion order, and the worst order is one you meet constantly in real life: already-sorted input, which makes every insert go the same direction, producing a chain — a linked list with extra steps, O(n) everything.

Where you'll meet this

Ordered maps everywhere: Java's TreeMap, C++'s std::map, Rust's BTreeMap — reached for precisely when you need what hashes can't do: range scans ("orders between Tuesday and Friday"), nearest-key lookups, sorted iteration, priority-with-updates. The tree idea scaled to disk pages becomes the B-tree — the index inside practically every relational database — which unit 9's storage-engines page treats as this page's giant cousin.

The details (open as much as you like)

Everything is a walk: the operation catalogue

Search: walk down, one comparison per level — O(height). Insert: search for where it would be, attach it there. Min/max: walk all the way left/right. In-order traversal (left, node, right) visits every key in sorted order — a sorted dump for free, and the reason the tree renderer above can place nodes left-to-right by value. Delete is the only subtle one: a leaf just goes; a one-child node is bypassed; a two-child node swaps values with its in-order successor (the leftmost node of its right subtree — which has at most one child) and deletes there. One clever case, not three hard ones.

Show the math — why random order gives log height

Inserting n distinct keys in uniformly random order gives expected height O(log n) — in fact expected search cost ≈ 1.39 log₂ n. The argument is quicksort's in disguise: the first key inserted plays "pivot", splitting the rest into left and right subtrees, and random pivots split well on average. (Unit 3 makes that argument properly for quicksort; it transfers here verbatim.) The trouble is that production data isn't random — timestamps, sequence IDs and imported sorted files are exactly the adversarial order. Hence: balance by force, next page.

The code

// The demo's exact code (assets/js/algo/structures.js): the BST rule as a walk.
function* bstInsert(state, value) {
  const id = state.nextId++;
  state.nodes[id] = { value, left: null, right: null };
  if (state.root == null) {
    state.root = id;
    yield { type: "insert", id, parent: null, dir: "root" };
    return id;
  }
  let cur = state.root;
  for (;;) {
    yield { type: "visit", id: cur };                    // one comparison
    const dir = value < state.nodes[cur].value ? "left" : "right";
    const next = state.nodes[cur][dir];
    if (next == null) {                                  // found the gap
      state.nodes[cur][dir] = id;
      yield { type: "insert", id, parent: cur, dir };
      return id;
    }
    cur = next;                                          // discard other subtree
  }
}

Where this goes next

The degenerate chain you just built is not a corner case — it's what sorted input always does to a naive BST. The fix is to make the tree maintain its own bushiness: AVL and red-black trees, which promise O(log n) no matter what order the keys arrive in.
