Hash tables: the O(1) that runs the world

Look anything up in constant time, no matter how much you've stored — by computing where it lives instead of searching for it. It sounds like cheating. The fine print about when the cheat fails is what separates engineers who use maps from engineers who understand them.

Before you start Arrays (O(1) indexing is the engine under everything here) and mod from the notation reference.

The idea

The array gave us a superpower — O(1) jump to any index — with a catch: indexes are meaningless integers, and we want to look things up by keys ("alice", a URL, a session token). The hash table's move: build a function that turns any key into an index, then use the array superpower. That converter is the hash function; a good one scatters keys evenly and computes fast.

The catch behind the catch: more possible keys than slots means two keys must sometimes land on the same slot — a collision, and it's not a bug but a certainty to be managed. The two classic managements: chaining (each slot holds a little list) and open addressing (if your slot's taken, step to the next). How crowded the table is — stored keys ÷ slots — is its load factor, the single dial that decides whether "O(1)" stays honest.

Past a load factor of ~0.75, collisions snowball — real tables grow (double the slots, rehash everything) before that point. The resize is the dynamic array's amortized trick again: occasional O(n), O(1) averaged.

Where you'll meet this

It is barely an exaggeration to say hash tables ARE the industry: every Map/dict/HashMap, every cache from CPU-adjacent to Redis, database hash joins and hash indexes, deduplication, session stores, feature flags, DNS resolvers. The LLM-era additions run on them too — a KV cache is a hash-shaped store with an eviction policy (unit 9), and sharding a vector database starts with hashing keys to nodes (consistent hashing, also unit 9, fixes what naive mod n breaks when n changes). When unit 9 keeps saying "then we hash it", this page is the "it".

The details (open as much as you like)

Why "O(1)" is honest — and exactly when it isn't

With a good hash and a controlled load factor, the expected chain length is a small constant (at load α, about α for chaining) — hence O(1) expected lookups, and resizing keeps α controlled. Two ways the promise breaks: a bad hash (everything piles into few slots — the table quietly becomes a linked list, O(n)), and an adversarial workload: if an attacker can choose your keys and knows your hash, they can manufacture collisions on purpose. That's hash-flooding DoS — real CVEs, real outages — and it's why runtimes seed their string hashes randomly per process and why unit 3's "adversarial input" drum keeps beating.

Chaining vs open addressing: the real trade

Chaining is forgiving (load factor can exceed 1, deletions are trivial) but every chain hop is a pointer chase — the cache-miss tax from the arrays page. Open addressing keeps everything in one contiguous array (cache-friendly probes, no per-entry allocation) but degrades sharply as load nears 1 and makes deletion subtle (you leave "tombstones" so probe chains don't break). Modern high-performance tables (Swiss tables, Robin Hood variants) are open addressing plus SIMD-friendly metadata — contiguity won, same verdict as the arrays page.

What makes a hash function good here (and why this isn't crypto)

For tables you need: fast, deterministic, evenly-scattering, and — against flooding — unpredictable to outsiders (a per-process random seed). You do not need cryptographic one-wayness; SHA-256 in a hash map is pure waste, and conversely djb2 in a password store is a career mistake. Same word, "hash", two different contracts — the security page in unit 11 draws the full line.

The code

// The demo's exact code (assets/js/algo/structures.js): hash, then manage
// the collision. Chaining shown; probing differs only in the loop.
function hashString(key, buckets) {
  let h = 5381;
  for (let i = 0; i < key.length; i++)
    h = ((h << 5) + h + key.charCodeAt(i)) >>> 0;   // h*33 + char, unsigned
  return h % buckets;                                // mod folds it to a slot
}

function* chainInsert(state, key) {
  const h = hashString(key, state.buckets.length);
  yield { type: "hash", key, h };                    // computed, not searched
  const chain = state.buckets[h];
  for (let k = 0; k < chain.length; k++) {
    yield { type: "chain-walk", slot: h, k };        // the collision tax
    if (chain[k] === key) return false;
  }
  chain.push(key);
  yield { type: "place", slot: h, key };
  return true;
}
