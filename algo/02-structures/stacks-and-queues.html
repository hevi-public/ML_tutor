Unit 2 · Data structures

Stacks, queues and deques: restrictions as guarantees

Take a sequence and forbid yourself from touching the middle. What's left is barely a data structure — and that's why these two show up inside more algorithms than everything else in this unit combined.

Before you start Arrays and linked lists, plus the call stack from recursion — which was a stack all along.

The idea

A stack allows two moves: put a thing on top (push), take the top thing off (pop). Last in, first out. A queue allows two moves: join at the back (enqueue), leave from the front (dequeue). First in, first out. A deque (say "deck") allows both ends and is the Swiss-army version.

Why celebrate structures this restricted? Because the restriction is a promise other code can lean on. A stack promises: whatever you're handling now, you'll finish before returning to what you interrupted — which is why interrupt-and-resume problems (nested brackets, undo, function calls) are stack problems. A queue promises fairness: things are handled in arrival order — which is why spreading-outward problems (task scheduling, breadth-first anything) are queue problems.

Here's the sentence this page exists for, and it's one of the prettiest in computer science: take the same graph-exploration loop and swap its to-do container — a stack explores depth-first, a queue explores breadth-first. The data structure is the algorithm. Unit 4 stages this as a live side-by-side.

Where you'll meet this

Stacks: your undo history, the call stack in every stack trace, the back button, parser states in every compiler and JSON.parse. Queues run the async world: message brokers (SQS, RabbitMQ, Kafka partitions are queues with a ledger), your event loop's task queue, print spoolers, request buffers — and "unbounded queue" is the classic way a healthy service dies politely during an outage, which is why real queues are bounded and shed load. Deques: your browser history (bounded at both ends), work-stealing schedulers (own work popped stack-style, stolen work taken queue-style).

The details (open as much as you like)

Implementations: both are arrays wearing costumes

A stack is a dynamic array plus discipline: push/pop at the end are the array's cheap end — O(1) amortized. A queue on a plain array has a trap: shift() from the front is O(n) (everything slides down). The fix is the ring buffer: keep head and tail indexes that wrap around with mod — both ends O(1), one fixed block of memory, zero allocation in steady state. That's why ring buffers live inside network cards, audio pipelines and channel implementations.

The bounded-queue question every system design asks

Producers faster than consumers ⇒ the queue grows. Unbounded, it grows until memory dies — turning one slow dependency into a full outage, minutes later, far from the cause. Bounded, you must choose a policy at the full mark: block the producer (backpressure), drop new work (shed load), or drop old work (freshness wins). There is no fourth option, only unchosen defaults. This one paragraph is a startling fraction of real incident postmortems.

The code

// Ring buffer: a queue with O(1) at both ends and no allocation.
class RingQueue {
  constructor(capacity) {
    this.buf = new Array(capacity); this.head = 0; this.size = 0;
  }
  enqueue(x) {
    if (this.size === this.buf.length) throw new Error("full — pick a policy!");
    this.buf[(this.head + this.size) % this.buf.length] = x;   // wrap with mod
    this.size++;
  }
  dequeue() {
    if (!this.size) return undefined;
    const x = this.buf[this.head];
    this.head = (this.head + 1) % this.buf.length;             // wrap with mod
    this.size--;
    return x;
  }
}
