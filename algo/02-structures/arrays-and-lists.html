Arrays and linked lists: the two ways to hold a sequence

Every structure in this unit is a bargain: pay here, save there. The oldest bargain of all — contiguous block versus chain of pointers — still decides performance fights today, and the modern answer will surprise anyone who learned it from a 1995 textbook.

Before you start Big-O and amortized analysis (the dynamic array's push is priced there).

The idea

An array is one contiguous block of memory: element i lives at start + i × size, so jumping to any index is one multiplication — O(1), and the CPU loves the neighbours-next-door layout. The price: inserting in the middle shifts everything after it (O(n)), and growing needs the occasional copy (amortized O(1), as unit 1 proved).

A linked list is the opposite bet: each element is its own little allocation pointing at the next. Splicing a node in or out is O(1) once you're standing there — but getting there means walking the chain, O(n), and every hop is a jump to a random address the CPU can't predict.

Where you'll meet this

Arrays wear a hundred masks: your language's default list, database pages, network buffers, columnar analytics formats (Arrow, Parquet) that exist because contiguous scans are fast. True linked lists are rarer than the textbooks imply, but their idea — "nodes that point at each other" — runs free lists in allocators, LRU caches (unit 9 builds one), and the intrusive lists inside OS schedulers. And every ORM N+1 bug is secretly a "walk the chain" cost wearing a suit.

The details (open as much as you like)

The modern verdict: arrays win more than the table suggests

The Big-O table calls mid-insertion a tie-breaker for lists. Real hardware disagrees: an array's O(n) shift streams through the cache at full speed, while a list's O(n) walk stalls on every hop (each next pointer is a potential cache miss — unit 11's when-theory-meets-the-clock page measures this live in your browser). For teaching-sized n the list often loses the very benchmarks it was designed to win. The honest rule: default to the array; reach for links when you hold a handle to the node (LRU) or splice constantly at known positions.

Why O(1) indexing is really just arithmetic

address(a[i]) = base + i × elementSize. That's the whole mechanism — no lookup, no walk, one multiply-add the CPU does in a cycle. It's also why arrays are fixed-type in systems languages (the size must be uniform for the formula to hold), and why JavaScript engines quietly deoptimize arrays you mix types into.

The code

// The linked list in its natural habitat: O(1) splice when you HOLD the node.
// This is the skeleton of the LRU cache built in unit 9.
class Node { constructor(v) { this.v = v; this.prev = null; this.next = null; } }

function unlink(node) {              // O(1): no walking, just re-pointing
  node.prev.next = node.next;
  node.next.prev = node.prev;
}
function insertAfter(a, node) {      // O(1): ditto
  node.prev = a; node.next = a.next;
  a.next.prev = node; a.next = node;
}
