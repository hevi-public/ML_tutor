Unit 2 · Data structures

Union-Find: who's connected to whom, instantly

Two operations only — "merge these groups" and "are these two in the same group?" — answered so fast that describing the speed needed a function most engineers have never met. The trick: shameless laziness plus opportunistic tidying.

Before you start Nothing beyond arrays. This is the unit's simplest code hiding its subtlest analysis.

The idea

Track n items partitioned into groups. The representation is one array: parent[i] points at some other member of i's group; follow parents until an item points at itself — that's the group's root, its elected representative. Two items are in the same group exactly when they share a root (find). Merging groups (union) is one write: point one root at the other.

Naively the parent chains can grow long. Two lazy optimizations flatten them: path compression — after any find walks to a root, re-point everything it passed directly at that root, so the walk never happens twice; and union by size — hang the smaller tree under the bigger. Neither costs meaningfully; together they flatten the forest so aggressively that operations become, for every input that fits in this universe, constant time.

Where you'll meet this

Anywhere "connected?" must be answered under a stream of merges: network reachability under link churn, social-graph friend clusters, image segmentation (merging adjacent similar pixels), duplicate-entity resolution in data pipelines ("are these two customer records the same person?"), cycle detection while building spanning trees — which is exactly its starring role in Kruskal's algorithm (unit 5), where union-find IS the inner loop.

The details (open as much as you like)

The two optimizations, in words

Path compression is memoization with pointers: the walk you just did is knowledge, so cache it by re-pointing every visited node straight at the root. The forest gets flatter every time anyone merely asks a question. Union by size keeps the damage bounded meanwhile: hanging small under big means a node's depth only grows when its whole tree at least doubles — so depth ≤ log n even before compression helps. Both are two-line changes; the combination is the magic.

Show the math — "inverse Ackermann", the slowest-growing function in practice

With both optimizations, m operations on n items cost O(m·α(n)), where α is the inverse of the Ackermann function — a function that grows so explosively that its inverse crawls: α(n) ≤ 4 for every n smaller than a tower of exponentials that dwarfs the atom count of the observable universe. So "amortized constant" is the honest engineering summary, with the delicious footnote that it is not constant in theory — and provably can't be (Fredman–Saks). The full potential-function proof is genuinely hard; this course cites it rather than pretends to teach it in a layer. What you should carry: laziness + opportunistic caching can beat structures that work much harder.

The code

// The demo's exact code (assets/js/algo/structures.js), events elided:
function find(parent, x) {
  let root = x;
  while (parent[root] !== root) root = parent[root];   // walk to the root
  while (parent[x] !== root) {                         // path compression:
    const next = parent[x];                            //   re-point the whole
    parent[x] = root;                                  //   walked path at it
    x = next;
  }
  return root;
}
function union(parent, a, b) {
  const ra = find(parent, a), rb = find(parent, b);
  if (ra !== rb) parent[ra] = rb;      // (by-size refinement: hang smaller under bigger)
}
