Heaps: "just give me the smallest, fast"

Full sorted order is often more than you need. When the only question is what's most urgent right now?, a weaker rule buys a simpler structure — a bushy tree that lives inside a plain array, no pointers at all.

Before you start Arrays and the tree-height intuition from BSTs. The heap deliberately keeps LESS order than both.

The idea

A min-heap enforces one modest rule: every parent ≤ its children. Not left-smaller-right-bigger — siblings are strangers here. This buys exactly one superpower: the minimum is always at the root, readable in O(1). Removing it (or adding anything) just re-settles the rule along one root-to-leaf path — O(log n), because the tree is always perfectly bushy.

Why always bushy? The second trick: the heap is a complete tree — filled level by level, left to right — and a complete tree needs no pointers at all. Lay the levels out in an array: the node at index i has children at 2i+1 and 2i+2, parent at ⌊(i−1)/2⌋. The tree is pure arithmetic over a contiguous array — the layout the arrays page crowned. The demo below draws both views of the same bytes.

The interface this implements is the priority queue: push(item), popMin(). The queue page's fairness ("first in, first out") becomes urgency ("most important out first") — and that swap of promise is what schedulers, timers and Dijkstra's algorithm all need.

Rule of thumb: the words "most/least/soonest, repeatedly, under churn" mean heap.

The details (open as much as you like)

Why so fast? The rule is weak on purpose

A BST answers many questions (search, range, order) so it must maintain much order. A heap answers ONE question, so it maintains almost none — you cannot even find an arbitrary key in a heap without scanning (O(n), and that's fine: wrong tool for that job). Weak promise, cheap maintenance: push and pop touch one path of length log n; peek-min is free. Choosing structures is matching the promise to the question, never buying more order than you'll use.

Show the math — building a heap is O(n), surprisingly

Heapifying n items looks like n × O(log n), but sift-down cost depends on a node's height, and almost all nodes are near the bottom with height ≈ 0: half the nodes sift at most 0 levels, a quarter at most 1, an eighth at most 2… Total ≤ n·∑ h/2ʰ = 2n — the halving geometric series from the math toolkit, again. So "turn this array into a heap" is linear, which is why heapsort's setup phase is free and why top-K over a stream starts cheap.

The code

// The demo's exact code (assets/js/algo/structures.js): the array IS the tree.
function* heapPush(a, value) {
  a.push(value);
  let i = a.length - 1;
  while (i > 0) {                        // sift up
    const parent = (i - 1) >> 1;         // tree arithmetic, no pointers
    yield { type: "compare", i, j: parent };
    if (a[i] >= a[parent]) break;        // rule satisfied — done
    [a[i], a[parent]] = [a[parent], a[i]];
    yield { type: "swap", i, j: parent };
    i = parent;
  }
}
// pop: move last element to the root, then sift DOWN one path — O(log n).
