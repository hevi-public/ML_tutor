Counting steps

Before any notation, a habit: an algorithm's cost is a number you can count. This page gives you the site's stepper — every algorithm here runs under it — and uses it to catch two searches doing wildly different amounts of work on the same data.

Before you start Nothing but code fluency. This is the first page of the course proper, and it introduces the stepper controls you'll use everywhere else.

The idea

Here's the whole discipline of algorithm analysis in one move: pick what counts as a step, then count it. Not milliseconds — those belong to the machine. Steps. For searching, the natural step is a comparison: "is this the value I'm looking for?" Every look costs one.

Both demos below search the same sorted array of 64 numbers for the same target. The first is the loop you've written a hundred times: check each item in turn. The second exploits the fact that the array is sorted: check the middle, throw away the half that can't contain the target, repeat. Same input, same answer — watch the comparison counter.

Where you'll meet this

This exact pair is the difference between a database query that scans a table and one that hits an index; between Array.includes() and a Set lookup; between grepping a log file and querying the system that indexed it. Whenever a service "gets slow as the data grows", someone is about to swap a linear look for a logarithmic one — the rest of this course is largely a catalogue of moves like that.

The measurement

One run is an anecdote. Here's the experiment: run both searches at many input sizes, always hunting the worst-case target (the last place either would look), and plot the comparison counts. Dots are measurements; dashed lines are the shapes the next page will teach you to name. The names are the claim — the dots are the evidence.

Linear's worst case grows in lock-step with n. Binary's barely moves — doubling the array adds one comparison. At n = 1,000,000 that's a million looks versus twenty.

The details (open as much as you like)

Why count worst case?

Linear search sometimes gets lucky — target in the first slot, one comparison, done. Counting the lucky run tells you nothing you can promise anyone. This course counts the worst case by default: the most work the nastiest input of a given size can force. A guarantee that survives an adversary survives production traffic. (Average and amortized cost — other useful lenses — get their own pages.)

Why is binary search's count "the number of halvings"?

Each comparison discards half of what's left. Starting from n candidates: n → n/2 → n/4 → … → 1. The count of arrows is "how many times can you halve n before reaching 1" — which is the definition of log₂ n (the next page makes this symbol yours). 64 items: 6 halvings. A billion: 30. That is the entire magic trick, and it only works because sortedness lets one comparison speak for half the array.

The code

This is the actual code the demos above ran — the generators from the site's library (assets/js/algo/sorts.js). The yield lines are the instrumentation: each one both reports a step to the player and increments the counter you watched.

function* linearSearch(a, target) {
  for (let i = 0; i < a.length; i++) {
    yield { type: "compare", i };            // one step, counted
    if (a[i] === target) { yield { type: "found", i }; return i; }
  }
  yield { type: "not-found" };
  return -1;
}

function* binarySearch(a, target) {          // requires: a is sorted
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;              // integer midpoint
    yield { type: "focus", lo, hi, mid };    // the region still in play
    yield { type: "compare", i: mid };       // one step, counted
    if (a[mid] === target) { yield { type: "found", i: mid }; return mid; }
    if (a[mid] < target) lo = mid + 1;       // discard the left half
    else hi = mid - 1;                       // discard the right half
  }
  yield { type: "not-found" };
  return -1;
}
