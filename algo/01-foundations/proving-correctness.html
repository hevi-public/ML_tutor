Proving an algorithm correct

Tests check the inputs you thought of. A correctness argument covers the ones you didn't — and the working engineer's version is one sentence long: find the thing that stays true.

Before you start Counting steps (you've seen binary search run) and recursion (the leap of faith, which this page makes rigorous).

The idea

Every loop you trust, you trust because of a sentence you could say about it — usually without knowing you're saying it. "By the end of iteration i, the first i items are processed." "The running total always equals the sum of what we've seen." That sentence is a loop invariant: a claim that's true before the loop starts and stays true after every iteration.

An invariant proves a loop correct with three small checks — the same shape as climbing a ladder:

1. It starts true (you can reach the first rung).
2. Each iteration keeps it true (from any rung you can reach the next).
3. True + loop finished ⇒ the goal (the top rung is where you wanted to be).

That's induction — the recursion page's "leap of faith" formalized. The power move: the invariant is chosen by you, and a well-chosen one makes tricky code obvious.

Watch it hold

Binary search, but this time ignore the bars and read the sentence under the controls: it states the invariant at every step — "if the target is anywhere, it's between lo and hi". Step through and try to catch the sentence being false. You can't; that's the proof working:

Where you'll meet this

Invariant-speak is all over serious engineering, wearing different badges: database constraints and transactional invariants ("balances sum to zero across a transfer"), the safety properties model checkers like TLA+ verify, class invariants in an aggregate root, "this queue never contains a message twice". Code review is where it pays off daily: asking "what's the invariant of this loop?" finds more bugs than reading line by line — an off-by-one is precisely a broken step 1 or step 3.

The details (open as much as you like)

The three checks, run on binary search

Invariant: if the target is in the array, its index is in [lo, hi].

Starts true: lo = 0, hi = n−1 covers the whole array — the target (if present) is certainly in there.

Kept true: we compare the middle element. If it's too small, the target (being larger) can't be at mid or left of mid — everything we discard is legitimately condemned, so [mid+1, hi] still satisfies the sentence. Symmetrically for too-large.

Implies the goal: we stop either at a[mid] === target (found — correct) or when lo > hi, i.e. the "must be here" region is empty — so the target isn't in the array, and reporting not-found is correct. Also required: termination — hi − lo shrinks every iteration, so the loop can't run forever. Correct answers, always, in finite time. ∎

A second example: why insertion sort is correct

Invariant: before handling item i, the first i items are a sorted arrangement of the original first i items. Starts true (one item is trivially sorted); each iteration inserts the next item into its place among the already-sorted prefix, preserving both sortedness and the "same items" clause; at exit i = n, so the whole array is sorted. Notice the clause "arrangement of the original items" — without it, a.fill(0) would satisfy "sorted". Choosing the invariant IS the thinking; the checks are then mechanical.

Show the connection to induction, properly

Let P(k) = "the invariant holds after k iterations". Check 1 is the base case P(0); check 2 is the inductive step P(k) ⇒ P(k+1); together they give P(k) for all k by mathematical induction. Check 3 converts P(final) into the specification. Recursive algorithms run the same argument on input size instead of iteration count — which is exactly the recursion page's "assume the smaller call works". One idea, two costumes.

The code

Invariants belong in code, not just about it — as asserts in debug builds and as comments that outlive their authors:

function binarySearch(a, target) {
  let lo = 0, hi = a.length - 1;
  // INVARIANT: if target is in a, its index lies in [lo, hi]
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (a[mid] === target) return mid;
    if (a[mid] < target) lo = mid + 1;   // discards only impossible slots
    else hi = mid - 1;                   // ditto — invariant preserved
  }
  return -1;  // [lo, hi] is empty: invariant says target is nowhere
}
