Recurrences: reading cost off a function's shape

A recursive function's cost is itself recursive — "the whole costs what the pieces cost, plus assembly". Write that sentence as an equation and the growth rate falls out. Often on sight.

Before you start Recursion (the call tree) and Big-O (the names we're solving for).

The idea

Merge sort splits an array in half, sorts each half by the same method, and merges the results in about n steps. Its cost obeys:

T(n) = 2\,T(n/2) + n

In plain English: sorting n items costs two sorts of half the size, plus n steps of merging. This kind of equation is a recurrence — cost defined in terms of itself on smaller inputs, exactly mirroring the code. Solving it means finding the plain formula it hides.

    Watch it unfold

    The tool for seeing a solution is the recursion tree: draw the calls level by level, write each call's own work (the non-recursive part) inside it, then add up each level. Pick a recurrence:

    Each box is one call; the number inside is that call's own work. The right margin sums each level — the three classic shapes are level sums constant (total = work × depth), level sums shrinking (the root dominates), and level sums growing (the leaves dominate).

    Where you'll meet this

    Any time you split work and combine results, you're solving a recurrence whether you write it down or not: parallel map-reduce jobs (split, recurse, merge), a microservice fan-out that queries shards and merges pages, tree-structured aggregations in an OLAP engine. The habit of asking "how many levels, and what does each level cost in total?" is the fastest back-of-envelope sizing tool a system designer has.

    The details (open as much as you like)

    The three tree shapes, in words

    Balanced — every level does about the same total work. Merge sort: n per level, log n levels → n log n. This is the commonest shape in divide & conquer.

    Root-heavy — the top level's work dwarfs the rest, so the answer is just the root's work. Example: split in half but only recurse into one half doing n work first — the n at the top dominates.

    Leaf-heavy — the calls multiply faster than the work shrinks, so the bottom layer of tiny calls dominates. Naive fib is the extreme case: the tree has exponentially many leaves, and no cleverness at the top can save it.

    Show the math — the Master theorem

    For recurrences of the divide-&-conquer form:

    T(n) = a\,T(n/b) + f(n)

    In plain English: a subproblems, each a b-th of the size, plus f(n) of your own work. Compare f(n) against n^{\log_b a} — the "tree weight", how fast the leaf count grows:

    Case 1 (leaves win): f(n) grows strictly slower → T(n) = \Theta(n^{\log_b a}).
    Case 2 (a tie): f(n) grows like n^{\log_b a} → T(n) = \Theta(n^{\log_b a} \log n) — every level ties, so multiply by the level count.
    Case 3 (root wins): f(n) grows strictly faster (and is "regular") → T(n) = \Theta(f(n)).

    Merge sort: a = 2, b = 2 → n^{\log_2 2} = n, and f(n) = n ties it → Case 2 → \Theta(n \log n). Binary search: a = 1, b = 2 → n^0 = 1, f = 1 ties → \Theta(\log n). You've now derived both of unit 0's punchlines.

    Show a proof sketch — why the tree argument is sound

    The recursion tree is really a double sum: total cost = \sum_{\text{levels } i} \; \sum_{\text{calls at } i} f(\text{size}). At level i there are a^i calls of size n/b^i, and the tree is \log_b n levels deep. Substituting gives a geometric series whose ratio is a \cdot f(n/b)/f(n); the three Master cases are exactly the three behaviours of a geometric series — decreasing (first term dominates: the root), constant (all terms equal: multiply by length), increasing (last term dominates: the leaves, a^{\log_b n} = n^{\log_b a} of them). The full proof is careful bookkeeping around floors and ceilings, which the math toolkit page licenses you to ignore asymptotically.

    The code

    Recurrences aren't only pen-and-paper — you can check one empirically in ten lines, the same doubling experiment as always:

    function T(n) {                 // merge sort's cost, simulated directly
  if (n <= 1) return 0;
  return T(Math.floor(n / 2)) + T(Math.ceil(n / 2)) + n;   // 2T(n/2) + n
}
// T(1024) = 10240 = 1024 × 10 = n log2 n. Doubling n: T(2048) = 22528
// — slightly MORE than double (×2.2), the signature of n log n growth.
