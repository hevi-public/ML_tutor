Logs, sums and friends

The entire mathematical toolkit this course uses, on one page: four ideas, each earned through code you've already shipped. Skim now, return whenever a page's math layer sends you here.

Before you start School arithmetic, possibly rusty. Everything is rebuilt from "what does this loop do".

Logarithms: the halving counter

Forget the textbook definition for a second. \log_2 n — say "log base two of n" — answers one question: how many times can n be halved before hitting 1? It's the loop count of:

while (n > 1) { n = n / 2; count++; }   // count === log₂(n)

That's why it shows up wherever halving does: binary search's comparisons, a balanced tree's height, merge sort's levels, the number of bits in a number. Try it:

Show the three log rules this course actually uses
\log(xy) = \log x + \log y \qquad \log(x^k) = k \log x \qquad \log_b n = \frac{\log_2 n}{\log_2 b}

In plain English: logs turn multiplication into addition and powers into multiplication — and switching log bases only multiplies by a constant. That last one is why Big-O never bothers writing the base: O(\log_2 n) and O(\log_{10} n) differ by a constant factor, which Big-O ignores by design.

Sums: what loops cost

A loop's total cost is a sum, written with \sum — say "the sum of". One shows up constantly: the cost of the loop-inside-a-loop where the inner loop grows. Insertion sort, bubble sort, "compare every pair" — they all spend:

\sum_{i=1}^{n} i \;=\; 1 + 2 + \cdots + n \;=\; \frac{n(n+1)}{2}

In plain English: the staircase of work adds up to about half an n-by-n square — which is why "the inner loop grows by one each time" and "n²" are the same news. The picture proof: pair the first and last terms (1+n), the second and second-last (2+n−1)… — n/2 pairs, each summing to n+1.

Show the other sum that matters: the geometric series
1 + 2 + 4 + \cdots + n \;=\; 2n - 1 \qquad\qquad 1 + \tfrac{1}{2} + \tfrac{1}{4} + \cdots \;<\; 2

In plain English: doubling terms — the whole pile is barely more than the last term alone (that's why "leaf-heavy" recursion trees cost what their bottom level costs). Halving terms — the whole infinite pile never reaches 2 (that's why dynamic arrays and root-heavy trees are cheap: the tail is small change). These two facts settle more complexity arguments than everything else on this page combined.

Floors, ceilings, and why we wave at them

\lfloor x \rfloor rounds down, \lceil x \rceil rounds up — say "floor of x", "ceiling of x". They appear because real inputs don't divide evenly: splitting 15 items gives \lfloor 15/2 \rfloor = 7 and \lceil 15/2 \rceil = 8, and (lo + hi) >> 1 is a floor in disguise. The asymptotic license: since the pieces differ by at most one item, they never change a growth rate — so analyses on this site treat n as conveniently divisible and say so. (Off-by-one bugs, however, live exactly here — the binary-search page in unit 3 is largely about respecting these brackets in code even though we blur them in analysis.)

Factorials and choices: how big is the haystack?

Lower bounds and brute-force estimates need to count possibilities. n! ("n factorial") counts the orderings of n things — 10! is 3.6 million; 20! is 2.4 quintillion, which is why "try every ordering" dies young. C(n,k) ("n choose k") counts ways to pick k of n when order doesn't matter. You'll meet n! at the sorting lower bound (a decision tree must reach n! leaves) and both in unit 11's hardness arguments.

Where you'll meet this

Capacity planning is this page: "if traffic doubles, log-shaped costs add a step, linear costs double, quadratic costs quadruple" is a sizing meeting in one sentence. The geometric series is your cloud bill's best friend (retry-with-backoff sums to a constant multiple; so does dynamic array growth), and "how many bits do I need for k values" — \lceil \log_2 k \rceil — is every ID scheme and every index-page-depth estimate you've ever done.
