Big-O: naming how cost grows

You already know some code is "slow". Big-O is the precise version of that hunch — a name for how the cost grows when the input gets bigger, which is the only thing that matters once the input is big.

Before you start You've shipped code and you've met a nested loop. That's it — every symbol below is introduced before it's used, and the formal definitions are optional layers.

The idea

Run a function on 10 items, then on 10,000. The question that predicts whether it survives production isn't "how many milliseconds did it take" — that depends on the machine, the language, the weather. The durable question is: when the input gets 10× bigger, what happens to the work? Does it stay flat? Grow 10×? Grow 100×? Double a few times and stop fitting in the universe?

That growth pattern is the algorithm's growth rate, and Big-O notation is nothing more than a compact name for it. When we write O(n^2) — say it "big oh of en squared" — we're saying: as the input size (called n) grows, the work grows like n² at worst, ignoring constant factors and smaller terms. Not "it takes n² milliseconds"; just "double the input, roughly quadruple the work".

Why ignore the constants? Because they're the part the machine, the compiler and the clever tricks can change. The growth rate is the part they can't: an O(n^2) algorithm on the fastest computer ever built still loses to an O(n \log n) one on a laptop, once n is big enough. Big-O is the study of "big enough".

Where you'll meet this

Everywhere, mostly in disguise. The database index that answers in O(\log n) versus the full table scan that's O(n). The accidental includes() inside a loop that turns a request handler quadratic — fine in staging, on fire with real traffic. The vector index behind a RAG pipeline exists precisely to turn "compare the query against every embedding" (O(n) per lookup) into roughly O(\log n). When a code review says "this won't scale", Big-O is the ten-second way to say exactly why.

The details (open as much as you like)

The idea in words

Big-O is a ceiling on growth: "the work grows no faster than this shape". Two habits make it useful:

Drop the constants. 3n² steps and 900n² steps are both "grows like n²" — written O(n^2). The 900 is real money, but it's the same money at every size; growth rate is about what changes with size.

Keep only the biggest term. n² + 5n + 20 is O(n^2), because once n is large the n² term is practically the whole bill. At n = 1,000 the "+ 5n + 20" is half a percent of it.

Two siblings complete the family. Big-O is the ceiling; a floor ("grows at least this fast") is written with \Omega — say it "big omega". When floor and ceiling are the same shape — the usual case for the algorithms in this course — we say the growth is exactly that shape, written with \Theta — say it "big theta". People write O in conversation even when they mean Θ; this site says Θ when it means Θ.

Show the math

Here is the sentence "the work grows no faster than g" with every word pinned down. Let f(n) be the actual cost and g(n) the shape we're claiming:

f(n) = O(g(n)) \;\;\text{means:}\;\; \exists\, c > 0,\; n_0 > 0 \;\;\text{such that}\;\; f(n) \le c \cdot g(n) \;\;\text{for all}\;\; n \ge n_0

In plain English: past some starting size (n_0), the real cost never rises above the claimed shape times some fixed multiplier (c). The multiplier is where the dropped constants went; the starting size is where "big enough" begins.

    \Omega is the same definition with the inequality flipped (f(n) \ge c \cdot g(n)), and \Theta means both hold at once — squeezed between two multiples of the same shape.

    Show a proof

    Claim: 3n^2 + 5n + 20 = O(n^2). The definition asks us to produce the pair (c, n_0) — that's all a Big-O proof is, a working pair of constants.

    Pick c = 4 and n_0 = 8. For every n \ge 8 we have 5n + 20 \le n^2 (at n = 8 that's 60 ≤ 64, and the gap only widens — the left side grows linearly, the right side quadratically). So 3n^2 + 5n + 20 \le 3n^2 + n^2 = 4n^2, which is exactly the definition's inequality. Done. Two things worth noticing: a Big-O proof is nothing deeper than exhibiting one working pair of constants, and the definition doesn't care which pair — c = 100, n_0 = 1000 would have been just as valid, only less tidy.

    The code

    Growth rates aren't abstract — you can count them. This is the shape of the experiment the racer above runs, and the one you'll run for real when the stepper engine lands: instrument the work, double the input, watch the counter.

    function countedSum(items) {
  let steps = 0, total = 0;
  for (const x of items) { steps++; total += x; }     // one touch per item
  return { total, steps };                            // steps === n  → O(n)
}

function countedPairs(items) {
  let steps = 0, pairs = 0;
  for (const a of items)
    for (const b of items) { steps++; if (a + b === 0) pairs++; }
  return { pairs, steps };                            // steps === n·n → O(n²)
}

// countedSum([...])   on 1,000 then 2,000 items:   1,000 →   2,000 steps (×2)
// countedPairs([...]) on 1,000 then 2,000 items: 1,000,000 → 4,000,000 steps (×4)
// The ×2 vs ×4 under doubling IS the difference between O(n) and O(n²).
