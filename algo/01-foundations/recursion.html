Recursion: the machine under the elegance

You've written recursive functions; you may still not trust them. The fix isn't more practice — it's seeing the stack. Once the machine is visible, recursion stops being faith and starts being bookkeeping.

Before you start Counting steps — we'll count calls the way we counted comparisons.

The idea

A recursive function is an ordinary function that happens to call itself on a smaller version of its problem. The machine doesn't treat it specially: every call — recursive or not — pushes a frame (arguments, locals, where to resume) onto the call stack, and every return pops one. "The function calls itself" really means "several frames of the same function are stacked up, each with different arguments". That's the entire trick.

Two things make a recursive function sound, and both are visible on the stack: a base case that answers without another call (the stack's ceiling — without one, the stack grows until it overflows), and progress toward it — every call must shrink the problem.

Where you'll meet this

Every stack trace you've ever read is this page — a printout of the frames at the moment things went wrong. Recursion itself runs your world: JSON serializers walking nested objects, filesystem walkers, React reconciling a component tree, SQL engines executing recursive CTEs, compilers parsing the code you wrote this morning. And RangeError: Maximum call stack size exceeded is the base-case rule, enforced.

The details (open as much as you like)

How to read a recursive function without simulating it

The working programmer's technique is the leap of faith, formally known as induction: to check sum(n), verify the base case by hand, then verify one step — assuming sum(n-1) returns the right answer, does n + sum(n-1) give the right answer for n? If both hold, it's correct for every n, and you never traced a single stack frame. That "assume the smaller call just works" is exactly what the machine guarantees, and the proving-correctness page makes the induction rigorous.

Recursion ↔ iteration, and when the stack is the point

Anything recursive can be rewritten with a loop plus an explicit stack — that's all the machine was doing anyway. When the recursion is linear (one self-call, like sum), the explicit stack often collapses into a single accumulator variable and the loop wins on constant factors and stack safety. When the recursion branches (trees, graphs, divide & conquer), the stack is genuinely load-bearing — you can move it from the call stack to your own array, but you can't delete it. Unit 4's DFS page makes this concrete: the recursive and explicit-stack versions sit side by side as the same algorithm.

The code

function sum(n) {          // add n + (n-1) + … + 1
  if (n <= 0) return 0;    // base case: answers WITHOUT another call
  return n + sum(n - 1);   // progress: strictly smaller problem
}

function fib(n) {          // naive on purpose — the demo above
  if (n <= 1) return n;    // two base cases
  return fib(n - 1) + fib(n - 2);   // two calls: the tree branches
}
