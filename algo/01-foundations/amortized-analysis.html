Amortized analysis: usually cheap, occasionally terrible

Some operations are almost always instant and occasionally expensive by design. Worst-case-per-operation slanders them; amortized analysis prices them honestly — and you've been relying on it every time you call push().

Before you start Big-O, and the geometric series from the math toolkit — it does the heavy lifting here.

The idea

A dynamic array (JavaScript's array, Python's list, Rust's Vec) keeps a block of memory with some spare capacity. push() usually drops a value into a free slot — one step. But when the block is full, it allocates a block twice the size and copies everything — n steps in one call. So what does push "cost"? One step? n steps?

The honest answer prices the sequence, not the operation: amortized cost is the total cost of any run of k operations, divided by k. For doubling arrays the answer is a constant — the expensive moments are rare in exactly the proportion that keeps the average flat.

Where you'll meet this

Everywhere a system "pays rent occasionally": dynamic arrays and string builders, hash tables rehashing at their load factor (unit 2), LSM storage engines compacting (unit 9), garbage collectors, Kafka consumers rebalancing. Amortized thinking also explains the pager reality: p99 latency can be ugly while the average is fine — amortized bounds promise totals, not tail latencies. When a teammate says "it's O(1) amortized", the sharp follow-up is "and is the occasional spike acceptable here?"

The details (open as much as you like)

The banker's version: charge 3 coins per push

Charge every push 3 coins: 1 pays for its own write; 2 go into the bank. When a resize copies n items, the bank holds enough — since the last resize, n/2 new items each banked 2 coins = n coins, exactly the copy bill. The bank never goes negative, so the total cost of k pushes is ≤ 3k. Amortized cost: 3 = O(1). No probability anywhere — this is a worst-case guarantee about totals.

Show the math — the aggregate method
\text{cost of } k \text{ pushes} \;=\; k + \underbrace{(1 + 2 + 4 + \cdots + 2^{\lfloor \log_2 k \rfloor})}_{\text{all the copies}} \;<\; k + 2k \;=\; 3k

In plain English: k for the writes themselves, plus the copy bills — which double each time, so they sum to less than twice the largest one. Divide by k: fewer than 3 steps per push, no matter how long the sequence runs. The geometric series is the entire proof.

And why double, rather than grow by a fixed 100 slots? Fixed growth means resizing every 100 pushes, each copy bigger than the last: the copy bills become the staircase sum — Θ(k²) total, Θ(k) amortized per push. Growing by a factor is what makes the bills a geometric series. (Any factor works; 1.5× and 2× are the common choices, trading memory slack against copy frequency.)

Amortized vs average vs worst — the three-way distinction

Worst case per op: the most one operation can cost (push: Θ(n), during a resize). Amortized: the worst total for any sequence, divided by its length (push: O(1)) — an adversary-proof guarantee, no randomness involved. Average case: expected cost over random inputs (quicksort's Θ(n log n) — unit 3) — a probabilistic statement. All three are worth knowing; confusing them is how "O(1)" ends up on a whiteboard meaning three different things.

The code

class DynamicArray {
  constructor() { this.cap = 1; this.len = 0; this.data = new Array(1); }
  push(x) {
    if (this.len === this.cap) {           // full: pay the big bill
      this.cap *= 2;                       // the factor is the whole trick
      const bigger = new Array(this.cap);
      for (let i = 0; i < this.len; i++) bigger[i] = this.data[i]; // n steps
      this.data = bigger;
    }
    this.data[this.len++] = x;             // the usual 1-step case
  }
}
