Unit 2 · History rewriting

Cherry-pick

Copying one commit somewhere else. The mechanism is a three-way merge, which explains both why it usually just works and why the duplicate it leaves behind can bite you later.

The idea

You have a fix on one branch and you need it on another. git cherry-pick <commit> applies what that commit changed, here, and commits the result.

"What that commit changed" is computed, not stored. Git does a three-way merge with:

basethe commit's parent — the world before it
theirsthe commit itself — the world after it
ourswhere you are now

That's why a cherry-pick can succeed even when the surrounding code has changed a lot: the merge only needs to reconcile the one region the commit touched. And it's why a conflict here looks exactly like a merge conflict — it is one.

The result is a new commit with a new id: same author, same message, same tree change, different parent. The original stays where it was. You now have the same change twice in your project's history, under two names.

Try it

The sandbox has a hotfix branch with one commit you want on main:

git log --oneline --all
git checkout main
git cherry-pick hotfix
git log --oneline                     # a new id, the same subject
git show HEAD                         # same change
git cherry-pick -x hotfix~0           # try -x and read the message it writes

The details (open as much as you like)

-x, and why backports need it

git cherry-pick -x appends a line to the message:

(cherry picked from commit 961c4c8…)

It costs nothing and it's the only durable record of where the change came from — the new commit has no structural link to the original. On a maintenance branch six months later, that line is the difference between "this was backported from main" and a mystery.

Git doesn't do it by default because on a shared feature branch the referenced id may be one you rewrote away, making the note misleading. Rule of thumb: use it when picking from a permanent branch, skip it when picking from something you'll rebase.

Duplicates, and what git can spot

Because the copy is a separate commit, merging the two branches later means git sees two commits making the same change. Usually the merge succeeds and does nothing the second time — the three-way merge notices both sides agree. Sometimes it conflicts, and the conflict is baffling until you realise you're looking at the same change twice.

git cherry main feature (and git log --cherry-mark --left-right) compare patch ids — a hash of the change rather than of the commit — and mark commits whose change already exists on the other side. This is how git rebase silently drops commits it can tell you've already applied elsewhere.

-n, ranges, and the useful variants
-napply and stage, don't commit. Pick several and make one commit, or edit before committing
A..Bpick a whole range, oldest first
--continueafter resolving a conflict and staging the fix
--abortput everything back the way it was

When a pick of a range stops on a conflict, .git/sequencer/ holds the remaining list — the same mechanism interactive rebase uses, which is not a coincidence: rebase is cherry-pick in a loop.
