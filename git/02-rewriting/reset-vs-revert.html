Unit 2 · History rewriting

reset versus revert

Both undo. One rewrites history and one adds to it — and choosing wrong is how teams lose an afternoon.

The idea

Two questions, and the answers are unrelated:

The distinction

reset moves your branch to a different commit. History changes shape; the undone commits are no longer on the branch.

revert makes a new commit that undoes an old one. History grows; nothing is removed.

So the choice is not about safety — reset is perfectly safe on a branch nobody else has — it's about whether the commits are already somewhere else. If they are, reverting is the only honest option: rewriting would break everyone who already has them.

The three resets

reset takes a commit and moves up to three things to match it:

--softbranch onlyindex and worktree untouched, so the undone changes are all staged, ready to recommit
--mixedbranch + indexthe default. Changes survive in your files, unstaged
--hardbranch + index + worktreeyour files are overwritten. The one that discards work

Two things it never does, both worth knowing precisely: it never touches untracked files (so reset --hard won't remove that build directory), and it never deletes commits from the object database (so the reflog can undo it).

git reset --soft HEAD~3 is the useful one people don't know: three commits collapse into a fully staged change, and one git commit makes them one. That's a squash without a rebase.

Try it

git log --oneline
git reset --soft HEAD~2      # look at git status: everything staged
git reset --mixed HEAD       # keep going: now unstaged
git status
git reset --hard HEAD        # and now clean — the changes are gone from your files
git reflog                   # every one of those moves is recorded
git reset --hard HEAD@{3}    # back to where you started

The details (open as much as you like)

Reverting a merge, and why it needs -m

A merge commit has two parents, so "undo this commit" is ambiguous: undo relative to which side? git revert -m 1 <merge> keeps the first parent's line and undoes what the second brought in — almost always what you want, since parent 1 is the branch you were on.

The trap: reverting a merge records that those changes are unwanted, so merging the same branch again brings in nothing. Git considers it already merged. Re-merging after a revert-of-a-merge needs the revert reverted, which is as confusing as it sounds and worth avoiding by not merging half-finished branches.

ORIG_HEAD, the one-step undo

Before any big move — reset, rebase, merge, pull — git writes the previous HEAD to .git/ORIG_HEAD. So:

git reset --hard ORIG_HEAD

undoes the operation you just regretted, without your having to read the reflog. It's overwritten by the next big move, so it's a one-shot: use it immediately or use HEAD@{n} instead.

    reset with paths is a different command

    git reset <paths> doesn't move any branch. It copies those paths from HEAD into the index — that is, it unstages them. Same word, different operation, which is exactly why modern git added git restore --staged to say it unambiguously.

    Rule of thumb: reset with a commit moves your branch; reset with paths moves files into the index.
