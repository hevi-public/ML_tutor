Recovering with the reflog

The reason none of this unit is dangerous. Every ref movement is written down, so almost every git accident is two commands from being undone.

The idea

Every time a ref moves, git appends a line to a log. HEAD's log is .git/logs/HEAD; each branch has its own under .git/logs/refs/heads/. A line looks like this:

d1cf19b 587bc61 Ada Rivera <ada@example.com> 1709543400 +0000	commit: fix typo

Old id, new id, who, when, why. That's the whole reflog — and because it records the id a ref moved away from, it is a list of every commit you have abandoned.

So the recovery procedure for nearly everything is the same three steps:

  1. git reflog — read down the list until you recognise where you were.
  2. Note the id, or its HEAD@{n} address.
  3. git reset --hard <that> to go back, or git branch rescue <that> to give it a name without moving.

The second option is the better instinct: putting a new branch on the lost commit can't make anything worse, and lets you look before you leap.

Try it

Destroy something, then get it back:

git log --oneline
git reset --hard HEAD~3          # three commits gone from the branch
git log --oneline                # confirmed gone
git reflog                       # …and there they are
git reset --hard HEAD@{1}        # back
git branch rescue HEAD@{2}       # or name it instead of moving

Then try the harder version: delete a branch entirely and recover it. The branch's own reflog goes with it, so you need HEAD's log — or git fsck.

The details (open as much as you like)

HEAD@{n} versus HEAD~n — the distinction that matters at 6pm
HEAD~3three commits back through parents. A question about the graph
HEAD@{3}where HEAD pointed three movements ago. A question about your history of commands

After a bad reset --hard, HEAD~1 walks further into the past you didn't want, and HEAD@{1} is your rescue. Two characters apart, opposite directions.

The reflog also takes times: HEAD@{yesterday}, main@{2.hours.ago}. Useful when you know roughly when things were fine.

    What the reflog won't save you from

    It's important to know the edges, because they're where real loss happens:

    • Uncommitted work. The reflog records commits. A reset --hard over changes you never committed leaves nothing to find. (Staged changes are a partial exception — git fsck --unreachable can turn up the blob, because git add wrote it.)
    • Another clone's reflog. It's strictly local and never pushed or fetched. Your colleague's reflog can't help you and yours can't help them.
    • Expiry. Reachable entries expire after 90 days, unreachable ones after 30, and git gc can then prune the objects. Recovery is a race you almost always win, but not indefinitely.
    • A deleted branch's own log. Deleting a branch deletes .git/logs/refs/heads/<name> with it. HEAD's log still has the commits if you were ever on that branch.
    When the reflog isn't enough: fsck

    If the commit was made in a state where HEAD never pointed at it — a detached HEAD you left, or a stash you dropped — git fsck finds it by looking for objects nothing points at:

    git fsck --unreachable --no-reflogs

    --no-reflogs matters: without it, the reflog counts as a pointer, so anything findable that way is reported as reachable and you see nothing. With it, you get the genuinely stranded objects — usually a short list you can git show one by one.
