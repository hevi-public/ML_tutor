Unit 2 · History rewriting

Interactive rebase

The todo list is a file, the commands are a tiny language, and the whole thing is cherry-pick in a loop. Once you've seen the file, rebase -i stops being the scary one.

Before you start Cherry-pick, because that is literally what each step of a rebase does.

The idea

git rebase -i <upstream> does three things in order:

  1. Works out which commits are yours — the range <upstream>..HEAD — and writes them, oldest first, into a file: .git/rebase-merge/git-rebase-todo.
  2. Opens that file in your editor. You change it. That's the whole "interactive" part.
  3. Detaches HEAD onto the new base and works down the list, replaying each commit as instructed, then moves your branch to the result.

The file looks like this:

pick 88f724f wip report
pick b23dc77 more wip
pick 587bc61 fix typo, tidy up, works now

# Commands:
#  p, pick   = use commit as it is
#  r, reword = use commit, but edit the message
#  e, edit   = stop here to amend the commit
#  s, squash = meld into the previous commit, keeping both messages
#  f, fixup  = meld into the previous commit, discarding this message
#  d, drop   = remove commit
#  x, exec   = run a shell command
#
# Lines are executed from top to bottom.

Three things about that file are worth internalising. It's ordered oldest first — the opposite of git log, which catches everyone once. Reordering the lines reorders history. And deleting a line drops the commit, which is why an accidentally empty file makes git say "Nothing to do" and abort rather than destroy your branch.

Try it

The sandbox is on feature/report, three messy commits ahead of main. Run git rebase -i HEAD~3: an editor opens on the real todo file. Change the second and third pick to squash, save, and watch the graph.

One difference here Real git opens a second editor after a squash, so you can write the combined message. This sandbox simply joins the messages together, which means the squashed commit ends up with the first commit's subject. Follow it with git commit --amend -m "…" to get the message you want — that's exactly what the editor would have let you type.

Then try the other commands — drop a line, reword one, or swap two lines round — and after each attempt use git reset --hard ORIG_HEAD to get back and try another. That loop, rebase then reset, is how to learn this without fear.

The details (open as much as you like)

What each command actually does
pickcherry-pick this commit onto whatever the rebase has built so far
rewordpick, then amend the message. Nothing else changes
editpick, then stop and hand you the prompt. Amend, add commits, then git rebase --continue
squashpick, then fold into the previous result, and open an editor with both messages
fixupsquash without the message editor — the earlier message wins
dropskip it. Deleting the line does the same thing
execrun a command after that point. A non-zero exit stops the rebase, which is how you test every commit in a series
breakstop here for no reason other than that you asked

exec is the underused one. git rebase -i --exec 'npm test' main appends a test run after every commit, so you find out which commit in a nine-commit branch breaks the build — without doing it by hand.

In this sandbox exec is accepted but only runs the sandbox's own commands, since there's no shell behind it.

Conflicts, and why --continue knows where it was

Each step is a three-way merge, so any step can conflict. When one does, git stops with the conflict in your worktree and the remaining todo list still on disk. That's the mechanism: .git/rebase-merge/ holds the todo, what's done, the original HEAD and the commit it stopped on. So

git rebase --continueafter you've staged the resolution — reads the file and carries on
git rebase --skipabandon that one commit and continue
git rebase --abortput the branch back where it was, from orig-head

Nothing is lost by aborting, ever, because the original commits are untouched — the rebase has been building new ones alongside them. That's also why git reset --hard ORIG_HEAD undoes a rebase that already finished.

Why the ids all change, and what that costs you

Every replayed commit gets a new committer timestamp and, after the first one, a new parent — so every id downstream changes, even for commits you marked plain pick. A ten-commit rebase where you edited one commit still produces ten new commits.

Which is why rebasing a branch other people have based work on is antisocial: their commits point at parents that no longer exist on your branch. On your own unpushed work it costs nothing. Rewriting published history covers the negotiation.
