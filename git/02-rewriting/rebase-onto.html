Unit 2 · History rewriting

rebase --onto

Rebase normally conflates two questions. --onto separates them: which commits to move, and where to put them.

The idea

git rebase main means two things at once: take the commits that aren't in main, and put them on top of main. Usually that's what you want, so the conflation goes unnoticed.

It stops being what you want when your branch was started from the wrong place. Say you branched feature off feature-base, wrote three commits, and now feature-base is abandoned. A plain rebase onto main would replay everything not in main — including feature-base's commits, which you don't want.

The three-argument form splits the question:

git rebase --onto <newbase> <upstream> [<branch>]
                  │           │
                  │           └── which commits: <upstream>..branch
                  └── where they land

So "move just my three commits onto main" is:

git rebase --onto main feature-base feature

Read it as: replay the commits after feature-base up to feature, on top of main. Once you can read that sentence off the command, --onto stops being intimidating.

Try it

The sandbox has main, feature (branched off an older main) and hotfix. Try both forms and compare:

git log --oneline --all
git checkout feature
git rebase main                     # the ordinary form
git reset --hard ORIG_HEAD           # undo it
git rebase --onto main HEAD~1 feature   # move only the newest commit
git log --oneline --all

The second one is the other everyday use: dropping the older commits of your own branch by choosing an upstream inside it.

The details (open as much as you like)

The three uses worth remembering
Transplant a branchgit rebase --onto main old-base feature — my commits, onto main, ignoring the old base's
Drop early commitsgit rebase --onto main~3 main~6 main — keep the last three, throw the middle away
Excise one commitgit rebase --onto <bad>~ <bad> — replay everything after the bad commit onto its parent, removing it from history

That last one is the surgical alternative to revert: instead of adding a commit that undoes it, the commit stops existing. Only sane on history you haven't shared.

Why the middle argument is exclusive

<upstream> is the commit before the first one you want to move — the same exclusive endpoint as in a <upstream>..branch range. So to move a commit X and everything after it, you name X~, not X. Off-by-one here is the most common --onto mistake, and it shows up as "why did it skip my first commit?"

The safe habit: run git log --oneline <upstream>..<branch> first. Whatever that prints is exactly what will move.

The undo, and why it's reliable

git reset --hard ORIG_HEAD, every time. A rebase doesn't modify the original commits — it builds new ones and moves the branch — so the old chain is still there, reachable through the reflog until gc gets round to it.

If you've already rebased twice and lost track, git reflog shows every position with a rebase (start) / rebase (finish) label, so you can pick the one you want.
