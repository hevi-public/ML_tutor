Unit 2 · History rewriting

squash, fixup, autosquash

The habit that makes review comments cheap: commit the fix now, marked for where it belongs, and let one rebase put everything in its place.

The idea

You're six commits into a branch and a reviewer points out a bug in the second one. The bad options are: amend the wrong commit, add a commit called "fix review comment" and leave the history messy, or stop everything and rebase interactively right now.

The good option is a two-part habit.

Now, commit the fix with a marker saying where it belongs:

git commit --fixup=<the commit it fixes>

which writes a commit whose subject is literally fixup! <that commit's subject>. You carry on working.

Later, when you're ready to tidy up:

git rebase -i --autosquash main

Git reads the fixup! prefixes, moves each of those commits directly beneath the commit it names, and changes its command to fixup — before showing you the todo list. You confirm and it's done.

Two variants:

--fixup=Xfold in, keep X's message. The everyday one
--squash=Xfold in, and combine both messages so you can edit them together

Set git config --global rebase.autoSquash true and --autosquash becomes the default, at which point this is just how you work.

Try it

The sandbox already contains two marked commits — one fixup! and one squash!. Look at them, then let autosquash place them:

git log --oneline
git rebase -i --autosquash HEAD~5
# read the todo list carefully before saving: the lines have been reordered for you

Compare it with git rebase -i HEAD~5 without --autosquash and see how much manual reordering you were spared.

The details (open as much as you like)

How git matches a fixup! to its target

By subject text, not by id. fixup! Add the report attaches to the commit whose subject is Add the report. Consequences:

  • Two commits with the same subject make the match ambiguous — git picks one, and it may not be yours.
  • --fixup=<sha> is only a convenience for looking up that subject; what's stored is the text.
  • If you later reword the target, the fixup! stops matching and quietly stays where it is as an ordinary commit. Worth knowing before you wonder why autosquash "didn't work".

Newer git also has --fixup=amend:<commit>, which folds in and replaces the target's message — the third variant, for when the fix changes what the commit should say.

What squashing does to authorship

The result keeps the first commit's author and author date. So squashing a colleague's commit into yours quietly makes it look like theirs, or yours, depending on order — worth a glance when you're tidying a branch with more than one contributor.

If you need both attributed, the convention is a Co-authored-by: trailer in the squashed message, which forges are taught to read.

The maintainer's loop, end to end 
git commit --fixup=HEAD~2        # fix something, keep working
git commit --fixup=HEAD~2        # again, why not
git rebase -i --autosquash main  # one tidy-up
git push --force-with-lease      # publish the rewrite safely

That is most of what "keeping a clean history" means in practice, and it needs no cleverness — just the marker at the time you make the fix, when you still know which commit it belongs to.
