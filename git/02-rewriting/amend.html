Unit 2 · History rewriting

Amending the last commit

git commit --amend doesn't edit your commit. It builds a replacement and abandons the original — and everything else in this unit is that same move, at larger scale.

The idea

You commit, then notice the typo. git commit --amend fixes it, and the mental model most people carry away is "amend edits the last commit". It can't. A commit's id is a hash of its contents, so an edited commit is a different commit.

What actually happens:

  1. Git builds a new commit from the current index, with the same parent as the old one and whatever message you give.
  2. It moves your branch to the new commit.
  3. The old commit is now unreachable. It is still there, byte for byte, named in the reflog.

Two useful consequences fall straight out. An amend is always recoverable — git reset --hard HEAD@{1} puts you back. And an amend is a rewrite: if you already pushed, your branch and the remote's now disagree about a commit that exists in both, which is why the next push is rejected.

Try it

git log --oneline
git commit --amend -m "A better message"
git log --oneline                 # same position, different id
git reflog                        # both ids are here: the new one and the old
git cat-file -p HEAD@{1}          # the "gone" commit, still perfectly readable

Amending content works the same way: stage something first, and it joins the replacement commit instead of becoming a new one.

The details (open as much as you like)

Amend keeps the author, replaces the committer

The new commit inherits the original's author name, email and date, and gets you and now as committer. So git log still shows the original date while git log --format=%cd shows today. This is the same mechanism as cherry-pick and rebase — anything that replays a commit preserves authorship and records who moved it.

Use --reset-author when you genuinely wrote it now, which mostly matters when you're amending someone else's commit.

Amending a commit that isn't the last one

You can't, directly — but the answer is mechanical rather than clever:

  • git commit --fixup=<commit> now, then git rebase -i --autosquash later. The fix goes into the history at the right place, and you never have to interrupt what you're doing. See squash, fixup, autosquash.
  • Or git rebase -i <commit>~ and mark that line edit, which stops the rebase there and lets you amend normally.

Both do the same underlying thing: rebuild every commit from that point on. Amending the tip is cheap because there's nothing after it to rebuild.

The one genuinely dangerous amend

git commit --amend with a dirty index amends in whatever is staged, which is easy to do by accident when you meant to make a new commit. Nothing is lost — the previous commit is in the reflog — but the mistake can be confusing to spot, because git log looks almost right.

If a branch you pushed looks wrong after an amend, resist the urge to force-push until you have read --force-with-lease. Plain --force is how amends destroy other people's commits.
