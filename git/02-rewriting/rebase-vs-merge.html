Unit 2 · History rewriting

Rebase versus merge

Not a matter of taste, exactly. They record different claims about what happened, and only one of them is safe on history other people have.

The idea

Your branch and main have both moved. You need them combined. Two options, and they differ in what ends up in the repository:

mergeone new merge commit with two parents. Your commits keep their ids. History records that two lines of work existed and were joined.
rebaseyour commits are rebuilt on top of main, with new ids. History records a single line, as though you had started from today's main.

So merge preserves what happened, and rebase presents what you wish had happened. Both are legitimate. The interesting question is not which is nicer to read but which facts you're prepared to lose.

Where the answer is not a matter of taste:

  • Unpushed local work: rebase freely. Nobody has those commits, so replacing them costs nothing, and you get a history that's reviewable.
  • Anything others have based work on: merge. Rebasing changes the ids they're building on, and their next pull will try to reconcile two copies of every commit.
  • A long-lived shared branch: merge, and stop asking. The "clean history" argument is not worth the recovery work.

Try it

The sandbox has diverged branches. Do it both ways and compare the graphs — the shape is the argument:

git checkout feature
git merge main                      # a merge commit appears, two parents
git log --oneline --graph
git reset --hard ORIG_HEAD           # undo
git rebase main                     # same content, one line, new ids
git log --oneline --graph

Look at git log --oneline after each: the merge leaves your original ids in place, the rebase replaces every one of them.

The details (open as much as you like)

Fast-forward, and why --no-ff exists

If your branch tip is already an ancestor of what you're merging, there is nothing to combine: git can just slide the ref forward. That's a fast-forward, and it produces no merge commit at all.

--ff (default)fast-forward when possible, merge commit otherwise
--no-ffalways make a merge commit, so the branch is visible in history even when it needn't be
--ff-onlyrefuse anything that isn't a fast-forward. The safe setting for `git pull`

git config pull.ff only is worth setting: it turns a surprise merge commit from a routine git pull into an error message that makes you choose.

The third option: rebase then merge --no-ff

Many projects want both — tidy commits and a record that a branch existed. The recipe:

git rebase -i main        # tidy your own commits into a reviewable series
git checkout main
git merge --no-ff feature  # one merge commit recording the branch

Which is what most forge "merge pull request" buttons do, and why "squash and merge" versus "rebase and merge" versus "create a merge commit" is a choice your project makes once rather than an argument you have per pull request.

What a merge does that a rebase can't

A merge commit records the merge base implicitly, which means a second merge of the same branches only has to reconcile what changed since the last one. Rebase has no such memory — each rebase re-applies every commit and can hit the same conflict again.

This is why long-running integration branches are merged rather than rebased, and why rerere exists: it gives repeated rebases the conflict memory that merges get for free.
