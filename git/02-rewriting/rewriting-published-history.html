Unit 2 · History rewriting

Rewriting published history

Sometimes you have to. Here's how to do it with the least damage, and how to recognise the times you shouldn't.

The idea

The rule everyone repeats is "never rewrite published history". As stated it's too strong — the real content is:

The actual rule Rewriting a branch replaces its commits with new ones. Anyone who has the old commits keeps them, and their git will try to combine both copies. So the cost of a rewrite is paid by everyone who already pulled — which is fine if that's nobody, or if you tell them.

Which gives you a decision procedure rather than a taboo:

Your own unpushed workRewrite freely. Nobody is affected.
Your own pushed feature branch, no one else on itRewrite and push --force-with-lease. Normal practice.
A shared feature branchRewrite only after saying so. Everyone else needs git reset --hard origin/<branch> afterwards.
main, or any long-lived branchDon't. Use revert.

The exception that overrides all of it: a secret got committed. Then the history must be rewritten, everywhere, and the credential must be rotated anyway — because anyone who cloned already has it, and no rewrite can reach their disk. Rotate first; rewrite second.

Try it

The sandbox has a remote whose main has moved on, and a local branch you've rewritten. Watch git refuse, and then do it properly:

git log --oneline --all
git fetch
git status                      # ahead and behind: you've diverged
git push                        # rejected, and read the hint carefully
git push --force                # works, and would trample whatever origin had

Then reset the sandbox and try the same thing with --force-with-lease instead, which is the subject of its own page because the difference matters so much.

The details (open as much as you like)

The message to send when you do rewrite a shared branch

Rewrites go wrong socially, not technically. What people need is the exact command to run:

I've rebased feature/parser and force-pushed.
If you have it checked out:
    git fetch origin
    git reset --hard origin/feature/parser
If you have local commits on it, tell me first and I'll help move them.

Without that last line, someone will run git pull, get a merge of both copies, push it, and now the branch contains every commit twice.

filter-repo, and why not filter-branch

For rewriting all of history — removing a file from every commit, changing every author's email — the tool is git-filter-repo. git filter-branch still exists, is famously slow, and git's own documentation now recommends against it.

# remove a file from every commit that ever contained it
git filter-repo --invert-paths --path secrets.env

It rewrites every commit, so every id in the repository changes. In practice that means: everyone re-clones, open pull requests break, and any id anyone wrote down in an issue is now dangling. Plan it like a migration, not a command.

Not runnable here This sandbox won't run filter-repo or filter-branch. They're the two operations destructive enough that practising them on a toy repository teaches the wrong reflexes — the real skill is the planning around them, not the invocation.
What survives a rewrite anyway

Worth knowing before you promise anyone that a secret is gone:

  • Other clones. Nothing you do to your repository touches theirs.
  • Forge caches. GitHub and friends keep unreachable commits addressable by id for a long time, sometimes indefinitely. A commit id in an old pull request comment may still resolve.
  • Your own reflog and objects, until it expires and gc runs.

Which is the whole argument for rotating the credential: a rewrite makes the secret hard to find, not gone.
