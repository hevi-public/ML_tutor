Packfiles and gc

How a repository with a million versions of a file stays small — and the one routine operation that actually deletes your lost commits.

The idea

Every object starts as a loose object: one zlib-compressed file at .git/objects/ab/cdef…. That's simple and, past a few thousand objects, wasteful — one inode each, no sharing between near-identical versions of the same file.

So git periodically bundles them into a packfile: one .pack with the objects, one .idx for finding them by id. Inside a pack, an object may be stored as a delta against another similar object — usually a later version against an earlier one — so a thousand revisions of a file cost roughly one copy plus a thousand small diffs.

Two clarifications worth having, because they're the source of most confusion:

  • Deltas are a storage detail, not the data model. Every object is still addressable by its own hash and reconstructible on its own. Git stores snapshots; packs make snapshots cheap.
  • Packing changes nothing you can observe except speed and size. Ids don't change, history doesn't change.

gc, and what it actually deletes

git gc              # pack loose objects, expire reflogs, prune unreachable objects
git gc --aggressive # spend much more CPU looking for better deltas. Rarely worth it
git count-objects -v # how much loose stuff is lying around

The order matters, because it's where lost work finally goes:

  1. Reflog entries older than the expiry (90 days reachable, 30 unreachable) are dropped.
  2. Objects nothing can reach — including via the remaining reflog — and older than gc.pruneExpire (two weeks) are deleted.

So a commit you abandoned today survives roughly two weeks even after its reflog entry goes, and git gc --prune=now is the command that skips the grace period. That's the one to think twice about — it's also the one people paste from the internet when a repository is large.

Not runnable in this sandbox This engine only ever writes loose objects; git gc and git repack aren't implemented, and typing them says so. The consequence is worth naming: in these sandboxes nothing is ever really collected, so every "lost" commit stays findable forever. On your machine that's true for a couple of weeks.

Try it

You can still see the loose side of the story:

git count-objects -v
git fsck --unreachable --no-reflogs
ls .git/objects/

The details (open as much as you like)

When gc runs without you asking

Most porcelain commands call git gc --auto, which does nothing unless there are more than gc.auto loose objects (6700 by default). So gc happens on its own schedule, triggered by commits and fetches — which is why "my lost commit was there yesterday" is occasionally true.

Modern git also has git maintenance start, which registers background tasks (incremental repack, commit-graph, prefetch) instead of surprising you mid-command. On a large repository it's a real improvement.

The commit-graph file, and why log got fast

Answering "is A an ancestor of B" means walking commits, which means decompressing commit objects. The commit-graph file (.git/objects/info/commit-graph) caches parents and generation numbers in a flat format, turning many walks into cheap lookups.

git commit-graph write --reachable

It's maintained automatically by git maintenance, and it's why git log --graph on a big repository is dramatically faster than it was a few years ago. Purely a cache: delete it and nothing breaks.

Why your clone is big, and what to do about it

Almost always: a large binary was committed once, years ago. It's in a pack forever, because history is immutable and the object is reachable. Finding it:

git count-objects -vH
git verify-pack -v .git/objects/pack/*.idx | sort -k3 -n | tail -20

Removing it means rewriting every commit that contains it — see rewriting published history — or, if you only need a working clone rather than a clean one, a partial clone, which doesn't download blobs you never check out.
