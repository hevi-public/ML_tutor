Big repositories

Partial clone, sparse checkout, and the other features that exist because some repositories are far larger than git's original assumptions.

The idea

Git assumes you want every object in the history and every file in the tree. For most repositories that's right, and it's why clones are self-contained and everything is fast offline. Past a certain size it stops being right, and two independent features relax the two halves of the assumption:

Sparse checkoutfewer files in your worktree. The index still knows every path; only what you've asked for is written to disk
Partial clonefewer objects downloaded. Git fetches the commits and trees, and fetches blobs on demand when something actually needs one

They're usually used together, and the combination is what makes a hundred-gigabyte monorepo workable:

git clone --filter=blob:none --sparse <url>
cd repo
git sparse-checkout set services/payments libs/common

Now you have the full history graph, a worktree with two directories in it, and blobs arriving only when you check something out or run a diff that needs them.

Not runnable in this sandbox Both features are about what gets transferred and written, and this sandbox has no network and a handful of tiny files — so sparse-checkout and --filter aren't implemented here. This page is a map of what exists and when to reach for it; the mechanisms it builds on — the index, trees, refspecs — are all things you've already used.

The details

The filters, and what each one keeps
--filter=blob:noneno file contents at all up front. The usual choice: commits and trees are small, blobs are the bulk
--filter=blob:limit=1meverything except large blobs — the pragmatic version when a few big files dominate
--filter=tree:0commits only. Very fast, very limited: almost any operation needs a tree, so most things trigger a fetch
--depth=1a shallow clone: recent commits only. Different axis, and much more limiting — history operations either fail or silently see nothing

Prefer a partial clone to a shallow one where you can. A partial clone has the whole graph, so log, blame and bisect all work; it just fetches content lazily. A shallow clone doesn't have the history at all, which is why git log stops abruptly and bisect is useless.

Sparse checkout, cone mode, and why it got usable

The original sparse checkout took arbitrary gitignore-style patterns, which meant git had to match every path in the index against every pattern — slow, on the repositories that needed it most.

Cone mode (the default since 2.27) restricts you to whole directories, which lets git skip entire subtrees without matching. Faster, and the restriction costs almost nothing in practice.

git sparse-checkout init --cone
git sparse-checkout set services/payments
git sparse-checkout list
git sparse-checkout disable       # back to a full checkout

Files outside the cone get the SKIP_WORKTREE bit in the index. They're still tracked, still committed, still in every commit you make — they just aren't on your disk. Which is the source of the one confusing symptom: git status shows nothing wrong for a file that isn't there.

The rest of the large-repository toolkit
git maintenance startbackground repack, commit-graph and prefetch. The first thing to turn on
commit-graphcached ancestry, which is what makes log and merge-base fast at scale
fsmonitora filesystem watcher, so status doesn't have to stat a million files
untracked cachecaches directory scans for the same reason
Git LFSstores large binaries outside the repository, leaving a pointer file. Fixes the "someone committed a 2GB asset" problem that partial clone only mitigates

If a repository is slow, the order to try things in is: turn on git maintenance, check whether a huge blob is the real problem (git count-objects -vH), then reach for partial clone and sparse checkout. Rewriting history to remove the blob is a last resort, because it's a migration for everyone.
