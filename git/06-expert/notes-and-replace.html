Notes and replace refs

Two ways to change what git shows you without changing a single commit. Both are niche, and both are the right answer when you need them.

The idea

A commit is immutable. Its id is a hash of its content, so adding anything — a review link, a build number, a correction — normally means rewriting it and everything after it.

Git has two escape hatches that avoid that, and they work in opposite directions.

Notes: attach something alongside

git notes add -m "Reviewed by Priya; deployed 2026-07-04" <commit>
git log                      # the note appears under the message
git notes show <commit>

Notes live in refs/notes/commits: a parallel tree whose paths are commit ids and whose blobs are your text. The commit is untouched, its id is unchanged, and git log knows to look the note up and display it.

The catch is distribution. Notes are not fetched or pushed by default — they're a separate ref, and the default refspec doesn't cover it:

git push origin refs/notes/commits
git fetch origin refs/notes/commits:refs/notes/commits

which is why notes work beautifully for CI metadata (a machine can push the ref) and disappointingly for team annotations (a human has to remember).

replace: pretend a commit is a different one

git replace <old-commit> <new-commit>

Creates a ref under refs/replace/<old-id>, and from then on every read of that object transparently gets the other one. History appears to change; nothing was rewritten. Turn it off with --no-replace-objects and the original is right there.

The classic use is grafting an old repository onto a new one: convert the history, then replace the new root commit with the old tip, and git log reads through as one continuous story without anyone having to rewrite ten years of commits.

Not runnable in this sandbox Neither git notes nor git replace is implemented here; typing them says so. Both are ordinary refs and ordinary objects underneath, though, and you can build a notes tree by hand with the plumbing from Unit 1 — which the lab below does.

Try it

A note is a blob at a path named after a commit, in a tree, in a commit, pointed at by refs/notes/commits. All of which you can make with plumbing:

git rev-parse HEAD                       # the commit to annotate
echo "Reviewed by Priya" > note.txt
git hash-object -w note.txt              # → a blob
# then: build a tree whose entry name is the commit id,
# commit that tree, and point refs/notes/commits at it

The details (open as much as you like)

Notes in practice, and where they actually get used
Gerritstores review metadata in notes refs — the canonical large-scale use
CI systemsattach build results or artefact ids to commits after the fact
git notes --ref=<name>several independent namespaces, so tools don't collide

What defeats them for human use is the fetch problem plus rebase: notes are attached to commit ids, so rewriting history orphans every note on it. notes.rewriteRef can copy them across a rewrite, and knowing that it exists is usually the difference between notes being useful and notes being a disappointment.

replace versus grafts versus filter-repo
replace refsa real ref, pushable, reversible, and read transparently. The supported mechanism
.git/info/graftsthe old version of the same idea: a local file, unpushable, deprecated. Don't
filter-repoactually rewrites, so ids change and everyone re-clones. Permanent, and a migration

The way to think about it: replace changes what readers see, filter-repo changes what's there. If the goal is "the history should read correctly", replace is cheaper and reversible. If the goal is "this content must not exist", only rewriting counts — and even then, see what survives a rewrite.
