Refspecs and remotes

origin/main is a local file, not a live view of the server. Once that lands, fetch, push and 'ahead 2, behind 1' all stop being mysterious.

The idea

origin/main is a ref in your repository: refs/remotes/origin/main. It records where origin's main was the last time you fetched. It is a cache, it can be out of date, and nothing about it is live.

So three things that look similar are quite different:

mainyour branch
origin/mainyour note of where their branch was at last contact
origin's mainwhat's actually on the server right now, which you cannot see without asking

"Your branch is ahead of 'origin/main' by 2 commits" is a comparison against the middle one. It can be wrong the moment a colleague pushes, and git fetch is how you refresh it. This is also why git fetch is safe: it only updates remote-tracking refs and touches nothing of yours.

Refspecs

A refspec is the mapping that says which ref becomes which:

<src>:<dst>

Your .git/config contains the fetch refspec that creates all those remote-tracking refs:

[remote "origin"]
	url = git@example.com:project.git
	fetch = +refs/heads/*:refs/remotes/origin/*

Read it as: take every branch on the remote and store it under refs/remotes/origin/, allowing non-fast-forward updates (the +). That single line is why origin/* exists at all.

git push origin mainshorthand for main:refs/heads/main
git push origin HEAD:refs/heads/spikepush what I'm on, call it spike over there
git push origin :old-branchempty source — delete the remote branch
git push origin +mainthe leading plus is --force, written into the refspec
git fetch origin main:refs/remotes/origin/mainthe explicit form of what a plain fetch does

Try it

The sandbox has a remote whose main has moved on:

git remote -v
cat .git/config                   # the refspec is right there
git branch -a                     # remote-tracking refs listed separately
git fetch
git status                        # ahead/behind, computed against your local note
git log --oneline --left-right main...origin/main
git rev-parse @{u}                # the upstream, by name

The details (open as much as you like)

Upstream, and the @{u} shorthand

A branch's upstream is two config values:

[branch "main"]
	remote = origin
	merge = refs/heads/main

That's what makes bare git push and git pull know where to go, and what @{u} resolves to. Set it with git push -u or git branch --set-upstream-to.

Two habits worth having:

git log @{u}..           # my commits that aren't pushed yet
git diff @{u}...         # what a pull request would show
fetch versus pull

git pull is git fetch followed by an integration of @{u} into your branch — a merge by default, or a rebase with pull.rebase=true. The second half is the part that can surprise you, which is the argument for fetching first and looking:

git fetch
git log --oneline --left-right main...@{u}    # what happened on each side
git rebase @{u}          # or merge, deliberately

If you do use pull, set git config pull.ff only. It turns a silent surprise merge into an error that makes you choose.

    Pruning, and the branch that isn't there any more

    Deleting a branch on the server doesn't delete your remote-tracking ref, so git branch -a keeps showing branches that no longer exist. git fetch --prune removes them, and git config --global fetch.prune true makes that the default — which is one of the highest-value lines in anyone's git config.
