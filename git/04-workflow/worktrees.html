Worktrees

One object database, several checkouts. The feature that makes stashing and re-cloning mostly unnecessary.

The idea

A repository has one .git directory and, traditionally, one checkout. git worktree add gives you another checkout, in another directory, sharing the same objects and the same refs:

git worktree add ../review feature/parser   # check out that branch over there
git worktree list
git worktree remove ../review

What you get, and why it beats the alternatives:

versus stashingnothing moves in your main checkout. No stack to remember
versus a second cloneobjects and refs are shared, so no re-download, and a commit made in one is instantly visible in the other
versus switching branchesyour build artifacts, editor state and running processes stay put

The everyday uses: reviewing a colleague's branch while yours stays half-finished; running a long test suite on one branch while you work on another; and bisecting without disturbing your worktree.

One rule: two worktrees can't have the same branch checked out. Git refuses, because two checkouts moving one ref would be incoherent. Use a detached checkout (git worktree add --detach) if you just want to look.

The layout

A linked worktree is not a copy. The new directory gets a .git file — not a directory — containing a path:

$ cat ../review/.git
gitdir: /path/to/repo/.git/worktrees/review

And in the main repository:

.git/worktrees/review/
├── HEAD          # this worktree's own HEAD
├── index         # its own index
├── gitdir        # a path back to the .git file
└── commondir     # ../.. — where the shared objects and refs live

So each worktree has its own HEAD, index and reflog for HEAD, and they share the object database, the refs, and the config. That division explains every worktree behaviour worth knowing: a commit in one is immediately available in the other (shared objects), each can be on a different branch (own HEAD), and git worktree list can tell you which branch is busy where.

Not runnable in this sandbox

The sandbox has one filesystem and no way to hand you a second directory to cd into, so git worktree isn't implemented here — typing it says so rather than pretending. The details (open as much as you like)

Pruning, and the stale-worktree message

Delete a worktree's directory with rm -rf and the metadata stays behind, so git keeps thinking the branch is checked out somewhere. git worktree prune clears out entries whose directory is gone; git worktree list marks them prunable.

Which is why the correct removal is git worktree remove <path> — it takes the metadata with it. If you've already deleted the directory and git is refusing to check out the branch, prune is the answer.

Worktrees and bare repositories, the maintainer's setup

A pattern worth knowing: clone bare, then add a worktree per branch you're working on.

git clone --bare git@example.com:project.git project/.bare
cd project
git worktree add main
git worktree add feature/parser

Now main/ and feature/parser/ are sibling directories, both real checkouts, one object store. For anyone who juggles several long-lived branches, it removes branch switching from the workflow entirely.

What's shared and what isn't
Sharedobjects, refs, config, hooks, packed-refs, the stash
Per-worktreeHEAD and its reflog, the index, ORIG_HEAD, bisect state, rebase state, sparse-checkout settings

So you can have a rebase in progress in one worktree and a bisect in another, and they won't interfere. But a config change affects both, and a refs/stash is one shared stack.
