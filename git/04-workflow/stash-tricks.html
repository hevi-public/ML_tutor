Stash tricks

A stash is a pair of commits with a funny name. Knowing that turns it from a black box into something you can inspect, recover and script.

The idea

git stash shelves your uncommitted work so your worktree is clean. What it actually does:

  1. Makes a commit of the index.
  2. Makes a commit of the working tree, with two parents: HEAD and that index commit.
  3. Points refs/stash at the second one.
  4. Resets your worktree to HEAD.

So a stash is ordinary commits, and everything you know about commits applies: you can git show it, diff against it, cherry-pick from it, and recover it from the reflog after dropping it. The "stack" is just refs/stash's reflog — stash@{2} is a reflog address, exactly like HEAD@{2}.

The flags worth knowing

-uinclude untracked files. The default leaves them behind, which is how people lose new files to a subsequent checkout
-pchoose interactively which hunks to stash — the mirror image of git add -p
-kkeep the index, so your staged work stays staged and only unstaged changes get shelved
-m "…"a message. stash@{3} tells you nothing three days later
pop vs applypop applies and deletes; apply leaves the stash in place. Prefer apply when you're not sure it'll work
branch <name>create a branch at the commit the stash was made from, and apply there. The fix for "the stash no longer applies"

Try it

The sandbox starts dirty. Stash it, look at what got made, and get it back:

git status
git stash push -u -m "wip: argv handling"
git status                        # clean
git stash list
git log --oneline refs/stash      # it's a commit
git show refs/stash               # …with your changes in it
git stash pop
git status                        # back

The details (open as much as you like)

Recovering a dropped stash

git stash drop removes the ref entry, not the commit. So:

git fsck --unreachable --no-reflogs | grep commit
git show <each id>                    # find yours
git stash apply <that id>             # apply it directly

stash apply takes any commit that looks like a stash, which is why this works. It's the most common "I destroyed my work" recovery after the reflog itself, and worth knowing before you need it.

Why -u matters more than it looks

Plain git stash leaves untracked files exactly where they are. That's usually convenient and occasionally a trap: you stash, switch branch, and the new file — which the other branch also creates — collides, or gets quietly committed to the wrong branch.

Habit: git stash -u by default, and let .gitignore keep the build directory out of it. Ignored files need -a, which you almost never want.

When not to stash at all

Stashing is a habit from before worktrees were convenient. If the reason you're stashing is "I need to look at another branch for five minutes", a second worktree is strictly better: nothing moves, nothing to remember, no stack to forget about.

The other alternative is a WIP commit: git commit -am wip, do the other thing, then git reset --soft HEAD~ to unpick it. Less elegant, but it's on a branch, it's in the reflog, and it survives everything. Many people who used to stash heavily now do this instead.
