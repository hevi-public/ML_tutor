Merge strategies and rerere

What to do when git can't decide by itself — and how to stop resolving the same conflict every time you rebase.

The idea

A merge is a three-way merge per file: compare the merge base against each side, take whichever side changed, and stop when both changed the same lines differently. The strategy is how git handles the awkward cases around that.

Since git 2.34 the default strategy is ort ("ostensibly recursive's twin"), a rewrite of the old recursive. It's faster, handles renames better, and — usefully — can compute a merge without touching your worktree at all. You rarely need to name a strategy; the options are what matter:

-X ourson conflicting hunks, take our side. Everything non-conflicting from both sides is still merged
-X theirsthe same, favouring theirs
-s ourscompletely different: take our tree wholesale and ignore theirs, while still recording the merge. Used to declare a branch merged without taking its content
-X ignore-space-changethe answer to a whitespace-only conflict
-X patiencea different diff algorithm; sometimes untangles a conflict that looks worse than it is

The distinction to keep is -X ours versus -s ours. The first resolves conflicts in our favour; the second throws their changes away entirely. They are one character apart and not remotely the same.

Try it

The sandbox has two branches that both edited the cache size in config.ini. Watch a real conflict, then resolve it three ways:

git log --oneline --all
git merge tune-cache             # conflict — read the markers
cat config.ini
git merge --abort
git merge -X ours tune-cache      # our value wins, no prompt
git reset --hard ORIG_HEAD
git merge -X theirs tune-cache    # theirs wins

The details (open as much as you like)

Reading a conflict properly 
<<<<<<< HEAD
cache = 16
=======
cache = 512
>>>>>>> tune-cache

Between <<< and === is yours; between === and >>> is theirs. The markers are a note to you — git doesn't parse them back, so resolving means editing the file into what you want and staging it.

git config merge.conflictStyle zdiff3 is worth turning on: it adds the base version as a third section, so you can see what each side actually changed rather than guessing. And remember the index holds all three versions during a conflict — git show :1:file, :2:file, :3:file get at base, ours and theirs.

rerere — reuse recorded resolution

Rebase a long-lived branch repeatedly and you resolve the same conflict every time, because each rebase replays your commits from scratch.

git config --global rerere.enabled true

With that on, git records a hash of the conflict's "pre-image" and the resolution you produced, under .git/rr-cache/<hash>/. Next time it meets an identical conflict, it applies your old resolution automatically and tells you it did:

Resolved 'config.ini' using previous resolution.

It still leaves the result staged for you to check, which is the right balance — you review, you don't retype. For anyone maintaining a branch against a moving trunk this is the single highest-value line of git config there is.

Not runnable in this sandbox rerere isn't implemented here. The conflicts, the markers, the merge strategies and -X options all are, and the lab below uses them; the resolution cache is the part you'll have to turn on in your own config to see.
Merge drivers, for files that shouldn't be merged line by line

Some files conflict every time and should never be merged textually — lock files, generated code, notebooks. .gitattributes can say so:

package-lock.json merge=ours
*.ipynb           merge=nbdime

with the driver defined in config. The built-in union driver (keep both sides' lines) is right for append-only files like changelogs, and binary is right for anything where a half-merged file would be worse than picking a side.
