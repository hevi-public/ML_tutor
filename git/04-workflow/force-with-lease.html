--force-with-lease

The difference between overwriting your own rewritten branch and silently deleting a colleague's commit. One flag, and it should be the only one you ever type.

The idea

You rebased a branch you'd already pushed, so your history and the remote's disagree. A normal push is rejected — correctly, because accepting it would make the remote's commits unreachable:

! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs

--force makes it go through. It also makes it go through when the thing you'd be overwriting is a commit your colleague pushed ten minutes ago, which you never fetched and therefore have never seen. That commit becomes unreachable on the remote, and nothing tells anyone.

--force-with-lease adds one check:

What the lease is Push only if the remote's branch is still exactly where my origin/<branch> says it is. If someone else has pushed since my last fetch, refuse.

So it permits exactly the case you meant — I know what's there, I fetched it, and I intend to replace it — and refuses the case you didn't. The rejection reads:

! [rejected]        main -> main (stale info)

which means "fetch and look again". It costs nothing and it turns a whole class of incident into an error message.

Try it

The sandbox has a remote that's moved on since you last looked. Watch all three outcomes:

git log --oneline --all
git push                          # rejected: non-fast-forward
git push --force-with-lease       # also rejected: stale info — you haven't fetched
git fetch                         # now you can see what they did
git log --oneline --left-right main...origin/main
# then decide: rebase onto theirs (keeps their work), or lease-force (replaces it)

That middle step is the whole point. --force would have gone through and thrown away the remote's commit without mentioning it.

The details (open as much as you like)

Why the lease can lie, and the flag that fixes it

The lease is checked against your remote-tracking ref, which means it's only as trustworthy as the last thing that updated it. If a background git fetch — an IDE, a shell prompt, a scheduled job — runs between your last look and your push, your tracking ref quietly advances to include your colleague's commit, and the lease then approves overwriting it.

Git's answer is to state the expectation explicitly:

git push --force-with-lease=main:<the id I actually saw>

Newer git also has --force-if-includes, which additionally requires that whatever the remote has is already reachable from what you're pushing — closing the auto-fetch hole without your having to name an id.

Make it the default 
git config --global alias.pushf "push --force-with-lease"

There is no config that turns plain --force into the safe version, so an alias — plus the habit of never typing -f — is the practical answer. On the receiving end, the durable fix is on the server: protected branches, or receive.denyNonFastForwards on a bare repository, so nobody's local habits can rewrite the trunk at all.

When it does happen: recovering an overwritten branch

Someone force-pushed over a commit. It isn't lost — it's just unreferenced on the remote:

  • Whoever made the commit still has it locally, reflog and all. Easiest route: they push it again.
  • The remote's own reflog knows, if you have shell access to it — git reflog show main on the server.
  • Forges keep unreachable commits addressable for a long time; the id in a pull request comment usually still resolves, and can be fetched by id.

Which is worth knowing mainly so the response to "I force-pushed over main" is a procedure rather than a panic.
