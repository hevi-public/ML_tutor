Submodules and subtrees

A submodule is one tree entry with an unusual mode. Most of its reputation comes from people not knowing that.

The idea

A submodule is two things, and neither is complicated:

  1. A gitlink: a tree entry with mode 160000, naming one commit in another repository. Not a branch — a commit.
  2. A line in .gitmodules saying where to clone that repository from.
$ git cat-file -p HEAD^{tree}
100644 blob 8d0e412…	README.md
100644 blob 5cff6c5…	count.py
160000 commit 3bf7b3a…	vendor/parser

That's the whole data model. Everything people find awkward follows from the first point: the superproject pins an exact commit, so a clone doesn't get the submodule's content (only its id), your worktree can hold a submodule checkout that doesn't match the pin, and updating means committing a new gitlink in the superproject.

The commands are consequences of that:

clone --recurse-submodulesclone, then fetch each pinned commit. Without it, the directories are empty
submodule update --initthe same thing after the fact
submodule update --remotemove the pin to the submodule's latest upstream — then commit the changed gitlink
git diffshows gitlink changes as -Subproject commit a1b2… / +Subproject commit c3d4…

Try it

The sandbox's repository has a real submodule: a gitlink pointing at a commit in a separate repository next door. Look at it as data:

git cat-file -p HEAD^{tree}          # spot the 160000 entry
git ls-tree -r HEAD                   # …and its path
cat .gitmodules                       # where it would be cloned from
git rev-parse HEAD:vendor/parser      # the pinned commit id
What's real here and what isn't The gitlink and .gitmodules are genuine — real git reads this repository and reports 160000 commit … vendor/parser. What the sandbox doesn't implement is the git submodule porcelain, since it's mostly clone orchestration. Typing it says so.

The details (open as much as you like)

Subtrees: the other answer

git subtree takes the opposite trade: copy the other project's files into your tree, history and all, under a prefix.

Submodulesmall repository, exact pin, but every clone needs an extra step and every contributor needs to understand it
Subtreea plain clone just works and nobody needs to know, at the cost of a bigger repository and a fiddlier update procedure
git subtree add --prefix=vendor/parser <url> main --squash
git subtree pull --prefix=vendor/parser <url> main --squash

The rule of thumb that holds up: if the people cloning your repository shouldn't have to know, use a subtree. If the dependency has its own life and the pin matters, use a submodule. If you're just vendoring a small library you never update, copying the files in is fine and honest.

The failure modes, and what each one actually is
Empty submodule directoryyou cloned without --recurse-submodules. The gitlink is there; the content isn't
"modified: vendor/parser (new commits)"the checkout is on a different commit from the pin. Either commit the new pin or check the pinned one out
Detached HEAD inside the submodulenormal and correct: it's checked out at a commit, not on a branch
A colleague's pin doesn't exist locallythey committed a pin without pushing the submodule. Push the submodule first, always

That last one is the genuinely painful one, and the only real discipline submodules require: push the submodule before you push the superproject commit that pins it.

Useful config 
git config --global submodule.recurse true       # update submodules on checkout/pull
git config --global diff.submodule log          # show submodule changes as commits
git config --global status.submoduleSummary true

Those three remove most day-to-day submodule friction. The first in particular: it makes git checkout and git pull bring the submodules along, which is what people assume happens anyway.
