Hooks

Your own code at git's decision points. The mechanism is simple; the interesting part is which hook runs when, and what it's allowed to stop.

The idea

A hook is an executable file in .git/hooks/ named after the moment it runs. Git runs it, and for some hooks a non-zero exit code cancels the operation. There is no configuration, no registry, and no language requirement — if it's executable, it runs.

.git/hooks/pre-commit          # before a commit is made — can refuse
.git/hooks/commit-msg          # gets the message file; can edit or refuse it
.git/hooks/pre-push            # before objects are sent — can refuse
.git/hooks/post-checkout       # after a checkout; can't refuse anything
.git/hooks/pre-rebase          # can refuse to rebase a protected branch

The ones that earn their keep:

pre-commitformat, lint, reject debugger statements or a stray secret. Runs before the commit exists
commit-msgenforce a message convention, or append an issue number from the branch name
pre-pushrun the test suite, or refuse to push to main. Gets the refs being pushed on stdin
post-checkout / post-mergere-install dependencies when the lock file changed

The important limitation: hooks are not cloned. .git/ isn't part of the repository's content, so a hook you write protects only you. Teams distribute them with a committed directory plus git config core.hooksPath .githooks, or a tool like pre-commit that does the wiring.

Try it

Write a hook that refuses to commit anything containing the word TODO, then watch it work:

edit .git/hooks/pre-commit
# put a check in it, save
echo "x = 1  # TODO fix this" >> count.py
git add count.py
git commit -m "This should be refused"
How hooks work in this sandbox

There's no shell in a browser, so a hook here is JavaScript rather than a shell script. The path, the timing, and the veto are real: the file lives at .git/hooks/pre-commit, it runs before the commit is made, and returning false (or throwing) cancels it exactly as a non-zero exit would.

Your hook is called with one argument, an object with staged (an array of {path, text}) and fail(message). What you won't get here is the real thing's environment: no $PATH, no linters, no exit codes.

The details (open as much as you like)

Which hooks can say no
Can vetopre-commit, prepare-commit-msg, commit-msg, pre-rebase, pre-push, pre-merge-commit, pre-applypatch, and server-side pre-receive / update
Can'tpost-commit, post-checkout, post-merge, post-rewrite, post-receive — they run after the fact, and their exit code is ignored

So "reject this" has to happen in a pre- hook, and "react to this" belongs in a post- one. Trying to undo something in a post- hook is the classic mistake — by then the commit exists and you'd be rewriting history behind the user's back.

And every client-side hook can be skipped with --no-verify, which is why client hooks are a convenience for the author and never a security control. The enforcement point is the server: pre-receive can't be bypassed by the person pushing.

Sharing hooks with a team 
mkdir .githooks
# write .githooks/pre-commit, commit it
git config core.hooksPath .githooks

The config line is per-clone, so it still needs to be run once by each person — usually from a make setup or a bootstrap script. That's the whole of what hook-management tools automate, plus a runner and a version pin.

Keep shared hooks fast. A pre-commit hook that takes eight seconds trains everyone to type --no-verify, at which point you have the slowness and none of the checking.

The .sample files, and why nothing is running

A fresh .git/hooks/ is full of *.sample files. They're inert examples: git looks for pre-commit, not pre-commit.sample. Remove the suffix and make it executable to activate one.

The most common "my hook isn't running" causes, in order: the file isn't executable, the name has an extension, the shebang points at a missing interpreter, or core.hooksPath is set somewhere and git is looking elsewhere entirely.
