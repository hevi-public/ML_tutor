The idea

Here it is, all of it:

The whole model

A commit is a complete snapshot of your project, plus a pointer to the commit that came before it. A branch is a sticky note with one commit's name on it. HEAD is a sticky note saying which branch you're standing on. Almost every git command is a way of moving one of those notes.

Two consequences do most of the work in this course.

Commits are snapshots, not diffs. Git shows you diffs because diffs are what humans want to read, but it stores whole trees. When you hear that a rebase "replays your changes", what actually happens is that git computes a diff between two snapshots, applies it somewhere else, and stores the resulting snapshot. The diff is a means, not the data.

History points backwards. A commit names its parent; a parent knows nothing about its children. So "the commits on this branch" is never a list git looks up — it's the answer to a walk, starting at the sticky note and following parents until it runs out. Everything follows from that:

  • Deleting a branch deletes a sticky note. The commits are untouched — they have simply become unreachable, which is why they can be recovered.
  • You cannot edit a commit. Its name is a hash of its contents, parent included, so changing anything makes a different commit. Every "rewrite" command builds new commits and moves a sticky note to them.
  • Changing one commit changes every commit after it, because each one's hash includes its parent's hash. Rewriting the tip is cheap; rewriting the root rewrites everything.

The details (open as much as you like)

Why "snapshot" and not "change"

Every commit stores a tree: the entire file list, with an id for each file's contents. If a commit changes one file in a thousand, the new tree reuses the other 999 ids, so a snapshot costs about what a diff would. You get the storage efficiency of diffs and the addressing simplicity of snapshots at once.

This is why git checkout <old-commit> is instant and exact: there is nothing to reconstruct or unwind. The old state is sitting right there.

What "HEAD is detached" actually means

Normally .git/HEAD contains a ref name:

ref: refs/heads/main

So HEAD points at a branch, which points at a commit. Committing moves the branch, and HEAD comes along because it names the branch, not the commit.

After git checkout <commit>, HEAD contains an object id directly. Commits still work, but no branch moves to include them — so the moment you check out something else, they're unreachable. That is the entire content of the scary detached HEAD warning: nothing is following you. Rebase and bisect both spend their whole time in this state on purpose.

The three trees, in one table

Most confusing git states are a disagreement between three things that normally look identical:

HEADthe snapshot of your last commit
the indexthe snapshot your next commit will be
the working treethe files as they are on disk

git status is nothing but a report on the two gaps: index versus HEAD ("changes to be committed") and working tree versus index ("changes not staged"). reset --soft, --mixed and --hard are the three answers to "how many of them should I move?" — Unit 2 covers it.
