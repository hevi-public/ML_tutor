The pickaxe

Search history by content instead of by path: when did this string appear, and which commit took it out again?

The idea

git grep searches your working tree. The pickaxe searches history, and it comes in two flavours that answer different questions:

-S<string>commits where the number of occurrences of that string changed — so, where it was introduced or removed
-G<regex>commits whose diff mentions it at all, including lines merely moved around

The distinction is sharper than it looks. Move a line containing API_KEY from one file to another: the occurrence count across the commit is unchanged, so -S says nothing and -G reports it. So -S answers "who introduced this?" and -G answers "who touched anything to do with this?"

In practice -S is the one you want, and it's astonishingly effective at the question that comes up most: this line exists, why?

git log -S'DEPRECATED_FLAG' --oneline        # who added it, who removed it
git log -S'password' --all --oneline         # across every branch
git log -S'foo' -p                           # with the diffs, to read the context

Try it

The sandbox has a deploy script that briefly contained a hard-coded password. It's gone from the tip. Find both ends of its life:

cat deploy.sh                    # clean now
git log --oneline
git log -S'hunter2' --oneline    # two commits: the one that added it and the one that removed it
git log -S'hunter2' -p           # read what actually happened
git log -G'PASSWORD' --oneline   # a wider net

The details (open as much as you like)

The two commits -S always finds

Searching for a removed string typically returns exactly two commits: the one where the count went 0 → 1, and the one where it went 1 → 0. Which is what makes it the right tool for a leaked credential — you learn when it was exposed and for how long, which is what the incident writeup needs.

Add --all so branches and tags are searched too, and --reverse to read oldest-first, which is the natural order for a story.

Narrowing it: paths, pathspec magic and -L 
git log -S'timeout' -- src/            # only under src/
git log -S'x' -- . ':(exclude)*.lock'  # skip the noisy generated files
git log -L 10,20:config.ini            # the history of those lines specifically

-L is the underused one: it prints the successive diffs of a line range, following the lines as they move within the file. For "how did this function get like this" it's better than blame, because it shows the sequence rather than only the last step.

    Why it's slower, and when to care

    The pickaxe has to diff every commit it considers. On a large repository that's slow — noticeably so on --all. Mitigations, in order of usefulness: give it a path, give it a range (git log -S'x' v2.0..HEAD), and use -- before the path so git doesn't have to guess.

    It also only ever sees text diffs, so a string inside a binary blob won't be found unless you've told git how to diff that format.
