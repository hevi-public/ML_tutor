blame, moves and copies

Plain git blame answers a slightly different question from the one you asked, and after any refactor the difference is the whole story.

The idea

git blame <file> tells you, for each line, the last commit that changed that line in that file. That last clause is the problem. Rename the file, move a function between files, or reindent the block, and every line's answer becomes the commit that did the moving — which is almost never who you're looking for.

Three flags fix it, and they are the whole point of this page:

-Mdetect lines moved within the file, and follow them past the move
-Cdetect lines copied from other files modified in the same commit. Repeat it (-C -C) to search files that weren't modified too
-wignore whitespace, so a reindent stops hiding the author

Habit worth forming: never run plain git blame. Run git blame -w -M -C, always. It's slower and it's right.

Two more that narrow the question:

-L 40,60only those lines. Much faster on a large file
<rev> -- <file>blame as of an older commit — what did this look like before the rewrite?

Try it

The sandbox has a file that was renamed, then split in two. Blame the reporting code and watch the answer change with the flags:

git log --oneline
git blame report.py            # everything points at the split commit
git blame -C report.py         # …now the lines' real origin shows through
git blame -M -C report.py
git log --oneline -- report.py  # only the commits git thinks touched this path

The details (open as much as you like)

Why rename detection is a guess

Git stores no renames. A commit that renames a file stores a tree without the old path and with the new one — the "rename" is inferred later by comparing content similarity, and the threshold is configurable (-M50% by default in diff).

Consequence: a rename plus heavy editing in the same commit may not be detected at all, and splitting the change into two commits (rename, then edit) makes history much more legible. That's a real argument for the "one logical change per commit" rule beyond aesthetics.

--follow, and why it's log's version of the same problem

git log -- <file> stops at the commit where the path appeared, because before that the path didn't exist. git log --follow -- <file> continues through renames.

It's deliberately limited to a single path — the machinery only tracks one rename chain at a time — so --follow with a directory or two files doesn't do what you'd hope. For anything more complicated, the pickaxe is the better tool.

When blame is the wrong question

Blame answers "who touched this line last", which is a proxy for "why is this line like this" — and a poor one when the interesting commit is two moves back. Better instincts for that:

  • git log -S'<the exact text>' — every commit where that string's occurrence count changed. Finds the introduction directly.
  • git log -L 40,60:file.py — the history of just those lines, following them as they move.
  • Blame the commit's parent: git blame <commit>~ -- file to see what was there before.
