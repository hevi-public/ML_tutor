Unit 3 · Debugging & forensics

fsck and dangling objects

The last resort, and a genuinely useful one: everything in the database that nothing points at.

The idea

Git deletes objects only when gc runs, and gc only deletes objects nothing can reach. So between losing something and gc noticing, the object is still there — and git fsck is how you list what's in that state.

git fsck --unreachable --no-reflogs

Two words that get used loosely and mean different things:

unreachableno ref can get to it by walking parents and trees
danglingunreachable, and nothing unreachable points at it either — so it's the tip of a lost chain

Dangling is the more useful list: a lost branch of six commits produces six unreachable commits but only one dangling one, and that one is the tip you want to put a branch on.

--no-reflogs is not optional in practice. By default the reflog counts as a starting point, so anything the reflog remembers is "reachable" and fsck stays quiet — which is exactly the case where you didn't need fsck anyway. Excluding reflogs shows what's genuinely orphaned.

Try it

This sandbox had a branch deleted. Compare what fsck says with and without reflogs, then rescue the work:

git fsck --unreachable                # quiet: the reflog still reaches them
git fsck --unreachable --no-reflogs   # there they are
git cat-file -p <one of the commit ids>
git show <that id>                    # what was in it?
git branch rescued <the newest one>    # give it a name and it's history again

The details (open as much as you like)

Where lost work actually comes from
A deleted branchthe commits, plus the branch's own reflog, are gone. HEAD's log usually still names them
Commits on a detached HEADif HEAD was never on a branch, only HEAD's reflog knew — and once that expires, only fsck
A dropped stasha stash is a commit; dropping it unreferences it. git fsck finds it and git stash apply <id> takes it back
An abandoned rebasethe pre-rebase chain, findable via ORIG_HEAD or the reflog first
git added but never committedthe blob exists, with no tree or commit around it. fsck lists it as a dangling blob and cat-file -p prints your file back

That last row is the one people don't know, and it's saved many an afternoon: git add writes a real object, so work you staged and then destroyed is recoverable even though it was never committed.

--lost-found, and turning a list into files

git fsck --lost-found writes what it finds into .git/lost-found/ — dangling commits as refs, dangling blobs as files you can open in an editor. When you're facing forty dangling blobs and you don't know which one is your work, having them as files to grep is much better than forty cat-file invocations.

In this sandbox --lost-found isn't implemented here; fsck lists objects and you inspect them with cat-file or the object explorer. Nothing in this sandbox is ever packed either, so fsck sees every object as a loose file.
The other job fsck does: integrity

Reachability is the everyday use, but fsck's actual purpose is verifying the database: rehashing objects and confirming they hash to their own names, and checking that every referenced object exists. --strict turns on the pedantic checks (odd modes, malformed trees, duplicate entries).

Corruption in git is rare and, when it happens, usually the disk's fault rather than git's. If fsck reports a missing object, the fix is almost always to fetch it from a clone that still has it — one of the quiet benefits of a distributed system: every clone is a backup that can be verified by hash.
