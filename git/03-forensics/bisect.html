Unit 3 · Debugging & forensics

bisect

Ten questions to find one bad commit in a thousand. The command is easy; the skill is choosing a test that answers cleanly.

The idea

Something worked in March and doesn't now. There are 800 commits in between. Reading them is hopeless; binary search isn't:

git bisect start
git bisect bad                 # the current commit is broken
git bisect good v2.1           # this one was fine
# git checks out a commit halfway between. You test it.
git bisect good                # or: git bisect bad
# …repeat. About 10 rounds for 800 commits.
git bisect reset               # back to where you were

Each answer halves the range, so the cost is log₂(n) tests: 800 commits is ten. Git tracks the state in .git/BISECT_* and refs/bisect/*, checks out the midpoint for you, and at the end prints "<id> is the first bad commit".

What makes bisect work is the assumption that the property is monotone — good, good, good, bad, bad, bad. When it isn't (flaky test, a bug fixed and reintroduced), bisect will still give you an answer, and the answer will be wrong. That's the thing to be careful about, not the commands.

Try it

The sandbox has twelve commits. The tokenizer test passes at the start and fails at the tip; exactly one commit broke it. Find it:

git log --oneline
git bisect start
git bisect bad
git bisect good HEAD~11
cat tok.py                     # is the bug here? look at how it splits
git bisect good                # or bad
# …keep going until git names the culprit
git bisect reset

The bug: at some point text.split() became text.split(" "), which keeps an empty string when there are two spaces in a row. So your test each round is: does tok.py split on the literal " "?

The details (open as much as you like)

bisect run — let a script answer

If the test can be automated, don't sit through ten rounds:

git bisect start HEAD HEAD~11
git bisect run python -m pytest tests/test_tok.py

The convention is the shell one: exit 0 means good, anything from 1 to 124 means bad. Two special codes matter — 125 means "can't test this one, skip it" (use it when the build is broken for unrelated reasons), and anything ≥ 128 aborts the bisect.

The trick that makes this genuinely powerful: your test script doesn't have to be in the repository. Keep it in /tmp, so the same script runs against every commit even at revisions where it didn't exist yet.

In this sandbox There's no shell to run a script in, so git bisect run isn't available here — typing it says so rather than pretending. In the lab below you play the part of the test script: at each step, read tok.py and answer good or bad. The search itself, and the state it keeps in .git/, is real.
skip, and what it does to the answer

git bisect skip says "this commit can't be tested" — it doesn't build, or the feature doesn't exist yet. Git excludes it and picks another midpoint.

Skip enough commits and bisect can only narrow the answer to a range rather than a commit, and it says so: "There are only 'skip'ped commits left to test". That's an honest result, not a failure — it tells you the break is inside a region you can't test, which is itself worth knowing.

The state files, and bisecting without leaving your work

Bisect keeps everything on disk, so you can look:

.git/BISECT_STARTthe branch to return to at reset
.git/BISECT_LOGevery answer you gave — replayable with git bisect replay
refs/bisect/badthe current known-bad commit
refs/bisect/good-<id>one ref per known-good commit

Because it works by checking out commits, bisect needs a clean worktree. If you're mid-change, stash first — or bisect in a linked worktree, which is the better habit: your main checkout stays exactly as it was.

And git bisect log > bisect.log before you give up for the day. git bisect replay bisect.log puts you back mid-search tomorrow.
