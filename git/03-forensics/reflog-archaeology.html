Reflog archaeology

Your local history of commands, used as evidence. Where was this branch on Tuesday, and what was I standing on when I made that commit?

The idea

Unit 2 used the reflog as a rescue tool. It's also a record, and reading it as one answers questions the commit graph can't:

  • What did I do to this branch this morning? Every movement, with a reason attached: commit:, rebase (finish):, reset: moving to, checkout: moving from X to Y.
  • Where was main when I branched? main@{n} walks the branch's own log, separately from HEAD's.
  • What was I doing on Tuesday? The selectors take dates: main@{yesterday}, HEAD@{2.hours.ago}, main@{2026-07-01}.

The distinction to keep straight: HEAD's log records where you were, and each branch's log records where that branch was. They diverge constantly — every time you commit on another branch, HEAD's log gains an entry and this branch's doesn't.

git reflog                        # HEAD's log: everywhere you've been
git reflog show main              # main's log: everywhere main has been
git reflog --date=iso             # with real timestamps rather than @{n}
git log -g --oneline              # the reflog as commits, so log's flags work

That last one is worth remembering: git log -g walks the reflog instead of the parent chain, so you can grep it, patch it, or format it like any other log.

Try it

The sandbox has a history of moves in it already. Read it as a story:

git reflog
git reflog show main
git log -g --oneline main
git reflog --date=iso
cat .git/logs/HEAD                # the raw file, one line per movement
cat .git/logs/refs/heads/main

Notice that the file has both the old and new id on every line. That's the property that makes recovery work: the log records what each ref moved away from.

The details (open as much as you like)

Reading the raw format 
d1cf19b 587bc61 Ada Rivera <ada@example.com> 1709543400 +0000	commit: fix typo
587bc61 26a5243 Ada Rivera <ada@example.com> 1709543460 +0000	reset: moving to HEAD~2

Old id, new id, who, unix timestamp, timezone, tab, message. All zeros in the old-id column means the ref was created.

Because it's a plain file, you can read it when git's own tooling isn't cooperating — a corrupted index or a half-finished rebase doesn't stop cat .git/logs/HEAD from working. It's the first place to look when a repository is in a state you don't recognise.

    Expiry, and the two different clocks
    gc.reflogExpire90 days — for entries still reachable from the ref
    gc.reflogExpireUnreachable30 days — for entries pointing at commits nothing else reaches

    Both are enforced by git gc rather than by a timer, so an untouched repository can hold entries for years. Conversely, a repository where something ran git gc --prune=now may have lost them already.

    If you're about to do something frightening to a repository you care about, the cheapest insurance is a copy of the directory. The reflog is very good, and it is not a backup.

    What the reflog tells you about someone else's repository: nothing

    Reflogs are never transferred. They aren't in a clone, aren't fetched, aren't pushed. A fresh clone has exactly one entry per ref — "clone: from …".

    Which has an investigative consequence worth knowing: on a build server or in a fresh clone, the reflog can't tell you what happened, and the questions you'd have asked it have to go to fsck or to the forge's own logs instead.
