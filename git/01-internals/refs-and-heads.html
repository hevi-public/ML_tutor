Refs, HEAD and symbolic refs

Branches are one-line text files. Once you have edited one with echo, the difference between checkout, reset and branch -f stops mattering very much.

The idea

An object id is 40 characters of hex, so git gives you names for the ones you care about. A ref is a name holding one object id, stored as a file:

.git/refs/heads/main            → a branch
.git/refs/tags/v1.0             → a tag
.git/refs/remotes/origin/main   → a remote-tracking ref

Each contains one line: a 40-character id and a newline. That's it. A branch is not a container, a list, or a lineage — it is a filename with a hash in it.

HEAD is the interesting one, because it usually doesn't contain an id at all:

$ cat .git/HEAD
ref: refs/heads/main

That's a symbolic ref — a ref pointing at another ref. It's the indirection that makes committing work: git commit updates whatever ref HEAD names, so the branch moves and HEAD follows for free.

Try it

Read the files yourself, then move a branch by writing to one. The .git tab under the prompt shows every ref and the contents of HEAD as you go.

cat .git/HEAD
cat .git/refs/heads/main
git symbolic-ref HEAD                # the polite way to read it
git update-ref refs/heads/spike HEAD~2   # make a branch with plumbing
git checkout --detach HEAD~1          # now look at .git/HEAD again
cat .git/HEAD

The details (open as much as you like)

Why checkout is two different operations

git checkout main writes ref: refs/heads/main into HEAD and updates your files. git checkout <commit> writes the raw id instead. That single difference is detached HEAD, and it explains the behaviour that follows from it: committing works, but nothing is following you, so the commits become unreachable as soon as you leave.

Modern git splits the two jobs into two commands — git switch for branches, git restore for files — precisely because checkout doing both is how people accidentally throw away uncommitted work.

packed-refs, and refs that aren't files

A repository with thousands of tags would need thousands of tiny files, so git periodically moves them into a single .git/packed-refs:

# pack-refs with: peeled fully-peeled sorted
a3f5c1... refs/heads/main
b91d20... refs/tags/v1.0
^c00ffe...

The ^ line is the commit an annotated tag points at, cached so readers don't have to open the tag object. A ref can therefore live in either place, which is why you should read refs with git rev-parse or git for-each-ref rather than cat in a script — the file may simply not be there.

In this sandbox nothing is ever packed, so every ref is a file.

The whole family of ref-moving commands
git branch x <rev>create the ref, refuse if it exists
git branch -f x <rev>move it, even if it exists
git reset <rev>move the ref HEAD names, and the index too
git update-ref refs/heads/x <rev>move any ref, no safety checks, no worktree changes
git symbolic-ref HEAD refs/heads/xchange which branch HEAD names, without touching files

They differ in what else they touch, not in what they fundamentally do. Every one of them writes a reflog entry, which is what makes all of them survivable.
