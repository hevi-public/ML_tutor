Unit 1 · Internals & plumbing

Revision syntax

~ and ^, two dots and three, @{1} and @{u}. The notation experienced git users trade without ever having been taught it out loud.

The idea

Every command that takes a commit takes this grammar, so learning it once pays off everywhere. Two rules cover most of it.

~ goes back. ^ picks a parent. For an ordinary commit with one parent they're the same thing, which is why people use them interchangeably and then get surprised at a merge:

HEAD~the first parent — one step back
HEAD~3three steps back, always taking the first parent
HEAD^the first parent. Same as HEAD~
HEAD^2the second parent. Only a merge commit has one
HEAD~2^2two back, then the second parent of that

So on a merge commit, HEAD^ is the branch you were on and HEAD^2 is the branch you merged in. HEAD~2 is not "two commits ago" in any general sense — it's two steps down the first-parent line, ignoring everything that was merged in.

Two dots is a range; three dots is "how we diverged".

main..featurecommits in feature that aren't in main — "my branch's own work"
main...featurecommits in either but not both — the full picture of the divergence
^main featurethe long form of main..feature, and it takes any number of terms

The one that trips people up: git diff a..b and git diff a b mean the same thing, but git log a..b and git log a b do not. For log, a range is a set of commits to walk; for diff, it's just two endpoints.

Try it

The sandbox has diverged branches, so all of this has something to bite on:

git log --oneline --all
git rev-parse HEAD~2
git rev-parse main..feature       # try it: what does rev-parse make of a range?
git rev-list --count main..feature
git rev-list --left-right --oneline main...feature
git show :/README                 # find a commit by its message
git rev-parse HEAD^{tree}

The details (open as much as you like)

@{…} — asking about the past instead of the graph

Everything above navigates the commit graph. The @{…} family navigates the reflog instead, which is a different question: not "what came before this commit" but "where was this ref before".

    HEAD~1 and HEAD@{1} are almost never the same commit. The first is the parent of where you are; the second is wherever you were standing one command ago. After a reset --hard, the second is your rescue and the first is not.

    Peeling: ^{tree}, ^{commit}, ^{}

    <rev>^{tree} gives the tree of that commit rather than the commit, which is how you compare trees or read a file without checking anything out. ^{commit} follows an annotated tag through to the commit it names — necessary because an annotated tag is its own object, so v1.0 and v1.0^{commit} are two different ids.

    <rev>^! is a range containing that commit and nothing else: handy for git log v1.0^! when you want one commit's entry and no ancestors.

    Naming things without ids at all
    :/fix the parserthe newest commit whose message contains that text
    @{-1}the branch you were on before this one — what git checkout - uses
    @{u}your branch's upstream, usually origin/<same name>
    HEAD:src/app.pythe blob at that path in that commit

    Two are worth building a habit around: git log @{u}.. is "my unpushed commits", and git diff @{u}... is "what a pull request would show".
