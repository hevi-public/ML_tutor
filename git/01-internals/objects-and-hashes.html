Objects and hashes

Git is a key-value store where the key is the hash of the value. Once you have typed that hash out by hand, half of git's behaviour stops being surprising.

The idea

Git stores four kinds of object: a blob (a file's contents), a tree (a directory listing), a commit, and an annotated tag. Each one is stored under a key, and the key is the SHA-1 hash of the object itself. That's the whole storage layer.

The hash isn't taken over the file's bytes alone. Git prefixes a header — the type, a space, the length in bytes, and a zero byte — and hashes the lot:

sha1("blob " + <length> + "\0" + <contents>)

So a 12-byte file containing hello world\n is hashed as the 17 bytes blob 12\0hello world\n. You can reproduce this outside git with any SHA-1 tool, and people do, as a sanity check.

Being content-addressed has consequences you rely on daily:

  • Identical content is stored once, however many commits or branches contain it.
  • An id cannot lie about what it names. Corruption is detectable: rehash the object and compare.
  • Nothing can be edited in place. Every command that appears to modify history actually writes new objects — which is why so much of what looks destroyed is merely unnamed.

Try it

Type this in the sandbox and watch the id show up as a filename:

echo "hello world" > hello.txt
git hash-object hello.txt          # compute the id, store nothing
git hash-object -w hello.txt       # compute it and write the object
ls .git/objects/                   # the first two hex characters are the directory
git cat-file -t <paste the id>      # what type is it?
git cat-file -p <paste the id>      # print it back

Note what did not happen: nothing was committed, nothing was staged, and git status still shows an untracked file. You put an object in the database directly.

The details (open as much as you like)

Where the object actually lands

An id like 3b18e512dba79e4c8300dd08aeb37f8e728b8dad becomes the path

.git/objects/3b/18e512dba79e4c8300dd08aeb37f8e728b8dad

The two-character directory exists purely so that no single directory ends up with a hundred thousand entries. The file itself is the header plus contents, zlib-compressed — so cat shows you binary, and git cat-file -p is how you read it.

This form is called a loose object. Git later bundles many of them into a packfile, which is its own topic.

SHA-1, and why git isn't worried

SHA-1 has been broken for collision resistance since 2017. Git's exposure is smaller than it sounds — an attacker needs a collision between two objects where you would accept either — but it is real, and git ships collision detection that rejects the known attack patterns. The long-term answer is SHA-256 repositories, which git supports and almost nobody uses yet, because every hosting provider and tool would have to agree at once.

Practical upshot: the ids in your repository are fine. Don't build a security boundary on them.

Why abbreviated ids work, and when they stop

You can name an object by any unambiguous prefix of its id — usually seven characters. Git resolves the prefix by looking for exactly one match and errors if there are two. Very large repositories eventually need more characters; git lengthens its own output automatically as a repository grows, which is why the ids in git log --oneline are occasionally eight or nine characters.
