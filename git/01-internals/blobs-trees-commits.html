Unit 1 · Internals & plumbing

Blobs, trees and commits

One walk, from a commit id down to a file's bytes, with cat-file the whole way. After this the object graph is something you can navigate rather than something you've read about.

The idea

Three object types stack into everything git knows:

blobbytes. No name, no permissions, no history.
treea list of entries: mode name id. The id is a blob (a file) or another tree (a subdirectory).
commitone tree id, zero or more parent ids, an author, a committer, a message.

So a commit doesn't contain your files; it names one tree, which names blobs and further trees. "The state of the project at commit X" is a walk, and it is a walk you can do by hand:

git cat-file -p HEAD              # the commit: find its "tree" line
git cat-file -p <tree id>         # the root directory listing
git cat-file -p <blob id>         # a file's contents

Try it

Do that walk in the sandbox. The fixture has a file inside a subdirectory, so you'll pass through two trees on the way down. The object explorer below the prompt does the same thing with clicks if you'd rather see it laid out.

Then try the shortcut git gives you for the same journey:

git ls-tree -r HEAD               # every blob in the commit, recursively
git rev-parse HEAD^{tree}         # the tree id, without reading the commit
git cat-file -p HEAD:notes/plan.md  # straight to one file's contents

The details (open as much as you like)

Reading a tree entry

A tree prints like this:

100644 blob 8d0e41234f24b6da002d962a26c2495ea16a425f	hello.txt
040000 tree 4d5fcadc293a348e88f777dc0920f11e7d71441c	notes

The number is the mode, and git stores only a handful:

    Note what's missing: no owner, no group, no read/write bits, no timestamps. Git records the executable bit and nothing else, which is why "the permissions changed after clone" is never a git bug.

    Inside a commit object

    git cat-file -p HEAD prints the object nearly verbatim:

    tree b63a1aea7985e1741ecf1d833a25ed164eef0503
parent 26a52436a5b6d5a24e2b1c8cebc0eb0d4b6e2f9a
author Ada Rivera <ada@example.com> 1709543400 +0000
committer Ada Rivera <ada@example.com> 1709543400 +0000

Add the greeter

    Two people, not one. The author wrote the change; the committer created this object. They differ whenever a commit is replayed — after a rebase or a cherry-pick, the author line is preserved and the committer line becomes you and now. That's how git log can show a six-month-old date on a commit you made this morning, and it's the mechanism behind "why did my whole branch's commit dates stay the same but the ids change?"

    The two timestamps are why rebasing is not reproducible by default: same changes, different committer time, different ids.

    Empty directories, and why git won't track them

    Trees contain entries for blobs and trees. There is no representation for "a directory with nothing in it" — a tree with no entries would be a different object nobody references. This isn't a policy decision git could reverse; it falls out of the format. Hence the .gitkeep convention: put a file in it, and the directory exists because its contents do.
