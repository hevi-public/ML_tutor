Unit 1 · Internals & plumbing

The index, properly

The index isn't a queue of changes — it's a complete proposed snapshot. That one correction fixes most confusion about staging.

The idea

People picture the index as a list of changes waiting to be committed. It is actually a full flat list of every path in your project, each with a blob id and some cached file stats:

$ git ls-files -s
100644 8d0e41234f24b6da002d962a26c2495ea16a425f 0	README.md
100644 151e2f818f2f6a619a0049dec48becf86b836ca7 0	count.py

Read that as a proposed tree. git commit doesn't gather your changes; it turns the index into a tree object and points a commit at it. That's why git write-tree works at any moment, and why an empty git add session still produces a complete snapshot.

So git status is two comparisons against this middle thing:

index vs HEAD"Changes to be committed"
working tree vs index"Changes not staged for commit"
in neither"Untracked files"

And it explains the situation everyone hits: a file can appear in both lists at once. You staged version 2, then edited it into version 3. The index holds v2, disk holds v3, and committing gets you v2 — which is a feature, and the entire basis of git add -p.

Try it

The sandbox starts dirty on purpose: one staged change, one unstaged, one untracked file. Take it apart:

git status
git ls-files -s                 # the index as a proposed snapshot
git diff                        # worktree vs index
git diff --staged               # index vs HEAD
git write-tree                  # the tree the index would become
git cat-file -p <that tree id>   # a real tree object that isn't in any commit

Then stage the README edit, edit it again before committing, and look at git status. Both lists mention it.

The details (open as much as you like)

The stat cache, and why status is fast

Each index entry stores the file's size and modification time as of the last add. To answer "did this file change?", git compares stats first and only reads the file if they differ. That's how git status stays quick in a repository with 100,000 files.

It's also why a mangled clock or a filesystem with odd timestamps can make git think everything changed, and why git status occasionally writes to .git/index even though you only asked it to look.

Stage numbers: the 0 in ls-files -s

That third column is the stage. Normally it's 0. During a conflict the same path gets three entries at once:

1the merge base's version
2ours
3theirs

All three sides of the three-way merge are sitting in the index, which is how tools like git checkout --ours and a merge tool get at each version without re-reading commits. git adding the resolved file collapses them back to a single stage-0 entry — which is precisely what "marking a conflict resolved" means.

Unstaging, and the three commands that do it
git restore --staged <file>index ← HEAD; worktree untouched. The modern spelling.
git reset <file>the same thing, in the older spelling
git restore <file>worktree ← index. Throws away your edit — the one to be careful with.

In this sandbox use git reset <file> and git checkout -- <file>; restore isn't implemented here, and typing it will tell you so.
