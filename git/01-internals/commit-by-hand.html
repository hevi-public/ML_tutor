Unit 1 · Internals & plumbing

A commit, by hand

Build a commit with four plumbing commands and no git commit anywhere. This is the page that makes the rest of git stop being magic.

Before you start This page uses everything in Unit 1: objects, trees, the index and refs. It's the payoff for them, so it's worth having read them first.

The idea

git commit is a wrapper. Underneath, it does four things, each of which is a separate command you can run yourself:

1git hash-object -w <file>store the contents as a blob
2git update-index --add …put that blob at a path in the index
3git write-treeturn the index into a tree object
4git commit-tree <tree> -p <parent> -m …make a commit object pointing at that tree
5git update-ref refs/heads/…move the branch to it

Notice where the boundary falls. Steps 1–4 only add objects; nothing about your repository's visible state changes. Only step 5 moves a ref — and that is the step that makes the commit part of history. A commit object that no ref reaches is exactly what "dangling" means, and you can create one on purpose here.

This split is not trivia. It's why the reflog can undo things, why rebase is implementable at all, and why commit-tree is what tools like filter-repo are built out of.

Try it

Work through it in the sandbox, pasting each id into the next command:

echo "print('hi')" > hi.py
git hash-object -w hi.py                  # → blob id
git update-index --add hi.py              # index now proposes it
git write-tree                            # → tree id
git commit-tree <tree id> -p HEAD -m "Add hi.py"   # → commit id
git log --oneline                         # nothing changed! the commit is unreferenced
git update-ref refs/heads/main <commit id>
git log --oneline                         # now it's history

Between the fourth and sixth commands you have a real commit that no branch can see. git cat-file -p it, and try git fsck --no-reflogs before you run update-ref.

The details (open as much as you like)

What commit-tree needs, and what it invents

commit-tree takes a tree, zero or more -p parents, and a message. It fills in the author and committer from your config and the clock. Everything else about a commit — that it belongs to a branch, that it's "the latest", that it's on your current line of work — is not stored anywhere in the commit. Those are facts about refs.

Pass two -p flags and you have made a merge commit. There is nothing else to a merge commit: the merging is work you do to produce the tree, and the second parent is a claim you're making about history.

Why write-tree needs the index at all

You could imagine a make-tree-from-directory command, and git doesn't have one, because the index is where the decisions live: which paths exist, which blob each one holds, what mode it has. write-tree is a pure function of the index — it reads no files from disk.

Which is why git write-tree immediately after git add -p gives you the tree of your partial staging, and why a commit can contain something that isn't on your disk at all.

The same five steps, as a shell one-liner 
git update-ref refs/heads/main \
  $(git commit-tree $(git write-tree) -p HEAD -m "Add hi.py")

That is, modulo hooks, config and error handling, what git commit -m "Add hi.py" does. Plumbing commands are designed to be composed like this — stable output, one thing per command — which is why so much of git was originally shell scripts over exactly these primitives.
